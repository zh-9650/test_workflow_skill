# 需求理解 Skill：最终改版设计与取舍

日期：2026-10-22。实现入口：[test-business-modeling/SKILL.md](../../test-business-modeling/SKILL.md)。

## 判断

此前的方向值得保留：从用户任务分析对象、事件、状态、关系、失败后果、配置生效和判断依据，能改善只复述页面功能的问题。

不足主要在分析顺序与完成标准。现有指令虽已要求“查漏、保留条件、独立审查”，但这些要求仍容易被整理模型、补引用和填审查表替代。真实样本表明，条款中的多个承诺可以只挂到一个事件，而具体差异未被保存。加强后台机制也没有自动解决基础交互和正常操作遗漏。

因此，本次将目标从“产出完整模型”进一步明确为“形成足以判断业务对错的基线”。模型是保存结果的工具；业务目标、有效条款、例子、分歧和验收依据是分析输入。

## 专家方法怎样落入 Skill

| 专家会做的工作 | 原版本情况 | 本次调整 |
|---|---|---|
| 理解真实工作、结果使用者和错误损失 | 已有用户任务与依赖，业务目标和使用环境较弱 | 在建模前查业务目的、相关方、责任边界、现状与变化 |
| 评审需求本身，不只总结需求 | 已有冲突/未知处理，缺少连贯的语义分析动作 | 提取复合条款中的具体承诺，检查歧义、矛盾、可达性和可判断性 |
| 用实例与反例澄清不同理解 | 已有场景与错误实现，但“具体实例留给下游”可能过度约束 | 明确允许业务例子与关键组合；只把执行数据集和步骤后置 |
| 按问题选择分析工具 | 状态、关系、输入专项较强 | 加入决策表、状态—动作表、边界含义、计算口径、交接分析的触发条件 |
| 发现规格之外值得查证的风险 | 历史缺陷和十三机制视角已有基础 | 增加使用场景、质量要求和风险后果分析，区分风险线索与已确认需求 |
| 判断如何知道结果正确 | 原版已有证明边界，是应保留的能力 | 与业务验收标准衔接，区分确定性规则、概率性质量与观察入口待落实 |
| 独立读资料，挑战作者理解 | 原版已明确要求，实际执行未充分落实 | 审查者先留下自身关注点；来源基础核对与风险深查分开；不能以长度/计数验收 |
| 把理解传给下一位设计者 | 已有模型和三份产物 | 明确规则必须同步进模型，附件说明和来源引用不能替代实际承接 |

这些调整不宣称所有专家遵循同一固定流程。它们综合了本次实际失败样本与下列一手方法：

- [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)：测试依据分析、静态审查、验收标准、条件/状态方法与风险。
- [Cucumber Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/)：区分规则、例子、问题，以具体场景澄清共同理解。
- [James Bach HTSM](https://www.satisfice.com/download/heuristic-test-strategy-model)：从产品、项目和质量等角度启发分析，按上下文取舍。

## 新的分析顺序

```mermaid
flowchart LR
    A[查证目标与有效证据] --> B[用任务和例子澄清规则]
    B --> C[建立模型与验收依据]
    C --> D[独立审查与修订]
    D --> E[澄清同步与交接]
    B -->|查不到或有冲突| A
    D -->|具体缺口| B
```

这不是五次审批。澄清可以在分析中发生，用户已有答案不重复问；阶段确认仍由既有 Router 处理。

本阶段仍不生成测试点和测试用例。区分的是产物职责，不是禁止使用分析方法：用两种状态解释规则属于业务理解；编排执行账号、步骤、样本、预期检查序列属于后续用例设计。

## 防止本次改版走向另一种问题

- 不规定测试点或模型数量，不要求每个事件拆成固定数量分支。
- 不强制每条简单规则都有正反例，不穷举全部条件笛卡尔积。
- 不把所有质量属性变成产品承诺，不随意增加性能指标、重试、锁或恢复要求。
- 不增加必填 JSON 字段，也不新增一套强制台账。利用已有模型和审查摘要保存内容。
- 不因当前没有接口、源码或数据库结构阻断已经明确的业务分析。
- 不把模拟利益相关方视角当作真实访谈，不把风险假设当已确认缺陷。
- 不按危险源专用术语写通用 Skill。该案例只用于回归检查；补充图书馆场景检查迁移性。
