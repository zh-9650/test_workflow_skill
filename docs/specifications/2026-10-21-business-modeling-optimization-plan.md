## 2. 全程保留的边界

- 以当前任务有效资料定义正确业务行为。代码、接口返回、原型演示和历史缺陷不自动成为产品承诺。
- 重要事实保留来源、条件、例外及适用范围。无依据且会改变结果的事项保持未决，不自行补成确定规则。
- 简单业务紧凑表达；复杂业务展开真实分支、异步、历史、权限、配置和恢复。没有的机制不编造。
- 不以任务、事件、规则、图、引用或问题的数量衡量质量。
- 业务理解可以说明未来需要检查什么，不要求系统已开发或此时执行真实测试。
- 正文使用中文业务名称、图解和因果讲解；内部稳定标识保留在追踪层。少用缩写并不意味着删除分析深度。
- 原始资料、图文报告、内部模型、审查和流程确认各有职责，不能互相冒充证明。

## 3. 阶段①：保留已落地设计，检查消费是否完整

### 输入、工作与输出

沿用当前七项工作：建立项目轮廓；提出依赖查证问题；按用途定位和读取历史资料；核对版本并提取必要事实；探索本轮交互；区分缺口；整理记录与后续去向。

本轮直接范围内的需求与交互按范围完整读取；历史模块按当前问题定向查证。旧报告帮助导航，必要结论回查原始依据。上游管理细节或源码是否继续读取，取决于它是否影响当前判断。不限定问题数、摘要句数或依赖深度。

保留已修正的两项要求：正式生效的评审变更按效力使用；审查核对实际查证内容，不限定台账名称和发现项编号。

交给阶段②的是：当前范围与资料基线、必要依赖事实及来源、条件和例外、版本关系、限制和后续去向。使用现有来源登记、工作记录和审查摘要，不新建强制“意图标签”语法，不提前要求完整能力或事件编号。

### 完成边界

已查明的部分有依据；无法查明的原因和影响明确；停止追踪有理由。资料受限可以继续后续草稿分析，受影响内容不能宣布确定或完整。真实系统尚不可验证不自动成为业务理解阻断。

实施时只核对阶段②至⑤是否真正消费这些内容；除非发现具体矛盾，不修改阶段①的已确认设计。

## 4. 阶段②：用户任务与业务全景

### 4.1 要解决的问题

避免把复杂业务压成几个抽象能力名，也避免按页面目录机械复述。让阅读者先看懂谁要完成什么、从哪里开始、经过哪些活动、最终得到什么，以及基础功能在哪里。

### 4.2 具体工作

1. 从角色、目标、触发场景和实际输入识别用户任务。任务大小依据业务差异，不限定数量。
2. 串起起点、必要前提、主要活动、关键分流和结果；说明结果何时允许被用户或下游使用。此处形成骨架，不提前穷举用例数据。
3. 反查本轮资料中的基础功能：将查询、筛选、编辑、启停、删除、查看历史等实际存在的功能归入任务或独立维护活动，明确排除依据。长旅程不能掩盖基础功能。
4. 使用阶段①查明的依赖，解释对象由谁提供、关系由谁维护、当前功能读取或改变什么、结果给谁使用。独立功能可以没有外部上下游，未确定引擎不强填技术提供方。
5. 解释会影响理解的概念区别和关系，例如对话、任务与一次执行；启用与就绪；当前配置与历史记录。对象身份、归属和独立状态不因通俗化表达而丢失。
6. 用总览图配连续讲解建立业务图景。依赖复杂时增加依赖图；图放在对应讲解附近，不要求固定数量或全部前置。
7. 对照重要来源，检查是否只有入口没有结果、只有复杂专项没有基础功能、同一规则分散重复或重要角色路径遗漏。

### 4.3 输出与完成条件

主报告按任务讲解基础主链、概念、关键分支和依赖。内部能力索引继续作为导航，关联后续具体机制，不形成第二套独立规则。

阶段完成时，应能沿任务解释起点到结果，并定位基础功能；已知重要来源有承接、明确排除或未决去向。未知不能被漂亮流程图掩盖。资料没有写明“取消”等能力时先查证其是否存在，不能仅因为流程图缺一个通用动作就扩需求。

交给阶段③的是任务路径、重要对象与关系、基础功能、关键条件、依赖事实及未决边界。发现新依赖时局部回查阶段①，不重建全部产物。

## 5. 阶段③：业务机制深入分析与判断依据

### 5.1 保留通用分析要素

沿阶段②的重要操作和事件说明：谁对什么对象做什么；哪些条件改变允许性、路径或结果；成功后什么变化；什么按规则保持；失败后留下什么；何时允许后续使用。

保留稳定身份、关系生命周期、独立状态、业务不变量、历史事实、跨模块影响和真实异常恢复分析。条件或恢复语义未知时查证或登记问题，不按常识填答案。

### 5.2 用业务差异决定分析粒度

触发主体、独立动作、状态迁移、结果归属、失败后果或下游影响不同，是需要进一步分析的线索，不是强制拆事件的算法。

分别说明需要独立判断的行为；表达可以是事件、分支、状态迁移、规则或完整流程。合并后仍能清楚定位每种条件和后果，就可以合并；合并导致笼统预期、无法解释时序或判断独立结果，就应拆开。重复出现的同一业务规则可以复用。

例如文件从选择、校验、上传、关联消息到参与回答，可能存在不同责任、状态和失败事实。应查清这些差异如何承接，不要求每个界面动作各建一条事件。同一事件的多个失败分支可以集中描述，但不能只写“失败时正确处理”。

### 5.3 按适用性深入

- **输入**：识别真正改变处理路径或结果的材料特征、内容分布、结构和边界。不是只有扩展名，也不是强制所有文件写固定页数、分辨率或哈希。实际执行数据留到用例阶段。
- **配置**：说明控制什么、谁采用、何时生效、影响哪些对象和版本、什么应保持、怎样识别未采用。只有资料支持时才写存储、广播、缓存和加载。相同输出不自动证明失效，不同输出不自动证明采用正确。
- **异步与失败**：区分受理、排队、处理、完成、可消费等确实不同的业务含义，说明已知超时、重复、中断、部分成功和恢复语义。没有重试或断点续跑承诺时不强造。
- **权限与依赖变化**：分析当前业务实际涉及的状态、授权和关系变化，区分新增、存量、运行中与历史。资料未定义的部分保留问题。
- **并发与旧状态**：解释允许结果、禁止结果、冲突或重复的业务处理。锁、队列和事务方案由技术设计决定，除非本任务有效合同已明确规定。

### 5.4 判断依据与证明范围

对重要结果说明：正确行为依据什么规则；需要核对什么事实；候选证据能证明到哪里；哪些现象单独不足；有哪些观察限制。依据应跟随任务或事件表达，复杂比较才使用表格。

区分当前业务中确实不同的受理事实、实际产物、内容有效性和下游可用性。解析、索引、正式检索是否分阶段完成，由有效需求决定，不能统一写成“检索命中才算解析完成”。普通读写也不强造四层。

跨位置比较先绑定同一对象、任务、版本、范围和时间窗口。关键词命中可能来自其他文档或旧版本，不能自动证明本次输入和配置正确。底层直读、接口读回和端到端使用都是候选证据，按证明能力选择，不要求此时执行。

原生引擎可以作为诊断对照，集成产品正确预期仍由产品需求及有效接口合同决定。

### 5.5 输出与完成条件

候选模型能分别解释重要条件、变化、保持、失败及下游准入，来源中的关键细则没有被大标题吞掉；来源和推导可回查，未决内容没有混入确定事实。具体场景换一条件后，模型能解释结果差异或指出尚未定义。

阶段④接收同版本报告和模型、来源定位、依赖资料、未决限制及修订范围。不得以编号齐全或脚本通过代替这一完成判断。

## 6. 阶段④：独立审查、修订与复核

### 6.1 独立性与输入

沿用真正独立上下文要求，适配宿主可用的子代理或独立会话，不写死工具名。审查者先读相同有效资料，独立形成关注点，再读取候选模型。有效输入包含后来发现的依赖原文、正式评审变更、人工裁定、临时口径、范围及版本，不只给生成者摘要。

只有实际派发、读取、发现和复核记录才能支持已完成独立审查。受限时可继续自查、保存草稿和整理问题，明确“独立审查未完成”；同一 Agent 换角色不能获得独立性，用户确认也不能被解释成审查已经发生。正式放行继续遵循已有工作流，不新增一套降级状态绕过门禁。

### 6.2 检查真实内容

保留现有十三个完整性视角，按适用性核查创建编辑删除、状态、关系、失败一致性、恢复、历史、权限、异步重试、长流程、跨模块、并发旧状态、身份复用和数据一致性。

具体执行：

1. 从来源反查：重要任务、条件、例外、限制和关系有没有遗漏；也检查无数字的重要规则。
2. 从模型反查：结论是否有来源，推导是否确实由有效前提支持，是否混入旧口径或实现猜测。
3. 核对任务、关系、状态、图和未决问题之间是否矛盾，历史依赖是否正确继承。
4. 按风险选择具体场景，检查模型能否解释条件、结果、保持与失败。对高风险结果提出合理错误实现假设，检查判断依据是否有辨别力；假设不是已发现产品缺陷。
5. 判断不适用和缺口是否有依据。无法裁定的产品规则应保留未决，不能靠审查者补成答案。

同一事件可支撑多个维度，只要各维度的实际判断成立。相同引用或措辞相似不能单独认定敷衍。随机抽查可补充审查，但不以固定五条或只查数值规则作为完整性门禁；抽查结果只证明被查部分。

### 6.3 修订闭环与完成条件

每项重要发现保留来源、候选位置、问题、影响、处置依据、复核结果和剩余限制。沿用现有记录承载，不新增强制编号体系或固定台账名称。

生成者按证据回应，审查者复核实际变化；检查直接引用与间接共享条件，同时核对原有正确事实没有误改。完成时已知重要发现均有处置或明确未决去向，独立审查实际状态清楚，不以轮数或“通过”字段收口。

进入阶段⑤的是经审查修订的候选基线、真实业务争议和限制；能自行查清的事项仍由 Agent 查清，不把审查发现全部转成用户问题。

## 7. 阶段⑤：澄清、回复同步与交付确认

### 7.1 提问前核查

先查相关有效来源、依赖事实、已有回复和裁定，考虑别名、图表和版本。说明查证范围及具体缺口，不要求证明所有资料“完全沉默”，不把关键词未命中当作无答案。

区分产品决定、可自行核查的事实、实现选择、待试验事项和资料访问限制。只有需要人决定且影响当前业务或范围的事项进入正式澄清；重要业务后果不能因为涉及技术概念就被排除，纯实现选择不转嫁给用户。

### 7.2 问题独立可读

每题围绕一个决定，自然解释具体场景、已知规则及相关摘录或忠实摘要、仍未明确的地方、不同答案的后果，以及现在要决定什么。来源显示资料名、章节和可访问定位，不只给来源编号。

不要求六个字段标题，不强制二选一。方案空间不明时开放询问；有可行选项时解释对用户和业务的后果，不能把某个选项与未确认的断点续传、自动重试等能力捆绑。没有充分依据就不推荐。

当前可独立回答的问题同轮集中在文末；真正依赖前置答案的问题后置，不拆成无必要的多轮。共享背景可以集中交代，但每个决定应能分别回答。

### 7.3 按回复性质更新

- 正式业务裁定：记录有效来源、范围及替代关系，更新受影响规则。
- 纠错或审阅意见：回查证据，查证属实后修订，不把线索自动升级成产品承诺。
- 获准临时口径：保留临时性质、适用范围和再确认条件，更新本轮适用事实，不改写长效承诺。
- 范围调整：记录明确排除、依赖及剩余影响，不靠悄悄改成非阻断清零。
- 阶段确认：绑定当前范围、版本和限制，由工作流记录，不自动改规则。
- 暂不能决定：保留问题和受影响范围，不自动判通过。

任何实际事实变化都应同步受影响正文、图、内部模型、问题及审查摘要，复核依赖和保持项，再运行适用结构检查。按实际影响局部更新；只有确实解决的问题才能标为已解决。

### 7.4 正式交付条件

影响当前交付的阻断事项经查证、有效裁定、获准口径或明确范围调整处理；剩余限制透明；独立审查实际完成；三份正式文件同版本一致，并由已有 Router 绑定人工确认。后续改动按既有机制触发重审、重新确认和下游失效。

非阻断技术/UI问题可以保留。不得绕过原有确认门禁，也不另造“已确认”布尔值替代工作流状态。

用户要求 HTML 或图解阅读时，继续提供同版本 `deliverables/01-business-understanding.html`。HTML 是人工阅读界面，不能替代正式模型或单独获得另一套规则。

### 8.2 人工报告如何呈现

按“用户场景与范围 → 基础主链 → 概念与任务讲解 → 关键局部机制 → 限制与交接 → 待确认问题”组织。先帮助读者理解，再按需展开证据和追踪。

复杂业务使用足够的图解释主链和主要难点，选择流程图、状态图、关系图、时序图或有来源的标注截图。每张图有场景、关键转折和结果讲解；未知部分明确标识。图形类型、数量和工具由表达需要决定，不固定三张 Mermaid 图或全部放开头。

正文、图、目录和问题用中文业务名称。长台账、字段映射和机器标识放内部文件或可展开区；重要背景和未决影响默认可见。表格用于确需比较的内容，不承担整篇叙事。

HTML 实际渲染检查文字、图、锚点、展开、窄屏布局和内容一致性。图形源码直接显示不算图，截图或演示不能冒充产品实测。无法渲染时记录未验证；工具无溢出不代表真实用户已理解。

### 8.3 模型与下游兼容

保留现有对象、状态机、关系、事件、规则、不变量、流程、来源状态、问题、完整性审查和同步字段。内部能力索引继续聚合具体机制，不强制所有功能填写不存在的外部上下游或技术引擎。

当前测试点合同使用具体机制 ID；其 `model_refs()` 不识别能力索引 ID。交接应展开索引并引用实际机制，不能只写“下游直接消费能力编号”。具体字段以当前调用方为准，不凭文案猜接口。

需要扩展字段时，先说明现有位置为何无法承载、由谁消费及如何兼容。优先使用已有事件/规则/流程和来源记录，不为展示增加必填字段。必要扩展采用最小向后兼容方式，同时更新示例、校验及调用说明；未获授权不改其他阶段的合同。

## 9. 自动检查的责任边界

脚本继续负责确定性结构、字段类型、ID、引用、问题依赖、来源状态及现有确认前检查。阶段①当前没有单独的“意图标签校验器”，不得为放行不存在的检查而新增协议。

若修改校验器：

- 针对实际发现的确定性缺口，说明能证明什么、不能证明什么。
- 保持合法旧模型兼容；新严格要求须有明确适用条件，不能使旧产物被迫改造成新展示格式。
- 证明边界存在时检查合法结构与成对内容；是否要求新模型提供、在哪个层级提供或由关联机制承接，要先定义清楚，再实施，不一刀切所有元素。
- 临时口径的来源、范围和再确认条件若实施结构检查，仅能证明记录存在，不能证明授权真实或业务正确。
- 不用关键词黑名单、固定引用重合阈值、图数或字数判断语义质量。

纯文档优化不新增复制提示词的单测。只有修改确定性行为时增加有意义的正反例测试；运行相关现有检查，失败后定位，不用无关全量测试制造完成感。

## 11. 用实际素材验证优化，而非只验格式

### 11.1 区分实施检查与效果验收

实施 Agent 必须完成改动范围、引用、格式、合同兼容和有改动代码的必要检查。用户可自行开展真实业务试用；不擅自启动正式 Run、操作真实产品或要求用户重新裁定已有业务。

若做离线效果试验，在仓库隔离目录生成副本，不覆盖历史产物。本文允许的仅是只读素材和隔离产物；以下效果验收可以由实施者在宿主能力内完成，受限则明确未完成，不阻止交付可审阅的代码与文档结果，但不能声称效果已验收。

### 11.2 固定对照和原始依据

固定当前待优化版本与候选版本、同一组原始资料、范围、有效裁定、工具权限和输出位置。使用与版本绑定的快照或哈希。旧提交版、其他未接受草稿可作额外参考，不把混合版本差异全部归功于本次改造。

选择既有真实素材覆盖简单业务和复杂依赖/异步业务，不为展示效果重造产品规则。优先回放真实出现过的依赖漏读、条件丢失、重复提问及受限观察问题。已知缺陷材料属于回归样本，另用未参与讨论的资料片段检查泛化，不能混称盲测。

原始素材可由独立审阅者提取核查要点；正确依据仍是有效资料和裁定，不是隐藏答案或审阅者个人偏好。对比未能公平执行时写清局限。

### 11.3 验收应观察的行为

- 是否主动找到会改变当前判断的历史依赖原文，并保留版本、限制和停止追踪理由。
- 是否能从报告解释主链、基础功能和关键概念，缺口不会被少数抽象标题遮住。
- 是否保留重要条件、例外、关系维护、变化/保持和失败后果；不以数字条款为唯一检查对象。
- 是否能查证已有答案，减少无效提问；真正问题能独立读懂并分别回答。
- 是否能发现无依据规则或跨处矛盾，并真实同步修订、复核保持项。
- 是否能在系统未开发时继续规则理解，清楚记录未来验证需要的事实。
- 下游读取同版本模型时，能否解释关键场景并定位规则，无需临场补预期。
- 隐藏内部编号后图文和问题是否仍可理解，是否减少无关跳转和重复解释。

记录具体命中、遗漏、误报、重复问题、返工和读取成本。复杂度不同的业务分开评价；合理共享同一事件或相同步骤不自动扣分。不得仅报告总覆盖率或通过率。

### 11.4 辨别试验与阅读反馈

有条件时在隔离候选副本中植入删除条件、误改关系、引用旧规则或修订遗漏等问题。原始资料保持不变，保留受审副本、独立发现、处置和最终差异，记录误报与漏报。生成者给出答案后再复述不能称为独立辨别。

独立代理检查与真实人员试读分开记录。让未参与生成者仅凭默认正文和单个问题解释流程及决定后果；未取得真实试读反馈时不冒称用户体验通过。

## 12. 实施顺序与最终交付

1. **检查基线**：读取当前目标、参考、合同和调用方，记录已有改动、版本和权限边界。确认阶段①为保留基线。
2. **逐环节实施**：先改阶段②及方法说明，再改③、④、⑤；相关呈现和来源规则同时局部对齐，避免多个文件冲突。发现资料缺口按需回查，不整套重写。
3. **检查衔接与兼容**：从来源到任务、机制、审查、回复和下游消费走读一个真实片段，检查版本、引用、未决和正式确认边界。需要新字段或脚本时按第8、9节处理。
4. **必要验证与独立复核**：完成相关确定性检查；取得独立实施复核时检查具体要求和差异，不只读作者总结。离线效果试验和用户后续真实测试分开报告，受限事项如实说明。
5. **交付可审阅结果**：给出修改文件及原因、阶段①保留情况、实际检查与试验结果、剩余问题、用户建议重点试用的场景及安装状态。不要提交 Git，也不把本文或检查项全部勾选当成验收。

安装同步只在用户明确授权后进行：指定唯一来源和目标，先比较文件差异，只同步授权内容并核对一致；不做无差别双向覆盖、不删除目标专有资产，不同步缓存。不将 Gemini 目录授权扩大到 Codex、其他 Agent 或真实业务项目。
