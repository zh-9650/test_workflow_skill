## 1. 这次究竟改什么

保留“业务理解 → 测试点设计 → 测试用例设计 → 执行方案”的既有分工。将测试点阶段组织成：接清依据与范围、盘点基础功能与正常路径、展开影响结果的条件、反查辨别能力、形成可供人工审查的交付物。

改造要解决的是：覆盖编号齐全但基础功能遗漏；预期只重复业务标题；条件不足以暴露所声称的错误；把未定规则或当前实现写成正确答案；报告充满缩写和宽表格，人工无法有效审查。

当前模块通常还在开发，没有当前模块源码、实际数据库结构或已实现接口是正常情况。测试点设计依据已确认的业务承诺开展，不以这些实现材料齐备为前提。

本方案不是增加一套“专家术语 + 台账 + 自审通过”的流程。实施者应把要求写成实际动作、完成条件和交接边界；具体方法按问题选用。

### 1.1 实施范围与权限

本轮用户要求的是完善方案文档。Gemini 接到实施指令后，才按本文修改仓库内对应 Skill。

实施仅限 test-point-design 中与本文直接相关的指令、参考资料和必要的局部合同兼容。先检查工作区与当前文件，以实施前实际内容为比较基线；已有未提交内容须区分，不以 Git HEAD 的全部差异代表本次改造。

不顺带重构业务理解、用例、Router 或执行阶段；不改真实业务项目，不提交 Git，不同步安装目录。需要超出上述范围时，先说明具体必要性与影响，交由用户决定。

## 2. 现有能力与不可丢失的内容

当前 SKILL.md 已经具备以下基础，不应以换流程为由删掉。实施前逐项定位；实施后逐项对照实际内容，不能只写“全部保留”。

| 现有内容 | 改造后如何保留 |
|---|---|
| 已确认业务理解、同版本模型和原始来源 | 继续作为输入；原始来源用于核对、定向补查，不擅改已确认规则 |
| 事件、状态迁移、关系生命周期、不变量、规则、失败事实与下游影响 | 逐项有覆盖、明确排除或未决去向；不能只消费能力清单标题 |
| 正常主链与真实使用结果 | 先盘点基础功能与主链，再展开专项；按有效需求区分各阶段完成 |
| 输入规则、权限、范围隔离、旧状态与并发 | 依据业务差异和风险检查；具体样本与执行编排留到后续 |
| 变化项、保持项、历史事实、失败一致性与恢复 | 保留各自判断要求；只分析实际定义或有依据推导的机制 |
| 原子机制与连续流程 | 连续流程不能替代中间机制；不为凑数机械拆分 |
| 来源状态与推导说明 | 继续使用现有 CONFIRMED、DERIVED、TEST_BASELINE 及对应约束 |
| 问题返回上游、人工确认、版本失效 | 继续使用现有流程；不增加第二份确认布尔值或放行捷径 |
| 正式报告、审查摘要与 JSON 同步 | 保持三份正式产物、现有版本和绑定方式 |
| 结构合同与下游消费 | 保留现有合法字段、引用关系和旧合法产物的兼容性 |

原有正文或示例如果与本方案冲突，修改冲突位置并说明原因。例如“代码能独立写错就一律拆分”需改为业务判断与风险驱动；不是删去独立机制覆盖要求。

## 3. 输入材料：开发前有什么，就怎样使用

### 3.1 开始条件

正式测试点设计接收：

- 已人工确认的 deliverables/01-business-understanding.md。
- 同版本 internal/business/business-model.json。
- 相关业务理解审查结果、有效裁定、范围限制、来源定位及已答问题。

沿用 Router 对确认和版本的管理。若尚未确认，可以在用户授权范围内整理候选和缺口，不能冒称正式测试点阶段已经放行。

读取上游实际字段与内容，不要求固定能力数、证明编号、不变量数、流程分支数。旧模型缺少可选扩展时，通过现有事件、规则、状态、关系、流程及来源取得必要事实；重要业务语义确实不足时再返回补充。

### 3.2 各种材料的用途

| 材料 | 用于什么 | 使用边界 |
|---|---|---|
| 当前需求、原型、有效评审与人工裁定 | 确定用户行为、业务规则、条件、结果与例外 | 核对版本、效力与范围；有效评审不能统统降为展示参考 |
| 已确认业务理解及模型 | 承接任务、机制、依赖和判断依据 | 不是机械逐条换标题；发现矛盾要标记并按影响返回 |
| 已有基础设施、公共能力和已完成模块资料或代码 | 查清当前功能依赖的权限、对象关系、公共规则、接口约定和风险 | 不全库通读，不把旧实现习惯自动扩成新需求 |
| 当前模块接口或技术设计 | 取得已确定的输入输出、状态和观察位置 | 可能尚不存在；未经确认的设计不冒充业务裁定 |
| 当前模块源码与运行证据 | 若已经可用，辅助发现实际路径、风险和观察办法 | 不作为必备输入；当前实现不自动等于正确预期 |
| 历史缺陷、复盘、旧用例 | 查找容易漏掉的条件、错误表现和判断依据 | 核对适用性与版本；已知缺陷后的补充不算提前发现能力 |

### 3.3 定向补查的方法

先提出具体查证问题，再选材料与工具。示例：“当前模块调用已有资源选择器，停用资源是否仍可能被旧页面提交？”据此查相关需求、已有接口约定和必要代码，带回适用条件、来源及未决限制。

全文检索用于定位；定位后读取相关段落、表格、图和上下文。历史缺陷要读取复现条件与实际结果，不能只看标题。文档、原型和代码工具按材料选择；本阶段不要求操作真实业务系统、调用写接口或改库造状态。

不重复把全部历史资料塞入上下文。复用上游已查清的事实与来源，只有缺口、冲突或机制辨别需要时再追查；读取范围不完整应如实交代。

## 4. 改造后的工作流程

~~~mermaid
flowchart TD
    A[接清已确认依据、范围与限制] --> B[盘点基础功能和正常业务路径]
    B --> C[展开影响结果的条件，形成测试点]
    C --> D[反查遗漏、错误辨别力与粒度]
    D --> E[独立复核，整理人工审查版本]
    E --> F[人工审查、修订与正式确认]
    C -.业务规则缺口.-> U[返回业务理解补充并处理版本影响]
    D -.发现业务理解矛盾.-> U
    U --> A
    F --> G[交给用例阶段展开具体执行场景]
~~~

五个工作环节是工作顺序，不是要求新增五份交付物。中间推导放现有内部数据和审查工作记录中，正式产物仍为三份。

### 环节一：接清依据和范围

输入：第 3 节材料。

工作：

1. 核对本轮版本、范围、角色、任务、依赖、有效来源和既有裁定。
2. 从能力索引展开到实际事件、规则、迁移、关系和流程，定位重要判断依据。
3. 区分已确认事实、可追溯推导、范围限制、业务未决及尚未落实的执行细节。
4. 对具体缺口定向补查；避免重复询问已有答案。

输出：本轮分析边界、适用事实、必要依赖和问题去向。

完成条件：可以解释“本轮测哪些业务、哪些不测、依据是什么”；重要矛盾或缺口没有混入确定预期。资料缺失按影响处理，不因没有当前模块源码而停止。

### 环节二：盘点基础功能和正常路径

输入：已确认任务、功能、对象与依赖。

工作：

1. 按用户实际目标串起入口、必要条件、主要动作、分流和结果。
2. 反查需求和原型中的查询、筛选、分页、详情、编辑、启停、删除、历史等基础活动，仅纳入实际存在且在本轮范围内的功能。
3. 将维护活动归入相关任务或单独列出，避免长旅程遮住基础功能。
4. 标明正常路径中各阶段的业务结果，以及结果何时允许被用户或下游使用。
5. 用必要的总览图与说明建立审查导航；没有外部依赖的简单功能不强造跨模块链。

输出：基础功能验收导航、正常业务路径骨架，以及各功能的后续设计去向。

完成条件：人工先看导航就能判断是否少了整块功能；每项重要功能有测试点设计去向或明确限制。导航不是第二套独立规则，也不重复整份业务理解。

### 环节三：展开条件并形成测试点

输入：功能与路径骨架、已确认规则和判断依据。

对各功能识别真正改变行为或结果的条件：

- 输入的有效与无效类别、结构、内容特征、数量或范围规则。
- 角色、权限、租户或其他业务作用域。
- 对象状态、引用关系、历史、时间与旧页面条件。
- 配置的保存、回显、执行采用、生效时机和存量影响。
- 异步各阶段、外部依赖成功或失败、部分成功与恢复。
- 必须变化的结果、必须保留的事实，以及实际下游影响。

这些是适用性视角，不是逐功能套一遍的分类生成器。先确认普通输入、合法条件与基础主链，再按实际风险深化。

每个测试点需清楚表达：

1. 在验证什么业务机制。
2. 什么关键条件下，触发什么动作或事件。
3. 什么实质结果说明该机制成立。
4. 哪些关系、历史或其他事实必须保持；适用时说明。
5. 需要观察什么事实、哪些表面现象单独不足以证明；按风险展开。
6. 依据来自哪里，是否存在限制。

用自然中文表达，不要求每条都变成六栏。决定条件、动作和预期不能省略；保持项、防假成功说明及内部观察只在有实际意义时展开。

正常与拒绝两面的条件需要有承接。例如验证组内重名限制时，既检查应拒绝的情况，也检查不会被错误扩大作用域而误拦截的允许情况。规则等价的多个样本留给用例展开。

输出：机制级测试点及覆盖去向。具体文件、账号、边界数值实例、点击顺序、轮询时间、注入方法和执行证据编排由后续阶段落实。

完成条件：下游无需重新发明业务规则，就能展开执行场景；测试点不是业务标题、覆盖标签或“结果正确”的改写。

#### 缺口如何分类和交接

| 缺口 | 本阶段处理 |
|---|---|
| 不知道业务应该怎样、来源冲突或重要规则缺失 | 定向查证；标记受影响项，返回业务理解，不凭实现或常识补成硬预期 |
| 业务结果已知，但当前模块接口或观察入口尚不存在 | 保留测试点，说明需要观察的事实与手段待落实，交给用例或执行方案；不标成业务已决问题 |
| 具体材料、账号、可构造数据或异常制造办法尚未明确 | 明确交给用例或执行方案，不能用泛化步骤冒充已可执行 |
| 当前条件已知不能验证 | 保留验证要求与限制，说明影响；不能悄悄排除或声称验证通过 |

不新增“观察手段待落实”等正式机器状态来绕过现有合同。先用现有说明和审查摘要承载。若缺口影响业务判断或本轮设计确认，则按真实影响进入现有问题机制。

### 环节四：反查辨别能力、覆盖与粒度

输入：候选测试点、有效来源、基础功能导航和相关历史风险。

先自查，再由实际独立上下文复核。自查不能冒充独立审查。

#### 4.1 对高风险点作具体错误挑战

记录“规则 → 可能错误 → 暴露条件 → 正确与错误结果的差别 → 对应测试点 → 剩余限制”。允许复用相关错误假设，不要求每点或每功能凑固定八类。

关键问题是：在该测试点的条件下，正确实现与假设错误实现，是否真的会表现不同？仅有错误类型标签与关联编号不算辨别依据。

这是设计推演，不是产品已存在缺陷，也不是实际变异代码已被测试杀死。低风险普通入口不必强造复杂错误假设。

#### 4.2 检查遗漏和错误遮蔽

- 从来源反查：重要功能、允许与拒绝条件、状态、关系、失败、历史和流程是否有去向。
- 从测试点反查：预期是否有有效依据，推导是否成立，是否混入旧规则或具体技术猜测。
- 检查实际用户输入、配置真实作用、异步状态、外部失败和最终消费等适用机制，避免复杂专项掩盖基础主链。
- 前置条件要能到达拟验证机制。例如非法输入被入口拒绝，不能因此声称验证了处理完成后的索引逻辑。
- 需要连续性覆盖时保留完整流程，但不能只靠一条长流程覆盖全部中间机制。

#### 4.3 拆分、归并与排除

是否可独立发生错误是拆分线索，应结合正确性目标、决定条件、结果归属及分别定位风险的价值判断，不按代码行或任意字段机械拆点。

不同业务机制或不同预期若合并后无法分别判断，就拆开；同一机制的等价输入和边界实例留给用例参数化。同一机制的多分支可以共同描述，但每种决定条件与结果必须可辨，不能合成一句总预期。

重要的关系保持、历史保全和下游影响不能因“附带结果”而消失；需要独立验证的继续保留独立承接。原子点跨多个覆盖项时，沿用现有 cohesion_rationale 说明聚合理由。

重要的排除、归并和未覆盖项在现有审查记录中说明：

- 已由其他测试点或明确共享验证承接：给出去向。
- 机制等价：说明等价依据及留给用例的差异。
- 范围外或不适用：给出有效范围或规则依据。
- 当前不可达或无法构造：给出证据、限制及残余风险。
- 暂无足够依据：登记未决，不能伪装为无需验证。

“网关应该拦截”“状态机声明禁止”“已有唯一索引”不能单独作为免测理由，它们本身可能就是待验证的承诺。界面按钮不存在，也不自动说明其他业务入口不可达。

不对所有未枚举组合逐项建立新台账；只记录影响覆盖判断的重要取舍。

#### 4.4 独立复核与修订

独立审查者先读取相同有效来源、已确认模型、范围和裁定，形成关注点，再读取候选测试点；原始依据包括新发现且适用的依赖材料，不只给生成者摘要。工具按宿主适配，不写死子代理工具名。

审查基础遗漏、无依据预期、条件辨别力、错误归并、范围排除、上下游衔接和阅读障碍。不要求重建一套形式完全相同的最小机制集合，也不以名称差集直接认定漏测。

每项重要发现记录来源、候选位置、问题、影响、处置及复核结果。生成者修订后，复核实际变化及受影响共享规则，检查原有正确事实没有丢失。覆盖调整同步正文、审查摘要和 JSON。

无法获得独立上下文时，可继续自查并整理候选，明确“独立复核未完成”，不能称已独立通过。不要借此改 Router、伪造通过或设立新降级通道；本次改造的最终验收需取得独立实施复核记录。

### 环节五：交付人工审查、修订与确认

输入：已经自查及实际独立复核的候选，以及尚待决定的事项和限制。

先让人能看懂，再让人作决定。人工负责审查业务正确性、完整性、范围和风险取舍，不负责替 Agent 逐条补条件与预期。

人工阅读顺序：

~~~text
本轮范围与基础功能导航
        ↓
业务路径图及关键分流讲解
        ↓
按功能分组的测试点
        ↓
重点风险、未覆盖限制与待确认问题
        ↓
人工反馈 → 按影响修订和复核 → 正式确认
~~~

收到回复后区分正式业务裁定、事实纠错、临时口径、范围调整和单纯确认。涉及业务语义变化时返回上游同步，再评估测试点与后续产物的版本影响；不是只改问答状态。非业务语义的设计调整在本阶段同步处理。

人工确认仍由既有流程绑定正式产物与版本。问题回复不等于最终确认，AI 复核不等于人工确认，人工确认也不代表产品已经执行通过。已确认内容变更后沿用重审、重新确认及下游失效机制。

正式进入用例阶段前，业务模型与测试点版本一致，必要自查与复核已完成，尚待回复的设计问题和待确认覆盖项已处理，影响预期的上游缺口已经按有效流程解决，三份产物同步并通过适用结构检查，最后取得人工确认。没有待确认问题时明确说明，仍需人工审查和正式确认，不自动跳过。

## 5. 人工交付物：明确阅读要求

### 5.1 保留三份正式产物

- deliverables/02-test-points.md：人工审查主报告。
- deliverables/02-test-point-review.md：审查发现、修正、覆盖取舍和限制。
- internal/design/test-points.json：结构关联和下游消费。

主报告负责让人理解与判断，JSON 负责追踪。不要把 JSON 字段逐项翻译成巨大表格。

### 5.2 主报告的组织

主报告先说明范围与版本，提供基础功能验收导航，再沿业务任务解释测试点。导航项能定位到相关分组；看起来有功能标题却没有实质测试点不算覆盖。

复杂业务提供总览图，并针对实际难点补充状态图、时序图、关系图或分支图，配紧邻文字说明条件、转折、结果和验证重点。简单活动简短讲清即可；不固定图数、不要求每点一图，也不把图源码当成已渲染图。

测试点使用中文业务标题。普通点可用简短段落或紧凑列表；便于比较的一组才用表格，不以单张八列宽表承载全文。允许保留短引用标识用于反馈，但标题、正文和问题不能依赖缩写编号才能理解。

重要条件、预期、未知和影响默认可见。来源给出资料名、章节或相关摘要，附可访问位置；长映射和内部编号放内部数据或按需展开区。不能让人为了理解一条测试点反复跳文件。

按业务分组展示优先级及其理由，避免所有项目一律最高优先级；理由可以在同类风险层共享，不为每条重复长段落。

### 5.3 审查摘要的组织

保留原有数量、模块、机制覆盖及进入下一阶段建议，但将实际发现、修正理由、重要排除、未决与人工重点放在前面。状态、关系、失败、恢复、并发、跨模块及基础目标的覆盖去向仍需可查。

报告应区分：已确认规则、合理推导、待澄清、观察手段待落实、仅设计推演和实际执行证据。本阶段没有运行产品的内容不能写为 PASS、已复现或已验证。

不要把正文重复成另一份长表，也不把自动统计当成实质审查结论。

### 5.4 待确认问题

主报告末尾集中呈现本轮可回答的事项；审查摘要只作关联，不把问题移到用户不易发现的位置。

提问前查相关来源、上游已答问题与有效裁定。每题自然讲清场景、已知事实、尚缺内容、不同答案的后果和现在要决定什么。来源用资料名与相关内容，不只写来源编号。

问题包括范围、优先级、粒度、额外流程覆盖及上游业务缺口；业务规则问题仍返回业务理解。仅尚未确定具体接口入口，不应要求用户重新裁定已知业务预期。

已知可行方案才给选项；空间不清时开放询问。有充分依据才推荐，没有依据就说明暂不推荐，不强迫二选一，不将未确认能力捆绑进选项。

### 5.5 图解与 HTML

用户要求 HTML 或图解阅读时，提供同版本阅读界面，并链接正式报告；默认内容仍按第 5.2 节组织，不能把 JSON 表格搬进网页。

图需实际可见，检查文字、连线、长文本、窄屏、目录锚点和展开行为。核心事实及问题不藏在折叠区。无法完成实际渲染检查时记录未验证；工具通过不等于真实人员读懂。HTML 不替代三份正式产物或单独形成确认规则。

## 6. 与上下游和现有合同的衔接

### 6.1 输入映射与既有字段

按当前业务模型实际结构消费。能力索引用于导航，需展开到实际事件、规则、不变量、流程或迁移。当前 test_point_contract.py 的 model_refs() 不识别能力索引 ID，不能直接把它们填进 source_model_refs。

覆盖项继续使用 coverage_obligations[].source_model_refs；测试点继续用 source_coverage_ids、primary_coverage_id、business_object_ids、business_event_ids 等已有引用。覆盖类型、状态和来源状态沿用现有枚举。

保留现有双向关联要求：覆盖项指向实际承接测试点，测试点反向指回相同覆盖项；主覆盖项须属于本点的来源覆盖项且已覆盖。连续流程的主覆盖类型与原子点聚合约束继续按现有合同执行。DERIVED 仍需 derived_from，presentation_sync 与现有自审结构也不省略。字段含义或形式不因阅读界面调整而改变，不为本次文案重排擅自升级 schema_version。

上游证明依据可能位于不同字段或正文，不能假设存在独立且固定编号的证明账本；也不混用能力级与事件级证明字段的名称。不同位置的自动校验程度以代码实际能力为准。

测试点的关键条件可使用现有 preconditions，业务动作及目标使用 mechanism，实质预期使用 core_expected，变化、保持、下游及来源使用现有字段。避免正文、扩展字段与既有字段各维护一套冲突规则。

### 6.2 观察要求不是提前写执行脚本

本阶段明确“需要观察什么事实、哪些证据单独不够”。已确认的接口或内部观察位置可以引用，但非通用必填。

具体 URL、状态码、表名、SQL、定位器、文件哈希、账号、轮询时限及异常注入方式，只有已有有效依据时才写；其余由用例与执行方案落实。不能为了显得可执行而编造，也不能要求所有机制都查数据库或底层引擎。

配置传递、策略采用与业务效果可能分别出错；按已确认语义承接，并为后续提供可区分条件。配置切换是否一定产生不同输出由具体数据和策略决定，不能统一规定“输出相同就是假开关”。

### 6.3 最小合同调整

默认不新增 decisive_condition、superficial_trap、observability_contract、pruning_ledger 等必填协议；先用既有字段和审查记录表达。需要可选扩展时，说明现有位置为何不足、谁消费、如何同步及兼容，不能只让脚本接受而下游无人使用。

本方案已发现一处需要处理的确定冲突：当前 validate_question() 要求待答选择题必须有推荐选项、开放题必须有推荐答案，与“没有依据可以暂不推荐”不一致。

允许在 test_point_contract.py 对这一处做局部向后兼容扩展，参考上游已有语义：

- 缺省 recommendation_status 仍按 recommended 处理，旧合法问题行为不变。
- 显式 not_recommended 时保留 recommendation_reason，用于解释为何无法推荐。
- 此时不提供推荐选项或推荐答案；选择题仍有实际可行且有影响说明的选项，开放题仍有完整问题和影响。
- 保留现有问题类型、来源核对、回复、状态和业务缺口返回约束；不因未推荐而解除阻断。
- 显式 not_recommended 却同时填写推荐，或使用非法状态，应被明确拒绝；是否确实缺乏推荐依据仍由内容审查判断，脚本不作此语义承诺。

增加针对旧行为、新选择题、新开放题及非法组合的必要测试。只处理这项已确认的格式能力冲突，不扩展为语义打分器、关键词黑名单或新的确认机制。实施前重读当前代码，若冲突已解决则不重复修改。

其余脚本继续负责确定性结构、类型、ID、引用、版本及状态，不声称能证明条件充分、独立审查真实发生或业务完整覆盖。

## 7. 给实施者的校准示例

以下是假设规则的教学示例，不是仓颉项目已经确认的需求或实际执行结果。实施者不能把示例接口、规则或结果直接带入业务模型。

### 7.1 名称唯一性：条件必须能区分错误

假设已确认规则：“同一分组内名称唯一，不同分组允许同名”。

合格测试点可描述“名称唯一性按目标分组判断”，并分别承接：

- 目标分组已有同名对象：拒绝创建。
- 目标分组没有同名对象，但其他分组存在同名对象：允许创建。

若假设错误是“按整个租户判重”，第二个条件才能暴露它。只有第一个条件时，正确与错误实现都会拒绝，不能声称已识别作用域错误。

具体分组、名称、账号及创建步骤留到用例阶段。是否需要额外独立验证失败保全，由已确认影响和风险判断，不能用这一点笼统宣称所有关系保持都已验证。

### 7.2 文档处理：区分已知预期与尚无实现

假设规则已明确：“底层仍排队或索引中时，不得展示正式可用”。

测试点写明条件、待验证动作或状态更新事件、实际处理阶段与展示状态应一致，以及上传受理成功单独不足以证明可用。具体状态查询接口尚未实现时，注明观察入口待落实，不编造 URL 或状态码。

如果只知道支持 PDF，不知道是否承诺无文字层扫描件的处理能力，应查相关来源与依赖能力；仍无依据时登记业务问题。不能自行规定默认 OCR 成功、切片至少两个、空结果一律缺陷。

假设错误为“重复提交产生两个任务”，只验证返回一个有效任务编号不够；需明确重复提交条件下按已确认规则判断任务数量或效果。幂等语义未定时先查证，不先规定所有重复请求都必须只产生一个任务。

### 7.3 失败与恢复：验证业务承诺，不指定实现

假设规则仅要求“失败产物不能被正式消费”。测试点应验证这一隔离结果，不擅自要求所有中间数据物理删除；隔离、保留诊断材料或后续恢复可有不同实现。

是否允许重试、重试是否继承进度、允许多大同步延迟，以及如何处理历史，都按有效规则确定。缺少规则不能自行规定锁、回滚算法、固定超时或断点续传。

## 9. 怎样验收改造没有退步

分开检查“实施是否符合本方案”“生成是否有改进”“产品是否正确”。前两项也不能互相替代。

### 9.1 固定比较基线

实施前固定当前 Skill、参考、合同和有关合法样本的快照或哈希，记录未提交内容。候选与当前版本使用相同已确认业务理解、范围、裁定、工具权限和材料可得性。

不能把其他草稿或早期 Git 提交与当前混合版本的全部差异算成本次收益。测试点对照只替换测试点 Skill，不顺带重跑并改写业务理解，使比较失去依据。

### 9.2 实施与兼容性检查

- 按第 2 节逐项核对原有机制、正式产物、来源约束和确认流程。
- 核对五环节的输入、工作、输出、完成条件及引用入口是否实际写入并无冲突。
- 运行相关格式、引用和必要合同检查；对局部脚本修改运行第 6.3 节测试。
- 用既有合法业务模型和测试点样本检查引用与旧行为兼容，并验证下游读取仍成立。
- 独立上下文对照本文、改造前快照和候选实际文件，查能力丢失、越界和阅读负担；记录实际发现及修订复核。
- 结构检查和单测只能支持对应确定性结论，不能标记业务效果通过。

### 9.3 离线生成效果对照

优先复用已有真实业务理解产物与相关原始材料，在隔离输出目录比较旧版与候选。覆盖的验证情境应包含基础操作、条件分流、依赖和历史风险；没有当前模块源码的情境必须纳入，不能只挑材料齐全的成熟系统。

按适用性选择有代表性的简单功能与复杂机制，不规定固定数量，不为测试改造而另造产品需求。真实材料不足时记录缺口，不用合成样例冒充真实业务验收。

比较实际内容：

1. 基础功能与正常链是否遗漏或被专项淹没。
2. 实际输入特征、允许与拒绝条件、状态、关系、配置和依赖失败是否准确承接。
3. 是否增加了无来源的能力、状态码、完成条件或技术方案。
4. 高风险错误假设能否被所列条件与预期区分；是否出现自我关联就算命中的情况。
5. 粒度、重复、重要排除和剩余限制是否合理，原有正确点有没有丢失。
6. 下游能否基于同版本测试点生成代表执行场景，无需补造决定条件或业务预期；具体数据与工具选择仍可在下游完成。
7. 人工阅读是否减少编号依赖、无关跳转和重复解释，问题能否独立回答。

保存输入版本、两个版本的完整产物、发现、处置和差异。不按测试点数量、字数、自审 true、覆盖编号数或图数评优。

### 9.4 历史缺陷和错误辨别试验

将历史缺陷分成用于设计的已知风险与保留用于验收的未公开样本，分别说明。缺陷答案已经给生成者后再补写，不算盲测召回。

在隔离副本中，可以植入漏条件、错误作用域、状态提前成功或错误归并等问题，检查复核者是否实际指出。保留受审副本、原始依据、独立发现、误报与漏报及最终差异。

仅判断假设是否可辨时，报告“设计推演”；只有实际修改并运行可执行变异试验，才报告对应实际检出结果。没有独立样本、定义和执行证据时，不使用 100% 召回、95% 击杀或低于 2% 歧义等门禁。

### 9.5 人工阅读与最终确认

让未参与生成的人只看默认正文，尝试指出本轮范围、关键条件、预期与限制，并独立回答一个待确认问题。隐藏内部编号后仍应能理解；图需要文字解释，宽表不能造成关键内容难以阅读。

真实人员反馈与代理阅读审查分开记录。尚未取得人员反馈时写未验证，不自评“用户体验通过”。人工仍须审查正式业务产物，不能被这次方案审查或独立代理检查替代。

如果用户选择自行试用，实施者如实交付已完成的实施检查与未完成的效果项目，不擅自启动真实系统测试，不把未执行项目填为通过。

### 9.6 收口标准

已知会造成规则虚构、基础功能遗漏、原有机制丢失、确认绕过或报告不可独立理解的问题，需要修正并复核；不能用统计改善抵消。

最终说明分别列出：改动范围、基线、实际检查、已发现并修正的问题、尚未验证项及需人工决定的事项。没有完成公平对照或真实试读时，不宣称整体效果已经优于旧版。
