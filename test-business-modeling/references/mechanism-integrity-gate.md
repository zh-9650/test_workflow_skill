# 业务机制承接、防退化与语义验收门禁（3.1）

本指南在**原业务发现—澄清—建模—审查的五环节之内执行**；不创建新的 Agent、额外 Run、产品测试阶段或单独人工确认状态。问题不是“模型有多少事件”，而是**同一个有效业务要求能否在模型中找到条件、结果和隔离边界，并被下一位测试设计者独立辨认**。

## A. 来源到行为的双向追溯（环节①、③、④）

1. 从 PRD/原型（含弹窗、隐藏页、事件绑定、交互图）、评审生效修改、明确裁定中识别**每一项可以独立成立/违反的有效承诺**。不要只提取章节标题或复制段落；每项记录完整的触发场景、主体、条件/例外、合法结果、禁止结果、后续影响。允许多个来源对应同一机制，但每项承诺不能只挂一个来源 ID 就声称已覆盖。
2. 在既有 `01-business-understanding-review.md` 的来源承接表（或此前已建立的证据附录）逐条登记：`来源定位｜原始承诺（含决定条件）｜效力与范围｜承接机制ID及具体行为｜不适用/替代理由｜仍需确认内容`。与用户沟通时显示中文行为与来源位置。对于原始编号清晰的资料逐编号展开核对；允许将连续编号在展示中分组，但不得丢失成员编号、条件或例外。来源本身若不可达，列读取限制，不能记为已审阅。
3. 从每一条模型机制反向找到有效来源；从来源记录反向读回具体行为。**两方向均成立**才记为承接，引用数量和表格行数不是完成证明。
4. 新需求仅替换被明确修改的旧事实。旧模型只用作“退化反查线索”，不自动获得更高效力；旧模型多出的上游 CRUD 若不属于当前交付，不得机械恢复。

## B. 逐事件六问与显式关联（环节③）

每个业务事件都必须回答六问：**谁与目标对象、决定条件、成功后的真实变化、必须保持、失败最终事实、下游准入或禁止**。若某问对只读、纯展示场景确实不适用，写“为什么不适用”的业务解释，不要虚构持久化、审计、接口或回滚。

对于每个事件，先检查其**实际状态机、关系生命周期及作用范围**，再写 `state_changes` / `relationship_changes`。`mechanism_links` 是结构化审查的定位信息，不代替具体业务说明。

| `impact` | 含义 | 必填证据 | 边界 |
|---|---|---|---|
| `change` | 事件实际改变状态或关系 | 对应 `SM/TR/REL` ID + 描述何时、如何变化 | 状态迁移优先关联具体 `TR`；创建进入初态如无 `TR`，写 `transition_not_applicable_reason` |
| `read_or_guard` | 读取、校验、阻断但不改变状态或关系 | 对应 `SM/TR/REL` ID + 描述被读取/校验的事实 | 不能误写成建立关系或修改状态 |
| `not_applicable` | 事件确实不涉及该维度 | 具体 `rationale`；空 `refs`、空变化数组 | 不要写“已检查”却没有判断理由 |
| `pending` | 资料不足以确定该维度 | `question_ids` 指向未决问题，写明不同裁定的影响 | 不得把未知按成功、失败或不适用任意定论 |

简化示意（独立字段适用性；不是具体项目业务规则）：

```json
{
  "event_id": "EV-001",
  "state_changes": ["TR-001：满足条件后状态 S1 变为 S2"],
  "relationship_changes": [],
  "mechanism_links": {
    "state": {"impact":"change","refs":["TR-001"],"rationale":"合法完成后 S1→S2"},
    "relationship": {"impact":"not_applicable","refs":[],"rationale":"本操作不创建、读取或改变跨对象关系"}
  }
}
```

- 对仅校验既有绑定的事件，用 `relationship: read_or_guard`、`refs:["REL-001"]`，`relationship_changes` 中描述“只核对当前有效绑定，拒绝后不建立新的绑定”。
- 状态 `change` 并非自动等于“持久化”：按照来源说明是当次内存状态、业务结果状态还是存储事实。
- 对每一条状态机迁移、关系，确认其至少被某个事件承接。若确为上层背景而未由本期事件直接改变/校验，放入模型顶层 `mechanism_link_exceptions`，注明机制 ID、业务性例外理由和有效来源 ID，绝不能用空数组放行。
- 同一事件可以承接多个分支；如果两个分支条件/结果/保持项/后续准入无法被人分别还原，必须拆分分支描述或事件，不靠增加事件数量作为目标。

## C. 并存事实与时间隔离（环节③）

**只有业务中实际存在配置/授权/异步/版本/撤销/重试机制时适用。** 对每个适用组合按以下五问核对：

1. 在同一时刻可同时存在的业务对象/事实有哪些（候选草稿与已发布版本、当前与历史快照、前次与本次请求、首轮与重试轮）？
2. 各对象的稳定身份与事实来源是什么？一个版本切换会不会错误覆盖另一个事实？
3. 哪个动作导致哪个版本**实际被消费**，生效时点、旧任务与新任务的归属是否明确？界面回显只能证明它展示了什么，不足以替代实际消费事实。
4. 发生失败/撤销/晚到/权限收回/并发时，什么必须保留、禁止污染哪些对象或报告？
5. 哪些事实来自需求，哪些尚未确定？不能从“应隔离”推断底层必须采用某种锁、事务或队列。

可用轻量时序表：`时点｜候选状态｜有效状态｜当前请求快照｜执行尝试｜允许改变｜禁止改变｜来源/待确认`；没有复杂并存语义时写“不适用＋证据”，不造图。

## D. 版本回归：保持机制、不照搬旧模型（环节④）

新版替换旧版时，在审查摘要或原有证据附件保留语义回归表：`旧机制/行为｜旧版证据｜最新有效来源裁定｜新版具体承接位置｜处理（保持/等价改写/正式排除/待确认/缺失）｜判别性复核`。

- “保持”：机制条件、变化、保持、不利结果和下游准入未弱化。
- “等价改写”：可换对象/事件组织方式，但提供一个具体反例说明为什么新版仍能辨别错误结果。
- “正式排除”：仅以新生效范围/人工裁定排除，不因旧模型复杂而照搬，也不因新模型较短而删除。
- “待确认”：列真实未决问题、影响范围及当前不能给出的预期；不把待确认写成“已覆盖”。
- “缺失”：要么回退环节③补齐，要么按事实登记阻断；不得写“后续测试点再补”。

**例子**：上层权限管理的 CRUD 可能属于依赖范围，不应变成本期直接功能；但权限失效是否禁止下一次本期调用属于影响当前判断的真实依赖，需要有承接或明确未决。

## E. 失效挑战、修订同步与独立复核（环节④⑤）

1. Reviewer 首轮**只看生效原文**独立形成义务/风险列表，再看模型。检查基本活动、分支/条件、状态与关系、异步/失败保持、并存隔离、真实消费与证明边界；对选定机制提出至少一个有事实依据的表面正确但业务错误的反例。没有真实独立上下文就标“未完成”，不要假装多角色评审。
2. 使用第 A/B/C/D 表反向复核：每一项发现有具体来源、影响和修复去向。仅运行 Contract 或同一 Agent 自评不足以通过。
3. 人工裁定/版本变更后，以该决定为起点遍历来源表、规则、事件、状态/关系、流程、图、问题、正文和审查摘要；必须同步，避免报告说“已决”而模型还写“待修订”。
4. 记录哪些原文无法访问、哪些模型未能完整建立、哪些方面只抽查过；不得把抽查说成全量核对。
5. 下游可用性验证：由未参与建模的人只看候选模型及当前证据回答“什么时候合法、什么时候禁止、成功后什么可用、失败后什么不变、凭什么判断”；回答需补猜则修模型。

### 3.1 门禁的职责分工

- `business_contract.py` 能核实 `mechanism_links` 的**字段、ID 类型、各维度一致性和未承接机制登记**；也能识别旧 3.0 模型不能直接当作新的正式成果。
- 它不能验证引用是否真正对应业务，不能从原始 PRD 自行证明每一条已被正确读取，不能识别编造的例外原因、过期裁定或假冒的独立 Reviewer。
- 3.0 数据仅用 `--allow-legacy-schema` **检查旧结构**，返回 `ready_for_confirmation=false`；不得把旧模型的检查绿灯当成本次改造的语义验收。
- 用 `--allow-waiting-confirmation` 允许业务待确认，**并不允许**绕过 3.1 机制关联。

### 交接闸门（与原有 Router 并用）

1. 有效来源与交互核对完成，或明确标出不可达/待确认影响。
2. 事件六问与状态关系机制关联已填、命名引用校验通过；并存事实有结论或未决。
3. 新旧版本语义回归（若存在）已核对，旧版没有无解释地静默消失。
4. 实际独立 Reviewer 审阅并对修订作复核；三份正式产物及其图/问题同步。
5. 业务阻断项解除、结构门禁正式通过，且由既有 Router 获得人工确认。没有真实完成就保留候选状态。
