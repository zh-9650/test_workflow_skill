# 业务链路推演与交叉变化：从一段功能描述走到全部有效终态

> 目的不是增加流程图或制造异常数量，而是在变化条件下推导**不同的业务后果**，发现功能间没有被需求文本直接串起来的依赖。

## 1. 以用户任务和业务事实为骨架

对每条主要用户任务画最短可解释链：入口与身份 → 允许条件 → 输入/对象 → 决策 → 中间可见结果 → 对外生效或消费 → 成功终态/失败终态 → 后续入口。每个节点检查：

- 开始前哪些事实存在；身份/租户/范围/数据版本/当前状态是什么；
- 操作真正改变什么，不应改变什么（同租户其他对象、进行中的旧任务、历史快照等）；
- 是开始处理、后台处理完成、已经对用户可用，还是只是页面提示成功；
- 成功如何证明；什么看似成功的现象不能证明业务成功；
- 失败、中断、重复、撤销后留下什么；下一次合法操作是什么；
- 与哪条当前有效子句对应，未知者具体记录疑问，不自行设定默认处理。

简单无状态查询可写成精简链，并标记“经核对无变更”。高风险链需要展示每一个会导致**不同最终业务结果**的分流。不要每个按钮都强制做并发排列组合。

## 2. 四种条件变化（逐链路按相关性使用）

1. **输入变化**：合法/非法、空/边界、不同含义、文件/格式/结构；不要只按后缀划分，必要时看真实有效内容与来源。
2. **状态变化**：创建/修改/发布/停用/删除/恢复，先前结果与当前结果不同；当前、历史、在途事实可能同时成立。
3. **时间与顺序变化**：先发布后提问 vs 在途发布；先取消后响应 vs 响应后取消；首次失败与最后允许一次重试失败；上游撤权/配置变更与下游运行交叉。只推演真实存在的依赖，不无限排列。
4. **上游影响变化**：共享对象变更、租户或权限调整、有效配置变更、外部处理排队/失败/退化是否让当前功能产生不同结果。未定义的技术动作不是当然的产品承诺。

对每个决定性的切换点写：旧事实 → 触发/条件 → 新事实 → 必须保留的旧事实 → 下游变化 → 业务终态。两种条件结果相同必须说明为什么；结果不同必须说明依据是什么。

## 3. 防止多维状态被一条线性状态机覆盖

若业务中同时存在“草稿版本、当前生效版本、运行中的请求快照”，必须明确它们是**三个可并存事实**；不要用“已发布→编辑中→已发布”作为完整事实模型。需要保留对各个对象的归属、适用时间、读取规则和是否能反向影响已经开始的处理。

重复/自动重试要明确“第几次尝试、允许最大次数、当前尝试与新用户请求是否同一业务任务、最后一次失败进入哪个终态”。如果次数由材料没有规定，仅留出适用的未决边界，不从模板强制推定重试。

停止/重新提交要分别解释：旧请求是否仍可能晚到、晚到结果是否有效、它与新请求的结果是否隔离；这些关系应有明确业务预期或待确认。不能用“停止”一词自动替代取消底层计算的技术保证。

## 4. 证明链路已经深入而不是堆字数

在 `evidence/effect-ledger.json` 的 `critical_paths` 为关键链路记录 `task`、`steps`、`terminal_outcome`、`clause_refs`。一个 `step` 至少明确 `event_ref`、`when`、`then`、`must_hold`。风险高的链路还需 `interruptions`（终止/失败/恢复实际业务结果）和 `interleavings`（交叉变化/并存事实，或者附理由说明确实不适用）。

使用 `discriminators` 保存少量真正能区分错误行为的正反条件：`outcome_a`、`outcome_b`、`oracle`（充分与不充分证据）、`clause_refs`、`confidence`（`confirmed` 或 `needs_decision`）。没有可证正确结果时不要伪造“正确值”，标记 `needs_decision` 并关联 `unknown_refs`。

脚本可以检查引用完整和缺字段，**无法判断文字对应的法规、产品规则是否正确**。需审查者逆向比对原始需求。禁止用 AI 自己生成的反例当作独立金标准。

## 5. 持续收敛而不机械凑覆盖

- 高风险优先：不能恢复的业务结果、权限/租户隔离、配置/版本生效、异步在途、长任务分支、来源真实消费、历史缺陷对应机制。
- 每轮只扩展发现新终态、新保持事实、真实依赖或未决问题的切换点；单纯措辞变化、重复排列不产生新机制时停止。
- 任何新增业务结果都回查有效来源；任何局部修订都检查与其共享同一有效事实的其它事件、关系、报表、提示词/配置、图和待确认项。回归不等于恢复已取消功能。
