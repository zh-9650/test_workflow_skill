# 业务事实来源状态与效力判断

业务理解中的每一条规则、状态跃迁、关系、事件与不变量，必须标记其来源性质，确保所有业务事实“可信、可追溯、知边界”。

---

## 1. 资料发现与多形态读取方法（环节一动作规约）

业务理解不是被动接收格式化文本，必须主动根据输入证据的形态采用针对性发现方法，并在进入模型构建前建立清晰的证据基线：

### 1.1 资料形态适配与提取方法
- **文本类（PRD、需求规格说明书、评审纪要）**：
  - 提取关键业务实体、状态定义、正向/逆向业务规则、前置校验与跨模块约束；
  - 提取表格与流程图中的分支逻辑，定位到具体章节或页码，避免仅作章节粗览。
- **静态设计稿与交互图（UI/交互稿、原型截图）**：
  - 提取界面可见输入框特征、按钮动作、只读与编辑态差异、列表筛选条件；
  - 重点核对**未展开区域与隐藏交互**：抽屉、模态弹窗、多标签页、悬浮提示及空数据状态。
- **可运行原型与环境观察**：
  - **安全边界核验**：动态探索前必须先查明该原型是否连接真实后台或生产数据库；若无法确认，严禁触发写操作或提交真实凭据，退回静态分析并声明限制；
  - **静态线索与动态路径双向核对**：沿 PRD 线索核对原型是否具备对应流转路径；沿原型交互核对 PRD 是否有明确业务规则支持；
  - **状态探索与重放**：探索不同模式（如新建 vs 编辑、空态 vs 满态、不同角色权限视图），记录到达条件与可重放路径；
  - **不可达项与资源收口**：若部分交互因环境受限无法访问，明确记录不可达原因、业务影响及待探索队列，不得因停止探索而假定该功能不存在。

### 1.2 证据性质、效力与冲突仲裁
- **资料年代与规则效力分开判断**：旧模块仍有效的正式需求，不能仅因形成较早就降为无关参考。
- **新旧资料关系判定**：
  1. 新需求明确替代旧规则；
  2. 旧规则仍适用，新需求没有重复描述（必须继承）；
  3. 两份资料确实存在冲突（列入待裁定）；
  4. 当前证据不足，尚不能判断（列入待查证）。
- **仲裁基准**：
```text
当前人工明确确认 / 业务裁定纪要
> 正式生效的需求规约（本轮直接需求 + 上游模块仍有效的正式业务需求）
> 交互原型与未确认评审意见（设计参考或查证线索，不能自行覆盖有效业务规则）
> 技术方案 / 接口文档 / 数据库 DDL（物理契约参考）
> 历史废弃草稿与旧版本残留代码（仅供线索，不具效力）
```
- **评审材料按效力归类**：经有权限人员或有效渠道确认生效的业务变更，按其性质归入有效业务裁定或正式需求变更。保留确认依据、适用范围、版本，以及被替代或补充的旧规则；需求正文尚未更新不构成忽略该变更的理由。尚未确认的建议、讨论稿和演示只作线索；确认依据不明时继续查证，不能自行宣布生效。不能仅按“评审记录”的文件名称决定优先级。
- 文件更新时间较晚、原型演示占位符或当前代码行为，**均不能自动覆盖有效业务规则**；
- 遇到不可调和的重大业务冲突时，保留冲突原文并提炼为待确认问题，**严禁 AI 擅自以“最新原型为准”掩盖分歧**。

## 2. 四类业务依据状态

现有合同接受的标记包含以下四种业务依据状态，以及仅用于内部表示的 PENDING；未定业务事实应进入问题集合，不以 PENDING 登记为已接受事实：

```text
CONFIRMED
DERIVED
TEST_BASELINE
IMPLEMENTATION_DETAIL
```

1. **`CONFIRMED`（正式确认）**：
   - 原始需求资料（PRD/需求规格/用户正式确认记录）有明确字面记载，或者经由授权业务人员/用户正式裁定确认。
   - `source_refs` 必须精确指向对应来源 ID（如 `["SRC-001"]`）。
   - **约束**：严禁把常识、经验或其它旧项目的假设填入 `CONFIRMED`。

2. **`DERIVED`（逻辑推导）**：
   - 基于已知确定规则推导出的必然业务闭环。
   - **强制要求**：必须填写 `derived_from` 列表，说明是由哪些已知事实/规则 ID（如 `["RULE-001"]`）稳定推导而来。
   - 推导前提若存在待决或冲突，不能作为确定推导登记。

3. **`TEST_BASELINE`（临时测试基准口径）**：
   - 需求或资料暂未明确定界，但经过用户明确允许采纳的临时口径，用于解阻下游继续推进测试设计。
   - 必须注明适用范围和后续再确认触发条件，不能直接替代正式需求。正式规则变更后必须触发下游影响分析。

4. **`IMPLEMENTATION_DETAIL`（实现现状与技术细节）**：
   - 不改变业务 Expected、不改变业务状态与流程的底层实现细节。
   - **典型内容**：内部错误码枚举、事务实现机制、日志与监控存储路径、异步技术队列实现、UI 具体文案排版等。
   - 按内容判断而非技术词汇判断：若有效资料承诺某种调用模式、协议输出、界面不展示、计数口径或提示时机，它就是待保留的要求。上述典型内容一旦影响已承诺的可见行为、数据边界或验收结果，也不能仅以“技术/UI细节”后置或排除。
   - **注意**：
     - 技术实现现状（Swagger、源码逻辑、当前环境返回）不能自动等同于正确的业务预期。
     - **契约约束**：现有合同对 events、relationships、state transitions、cross_module_flows 强制禁止标记为 `IMPLEMENTATION_DETAIL`（必须归入 CONFIRMED/DERIVED/TEST_BASELINE）。若观察到实现现状与 PRD 存在业务分歧，必须在 `unknowns` 登记为待确认问题（issue_type 为 source_conflict 或 implementation），而不能将业务事件直接标记为 IMPLEMENTATION_DETAIL。

## 3. 未定事实、查证与待确认问题

真正未确定、且不同答案会改变业务 Expected、流程、状态、关系或范围的内容：
- **严禁**直接作为已确认业务事实写入模型；
- 必须记录在 `unknowns` 集合中（并在主报告文末以集中澄清形式呈现）；
- 标记受影响的 `affected_scopes`，在人工确认前阻断对应范围的正式交付。

提问规范：
- 面向人的表达按 `human-readable-reporting.md`：先交代具体场景和已知内容，再说明缺口与不同答案的后果。来源显示文档名称、章节及相关短摘录或忠实摘要，内部来源编号留在追踪记录；问题主体应能独立读懂。
- 业务类问题必须先查资料再提问，`evidence_checked` 不能为空；
- 查证覆盖相关有效原文、依赖材料和已有回复，考虑别名、图表及版本。搜索未命中不等于资料沉默；资料受限、纯实现选择、待试验事项与产品规则未定分别记录，不能一律请求用户裁定；
- 来源冲突（`source_conflict`）必须至少比较两份证据并指出具体冲突章节；
- 选项应包含实际可行且有业务差异的方案，不搞诱导式提问；
- 允许在依据不足时设置 `recommendation_status: "not_recommended"` 并说明实质理由；
- **人工回复后的同步闭环**：先区分正式裁定、获准临时口径、纠错线索与阶段确认。经查证确需修订的纠错、获准口径、正式裁定和范围调整，都按实际影响同步正文、图、结构化模型、问题及审查摘要，复核关联依赖；保留来源性质，不把临时口径或线索升级为正式承诺。问题确实解决后才标记 `resolved`，仅有回复不代表全部阻断解除。阶段确认由流程状态记录。
- **范围与未决**：用户明确调整范围后保留排除内容、依赖及影响；暂不能决定的事项继续未决，不为清零改成非阻断。只在可交付范围的问题按已有门禁处理、版本与产物绑定一致后请求正式确认。
