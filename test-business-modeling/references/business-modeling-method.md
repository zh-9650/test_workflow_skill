# 用户任务与业务机制分析方法

> **核心原则**：业务理解不是需求摘要，而是**业务事实建模**。
> 本指南指导 Agent 将已澄清的业务事实转化为结构化、可追溯、能够支撑测试设计的业务模型。先按 [业务发现与规则澄清](business-discovery.md) 理解业务目标、提取有效要求、用例子检查规则，再使用这里的机制视角；不要直接按 Schema 填表。

---

## 1. 原则：以业务对象与事件为核心，拒绝模块抽象套话

1. **菜单帮助导航，任务解释业务**：
   - 模块可以说明业务提供方和维护边界，但不能只按菜单复述功能；
   - 从用户任务进入对象、状态、关系、事件和不变量；这些实际机制为下游设计提供依据，人工报告不需要读者学习内部缩写。
2. **避免替产品预设通用答案**：
   - 严禁武断预判“同名重建必须形成新身份”、“历史一律不可修改”、“已发布对象一律不可变”、“有引用一律阻止删除”或“失败一律必须提供重试”；
   - 正确的方法是指导 Agent **从资料与证据中查明这些规则**。若资料沉默，应列出可能的分歧作为待确认问题，而不是自行填入假想规则。

---

## 2. 先建立用户任务与业务全景

消费阶段①的范围、有效资料、依赖事实及其条件/例外、版本、限制和查证去向。发现新依赖时局部补查，不复制整个历史模块。

围绕用户目标说明角色、场景和输入，串起必要前提、重要活动、决定性分流、最终结果及后续使用条件。同一任务可以经过多个页面或模块；同一页面也可能服务不同任务，不限定任务数量。

从范围内资料反查基础操作，确保查询、筛选、维护、启停、删除、历史等实际存在的功能有任务或独立维护活动承接。主旅程没有覆盖某个操作，不代表它自动排除；原型未出现“取消”也不代表必须新增该能力。排除或未知要有依据。

解释重要概念的业务目的、稳定身份、归属和关系，例如同名是否同对象、当前事实与历史快照是否分离。由谁提供、谁维护、读取/改变什么和谁消费结果，都采用已查明的业务事实；独立功能不强造外部依赖或技术引擎。

主报告先用总览图配连续讲解串起基本任务，再在难点放局部图和说明。内部能力索引聚合任务所需机制，不能代替完整任务讲解，也不形成另一套正确行为。

**本环节自查**：从起点能否走到已知结果；基础功能是否有去向；重要角色、概念和依赖是否清楚；是否把未知画成确定箭头。输出任务路径、基础功能、对象关系、条件、来源和未决边界，供后续深入。

## 3. 重要事件分析与粒度判断

**3.1 执行增强**：在六问推导完成后，必须用 [业务机制完整性门禁 B/C](mechanism-integrity-gate.md) 将事件连接到状态机/实际迁移/关系，区分改变、只读校验、不适用、未决。只有模型中的 `state_changes` 文本或旁边一个孤立状态机，不代表完成了可追踪的关联。若存在并存版本或运行中请求，必须单独说明两个事实的身份与生效窗口。

对于每个重要业务事件，必须遵循以下完整的推导顺序：

```text
发起者与目标对象
➔ 入口与前置条件 (Preconditions & Guards)
➔ 输入载体与特征 (Inputs & Variations)
➔ 决定条件 (Decision Conditions)
➔ 行为与动作 (Action)
➔ 状态 / 关系 / 事实变化 (Changes)
➔ 必须保持不变的事实 (Invariants / Must-Not-Change)
➔ 下游消费能力 (Downstream Capability)
➔ 失败后最终事实 (Failure Final Facts)
```

### 必须明确回答的六个核心问题：
1. **谁能对什么对象做什么？**（角色权限、主体租户、目标对象稳定身份）
2. **哪些条件改变是否允许、执行路径或结果？**（前置检查、输入特征分支、业务限制条件）
3. **成功后真正改变了什么？**（对象属性更新、状态跃迁、数据落盘、关联建立）
4. **哪些相关事实按规则绝对不能被改变？**（关联对象保持、历史审计快照保持、其他租户/命名空间隔离）
5. **失败后最终留下什么？**（事务回滚、部分失败保留、错误标记、是否产生孤儿数据）
6. **什么时候允许后续操作或下游使用？**（准入条件、就绪标志、消费准则）

> **红线**：严禁使用“执行对应操作”、“符合业务要求”、“相关对象保持正确”等套话代替实际分析。

### 用业务差异决定合并与拆分

主体、触发、独立动作、状态迁移、结果归属、失败后果或下游影响不同，提示需要分别分析；不自动等于每项必须拆成事件。

- 可以合并：不同入口遵循同一规则；同一动作的多个分支能分别写清条件和后果；共享规则集中定义后各处准确引用。
- 应进一步拆解：合并后只剩“上传成功”“按权限处理”等笼统描述；同一条预期无法分别解释不同状态、时间点、保持项或独立失败。
- 承载方式可为事件、分支、状态迁移、规则或完整流程。分析清楚差异后，再根据现有合同组织，不以记录数量判断深度。

例如上传链需按资料区分选择、校验、受理、关联与内容消费。前置拒绝和受理后失败若留下不同业务事实，应分别说明；可以放在一个事件的明确分支中，也可以拆开，不能只写“失败不影响数据”。事务、错误码和日志是否属于正式承诺，需查证。

**本环节自查**：换一个决定条件后，模型能否解释变化、保持和失败结果，或指出哪个规则尚未定义。只在名称、输入列表或引用中提到一个操作，不算解释了其行为。若需要执行者临时决定产品行为，当前分析仍有缺口。业务例子与关键条件组合可在此用于澄清；全量测试数据、执行参数组合和操作步骤留给下游。

## 4. 跨事件、分支、时序与关系生命周期

### 4.1 跨事件时序与并发分析
- **正常主链与分流分支**：分析真实存在的主干与异常分支；
- **异常中断与撤销**：中断、取消、撤回、驳回、回退时的状态和关联处理；
- **部分成功与后续处理**：多步骤流程中，部分成功时的状态与补偿机制；
- **合法恢复路径**：失败后系统是否支持重试、重入或人工补偿；
- **关键操作时序**：
  - 先绑定后停用 vs 先停用后绑定；
  - 处理中修改配置 vs 完成后修改配置；
  - 存量任务运行中修改规则对已有任务与新增任务的差异；
- **上游变更的传导影响**：上游对象状态改变后，下游候选列表、执行引擎、统计视图和引用关系的连锁反应。
- 并发说明允许与禁止的业务结果、重复或冲突后果，不要求指定锁、排队或事务算法。受理、处理、完成及可消费按真实业务含义区分，不预设统一状态名或恢复能力。

### 4.2 关系生命周期
不能只写“A 与 B 是 1:N 或 N:M”。按适用性查清生命周期，不存在的环节说明不适用，不编造恢复或解绑入口：
```text
建立 (create) ➔ 修改 (update) ➔ 失效 (invalidate) ➔ 恢复 (recover) ➔ 解绑/删除 (remove) ➔ 删除保护
```
- 谁是事实来源（Source of Truth）？
- 谁只能查看不能维护？
- 上游改名后关系是否保持？
- 上游停用/异常时关系是删除、失效还是保持？
- 上游删除时是阻止、级联删除还是解除关联？

### 4.3 独立状态与当前/历史事实
- 每个状态说明：从何处进入、可执行动作、合法迁移、非法阻断迁移、迁移对下游的影响；
- 多个独立业务维度不能压缩为一个混杂状态字段（如：处理进度维度 vs 审批状态维度应正交拆分）；
- 排查状态机中的不可达孤儿状态（Dead States）与非预期的死锁陷阱（Traps）。
- 核对配置、名称、权限或关系变更是否影响存量、运行中与历史。状态图表达资料支持的迁移和限制，未知分支明确标注，不因图中缺箭头就扩充产品能力。

## 5. 输入、配置与判断依据（按适用性展开）

三大推导专项旨在防范“名义实现”与“假通过”，应根据业务机制的真实特征**精准触发、深度展开**。适用机制严禁无理由跳过，简单直观链路允许紧凑表达，跳过项必须给出明确依据：

### 专项 A：输入载体特征与支持边界
- **适用机制**：输入的形态、内容分布、规模或关系结构会改变路径、限制或结果时展开，不只分析文件后缀。
- **紧凑表达条件**：简单字段或固定枚举可以紧凑表达有意义的条件；说明当前适用性依据，不机械复制豁免口号。
- **分析维度**：
  - **物理载体形态**：不仅识别格式后缀（如 `.pdf`、`.xlsx`），还需拆解载体内部物理特征（如纯文本 PDF vs 扫描件图片、带合并单元格/多 Sheet 报表 vs 平铺表格、加密文件、多编码字符集）；
  - **内容与规模**：时间跨度和分布、空内容、字段结构、文本长度、文件大小和附件数量等。具体限值来自资料，实际执行样本留到用例阶段；
  - **损坏与破损边界**：格式伪造（扩展名与 MIME 魔数不符）、网络传输中断导致文件损坏、内容缺页或乱码；
  - **系统承诺与替代行为**：明确系统对不同输入形态是“完整处理”、“降级提示”还是“硬性拒绝拦截”；若资料未定义，必须作为待确认问题提出。

### 专项 B：控制策略与配置生效闭环
- **适用机制**：凡系统行为受控于配置参数、业务开关、阈值限制、算法策略、租户配额或路由分流的场景，**必须展开**。
- **紧凑表达条件**：完全写死在代码中无任何外部参数或配置干预的静态逻辑，可紧凑声明并注明“无动态配置项介入”。
- **分析维度**：
  - **控制什么**：明确配置影响的核心计算、过滤规则或业务执行路径；
  - **生效时机与作用对象**：配置修改后是即时对所有对象生效，还是仅对增量生效，正在运行中的存量任务是否受影响；
  - **实际生效链路**：区分填写、保存、回显、传递、采用和业务结果，按资料说明实际存在的环节。请求参数可以直接消费，展示配置按展示目标判断；不预设必须持久化、广播或加载。相同输出不自动证明配置无效，不同输出不自动证明配置正确；具体对照输入与操作留到用例阶段。
  - **未采用与失效识别**：当配置未被运行时采纳时，系统留下什么可识别的事实（如依然走默认策略、产生特定告警日志）。

### 专项 C：判断依据与证明范围

对重要结果说明正确行为的来源、判断需要的事实、候选证据及其证明范围、单独不足的现象与剩余限制。正文随任务用图文或紧凑说明承载，复杂比较才用表格；不要求固定七列。

按业务实际区分受理、产物、内容有效性与下游可用性。解析、索引和正式检索可以是不同阶段；各自完成条件从有效资料查明，不统一规定“检索命中才算解析完成”。普通读写也不强造多层链路。

跨位置核对先确认同一对象、任务、版本、范围和时间窗口。检索到旧版本或其他文档相同关键词，不足以证明本次文件处理或配置采用正确。观察不到某个环节时，应说明替代证据能证明什么，剩余环节保持受限；物理直读和端到端使用均不自动优于其他证据。

例如，若当前合同明确将解析产出与索引就绪分开，则应分别说明解析结果事实和检索准入事实。模型只定义未来需要核对的内容，不声称已经读回，更不要求在业务理解阶段连接真实存储或执行产品测试。原生底座结果可作诊断对照，正确预期仍由集成产品需求和有效接口合同决定。

- **假通过排查要点（铁律）**：
  - **状态持久化 ≠ 处理完成**：接口返回状态 `active` 或 `success` 仅证明“状态字段被置成了该值”，不能单独证明真实数据已解析落盘；
  - **受理提示的范围有限**：HTTP 成功响应或前端提示的具体含义由接口合同决定，单独展示它不足以证明异步处理或最终业务结果；
  - **元数据存在 ≠ 内容可用**：列表展示记录仅代表外壳记录生成，不代表切片、向量或依赖的外部引擎已就绪；
  - **计数一致 ≠ 隔离合规**：数量吻合不能证明多租户/角色鉴权无串号泄漏。

## 6. 用合理错误实现检查辨别力

在业务建模与审查过程中，分析人员必须主动站在反向角度提出**“合理的错误实现假设”**，以检验业务理解是否具备足够的辨别力：

1. **什么是合理错误实现假设？**
   - 从当前有效规则出发，构造一个可能满足表面现象、却违反真实业务结果的实现。用于检查模型的判断能力，不推断开发动机，不把假设当已发现缺陷；
   - 例如：
     - 后台创建任务表项并直接把状态写成 active/success，但后台解析消费线程异常退出，未产生物理切片；
     - 前端仅通过 `v-if` 隐藏了操作按钮，而后端 API 完全未做角色鉴权拦截；
     - 重试场景若要求独立执行记录，却复用旧执行结果或缓存，造成结果归属错误；
     - 删除会话时仅将主表记录打上逻辑删除标记，但关联的下载直链与临时文件存储未加鉴权校验；
     - 两个异步结果到达后违反已明确的先后或归属规则，覆盖了不应改变的结果。核对业务后果，不规定必须用锁或某种版本算法。
2. **如何应用于业务建模？**
   - 检查模型中定义的业务规则、成对证明账本和不变量，是否能够**精准识别并拦截**这些合理的错误实现；
   - 若错误实现仍满足现有判断依据，回查当前规则与候选事实，补足实际有依据的条件；无法定义的部分登记未决。按风险选择场景，不要求每个低风险点编造故障。

## 7. 查证与待确认问题

当需求缺失、存在歧义或资料冲突时，形成待确认问题：
- **查漏补缺**：能从现有资料中查到的事实必须自己查，不把原本有记载的事项转嫁给用户；
- 提问前查相关有效来源及已有回复，考虑别名、图表和版本。搜索未命中不等于全部资料沉默；资料不可达、实现选择、待试验事项与产品规则未定分别处理。真正需要人决定且影响业务或范围的才提问，技术术语不改变问题性质。
- **非引导性提问与开放性兼顾**：
  - **前置能力承诺澄清**：在已知资料不足时，先澄清基础能力承诺（例如“系统是否承诺支持此形态”），严禁在未确认底层能力时强行抛出二选一；
  - **允许开放式澄清**：若方案空间未定界，允许提出开放式问题，不强制所有问题均列出预设选项；
  - **not_recommended 规范**：若必须列选项且依据不足以支持偏好，显式设置 `recommendation_status: "not_recommended"`，严禁附带 `recommended_option`，并给出中立代价分析；
- **人工回复性质分类与 5 步扩散闭环**：
  在同步人工回复前，先识别回复性质（见 `SKILL.md` 环节⑤）。正式裁定、获准临时口径、经来源查证的纠错及范围变化均可能更新当前模型；按实际影响同步正文、图、结构化数据、问题和审查摘要，复核直接与间接依赖。保留各自来源与效力，不把纠错线索或临时口径升级为正式产品承诺。问题的场景、依据及影响表达见 `human-readable-reporting.md`。

## 8. 内部能力索引与下游承接

本节的缩写、字段和标识供 Agent 内部建模与交接使用。人工报告、图解和问题采用中文业务名称，映射按需展开，不要求读者理解编号。

为确保上游业务理解与下游测试设计（`test-point-design`）无缝对接，必须明确 CAP 的承接与展开规则：

1. **CAP 的职责定位**：
   - CAP 是面向业务全景的**顶层能力索引与审查导航**，用于回答“系统承诺向用户交付哪些端到端能力，成立条件与成对证明边界是什么”；
   - CAP 不替代底层的原子机制，而是作为底层模型元素（`events`、`rules`、`invariants`、`cross_module_flows`）的高层业务聚合。
2. **下游测试点设计的引用规约**：
   - 下游契约工具（`test_point_contract.py`）直接校验机制级 ID 引用（`events`, `rules`, `invariants`, `flows` 等）；
   - 当前测试点合同的 `model_refs()` 不包含能力索引 ID；覆盖义务的 `source_model_refs` 引用实际机制，测试点再经 `source_coverage_ids` 关联覆盖义务，并在适用时使用 `business_event_ids` 等具体机制字段。不要虚构一个统一的单数 `source_model_ref` 字段，也不要仅以能力索引替代机制；
   - **展开映射示例**：
     ```text
     [上游业务模型]
     CAP-WB-001 (会话全生命周期管控)
       └── applies_to_refs: ["EV-CONVERSATION-INIT", "EV-CONVERSATION-DELETE", "RULE-FIRST-MSG-CREATE"]
           └── proof_boundary: (成对证明事实与假通过陷阱)

     [下游承接，以下是关系示意，不是可直接导入的完整模型]
     覆盖义务.source_model_refs: ["EV-CONVERSATION-INIT"]
       └── 测试点.source_coverage_ids: [该覆盖义务的实际ID]
     其他具体规则和事件分别承接，不以能力索引整体引用替代。
     ```
   - 这样既保证了业务全景的 CAP 导航审计清晰，又确保了下游测试点具备明确、可落地的机制级断言和契约校验闭环。
