# 业务理解方法｜从资料到可确认业务基线

这份 Reference 只解释主 Skill 里的关键分析方法，不新增另一套框架。

## 1. 来源怎么用

### 规范性来源

用于回答“应该怎样”：

- 当前 PRD / 需求规格；
- 当前评审结论；
- 正式产品补充；
- 当前任务用户明确确认。

### 当前实现来源

用于回答“现在怎样”：

- 页面；
- API；
- Network；
- 当前源码；
- 配置；
- 数据库只读信息。

### 历史材料

用于风险提示，不自动继承规则。

### 冲突处理

例：

```text
PRD：同分组内唯一
接口：全租户唯一
```

记录双方，不能静默选择。

## 2. 真实业务面盘点

拆模块前扫：

- 页面入口；
- 二级入口；
- 从其他模块跳入；
- API-only；
- 导入/导出；
- 批量；
- 异步任务；
- 外部触发。

每个真实能力都要有归属：

- 当前范围；
- 依赖了解；
- 不测；
- 已废弃；
- 未知；
- 与需求冲突。

## 3. 核心对象

对真正重要对象理解：

- 身份：如何唯一识别；
- 所有权：用户/部门/租户/项目；
- 关联：与谁绑定；
- 创建和消亡；
- 状态；
- 下游谁消费。

不需要为了完整性把每个字段实体化。

## 4. 状态和生命周期

只有状态真正改变业务行为时建立。

至少回答：

- 如何进入状态；
- 如何离开；
- 允许什么；
- 禁止什么；
- 谁触发；
- 失败在哪里；
- 重复操作；
- 撤回/驳回；
- 恢复；
- 终态后的行为。

## 5. 数据变化与影响

针对重要写操作：

```text
前置
→ 直接变化
→ 关系/状态变化
→ 下游影响
→ 独立观察位置
→ 应保持不变的内容
```

尤其关注：

- 修改名称后哪些地方同步；
- 删除后历史引用；
- 停用后已有绑定对象；
- 切换配置对旧数据/新数据；
- 状态变化后的角色权限。

## 6. 配置类能力

配置保存成功不是重点。

重点：

```text
何时生效
影响谁
旧数据是否变化
新数据是否变化
进行中的流程怎么办
是否需要重处理
是否存在异步/缓存
```

## 7. 时间和异步

时间：

- 到期当天；
- 生效时刻；
- 下个周期；
- 时区；
- 定时任务。

异步：

```text
请求接受
→ 处理中
→ 成功 / 失败
→ 重试 / 超时
```

不要把“请求返回 200”当成业务处理完成。

## 8. 跨模块五条线

沿完整业务链检查：

1. 对象身份连续；
2. 状态连续；
3. 数据传递连续；
4. 角色交接连续；
5. 时间/异步连续。

## 9. 长链路异常

从以下方向产生业务理解问题：

- 阶段前上游发生变化；
- 阶段中失败；
- 阶段中重复；
- 阶段中退出/换角色；
- 阶段后上下游不一致；
- 恢复后是否重复副作用。

## 10. Unknown 与 Conflict

### Unknown

所有当前资料都没定义。

### Conflict

现有资料说法不同。

问用户前写清：

- 已查什么；
- 缺什么；
- 不同答案影响什么；
- 影响哪些模块/业务链。

## 11. 简单模块

只读查询、没有状态、没有流程时，文档可以很短。

不要为了“模型完整”填一堆 `not-applicable`。

## 12. 复杂模块

如果真实存在状态、多角色、多模块、异步、影响链，就必须展开。

“简单模块简洁，复杂模块深入”才是目标。
