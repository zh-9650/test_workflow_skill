# Business Modeling Method

## 1. 原则

业务理解不是需求摘要，而是业务事实建模。

对于每个重要操作，至少从以下角度追踪：

```text
触发
→ 前置
→ 输入
→ 输出
→ 直接变化
→ 状态变化
→ 关系变化
→ 下游影响
→ 不应变化
→ 失败后事实
```

## 2. 不把模块当模型

模块用于组织文档。
对象、状态、关系、Event、Invariant 才是 Test Point Design 的稳定输入。

## 3. 关系要有生命周期

仅写：

```text
A N:M B
```

不足以支持测试设计。

还需要：

```text
建立
修改
失效
恢复
解除
删除保护
```

## 4. 状态要有迁移

仅写：

```text
draft / enabled / disabled
```

不足以支持状态测试。

还要有：
- 从哪里进入；
- 哪个动作触发；
- 哪些前置 guard；
- 哪些迁移被阻断；
- 迁移后影响。

## 5. 失败要有最终事实

失败测试真正关心的是：

```text
失败以后系统还剩什么？
```

因此失败条件必须追：
- 主对象；
- 状态；
- 关系；
- 下游；
- 可重试性。

## 6. 历史事实和当前事实分离

如果业务存在历史记录、快照、审计、已完成任务，需要明确：
- 当前配置变化是否影响历史；
- 历史对象是否继续引用旧 ID；
- 当前事实源是什么。

## 7. 待确认/未知项不等于全部阻塞

只有会改变 Expected 的业务待确认项 才阻塞对应 Scope。

其它实现/UI/外部依赖问题保留，但不强行阻断整个测试设计。
