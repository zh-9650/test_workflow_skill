# 业务发现与规则澄清

业务理解需要发现资料没有讲透的问题，同时保留资料已经讲清的要求。本指南用于建立业务图景、拆解含义、选择分析方法和形成验收依据；事件等内部结构见 `business-modeling-method.md`。

## 1. 从业务目的和使用现场开始

先从可得资料查明以下内容，简单业务可用一段话说明：

- 谁发起工作，谁使用结果，谁承担错误后果，谁有权裁定规则；这些角色不一定是同一个人。
- 过去如何完成，现在改变什么；用户真正需要的结果是什么。按钮点击、请求受理和任务结束可能只是中间步骤。
- 系统负责到哪里，哪些由人员、外部系统或其他模块负责；入口、出口、信任与数据边界在哪里。
- 实际使用涉及哪些角色、数据形态、规模、频率、环境和时间约束；哪些是已知事实，哪些只是待验证假设。
- 当前变更影响哪些已有行为、共享规则和使用者。已有业务未被明确替代的规则仍需继承。

背景用于决定查证方向和分析深度，不强制补写商业指标。缺少用户访谈时可依据原文和已有反馈分析，但明确缺少哪类现场信息，不假称与利益相关方达成共识。

## 2. 获取证据与选择工具

| 要解决的问题 | 可用方法或工具 | 留下什么 |
|---|---|---|
| 资料在哪里、哪些仍有效 | 目录、全文检索、关联需求、评审和版本差异 | 来源位置、效力及替代范围 |
| 条款是否藏在表格或图片中 | 文档解析、表格读取；关键图像/OCR结果回看原图 | 章节/页/表定位及读取限制 |
| 入口、禁用态或隐藏交互是什么 | 原型静态阅读；已授权环境中的浏览器走查 | 到达条件、状态、行为及与规则的差异 |
| 规则怎样在真实工作中被使用 | 已有反馈、业务案例、必要的澄清 | 场景、角色、结果和未决问题 |
| 历史哪里容易出错 | 用例库、缺陷 MCP/记录、修复和回归证据 | 原触发条件、违反的承诺、适用版本和处置理由 |
| 依赖交换什么、谁负责 | 相关接口/技术文档，必要时只读源码 | 业务边界与物理实现的区别 |
| 多条件/状态/交接是否自洽 | 条件表、状态表、流程/时序/关系图 | 可以解释业务差异的局部模型 |

优先使用可用连接器和现有工具；缺失就选择等效读取方式。大文件分段读取并保留未读范围；扫描件和复杂表格不能仅凭文字提取成功宣称完整。

原型探索遵循授权和环境边界。无法确定是否连接真实后台时以静态分析为主。此阶段不要求执行产品测试，也不自行联系他人、提交缺陷或改动业务数据。

历史案例提供风险线索，不直接提供当前 Expected。缺陷关闭不等于问题已验证消失；先读处置理由及回归条件。将可迁移的失效机制带回当前业务，不照搬旧版本功能。

## 3. 从条款提取业务要求，保留语义

“业务要求”指可分别成立或违反的承诺、限制或条件，不是测试点，也不是必须新增的一种 JSON 实体。

读取有效条款时，找出主体与对象、动作、适用条件、结果、例外、时间/顺序、数量/范围，以及禁止或保持项。一条来源可能包含多项要求；多处来源也可能共同说明一项要求。

以下差异容易在摘要中丢失：

- “只能查看”与“可以修改但不生效”；“不展示”与“禁用”；“不得发起”与“发起后失败”。
- “每次”“仅当前”“所有”“至少”“期间”“之后”“除非”的作用范围。
- 单对象与批量、局部恢复与全部恢复、新增与编辑、已保存与已发布。
- 角色授权、二次确认和独立复核：都影响操作，但不是同一个条件。
- 输入规则、结果展示规则、内部协议规则各自的适用边界。

先识别这些义务，再归入任务和机制。共享规则只保留一份定义，但每个适用处能定位；不要将一句复合条款挂到一个事件后就宣布全部承接。

利用已有来源记录或审查摘要保留紧凑的承接关系：

```text
有效来源定位 → 具体要求（条件与后果） → 模型中承接位置及含义
                                         或：未决问题 / 明确排除及依据
```

不强制逐句编号或额外新文件。范围内的有效要求均应核对，低风险要求可以紧凑表达；风险用于决定分析深度，不能据此静默删除。未取得的资料单列限制，不能虚构其要求清单。

**内容检查**：从承接位置能否还原原要求的条件和后果？如果只在 `inputs`、名称或来源引用中出现关键词，实际行为没有定义，仍是缺口。仅写“后续补充”或“测试点承接”不算本阶段完成。

## 4. 用例子检验规则含义

对含歧义、多条件、易误判或高后果的规则，组织“任务—规则—例子—问题”：

1. 给一个足以说明规则的业务例子，描述当前状态/输入、发生的事和应有结果。
2. 改变决定性条件，选择能区分不同理解的反例、例外或边界；解释为什么结果改变，或为什么仍应保持。
3. 回到有效依据核对答案。若两种行为都能与现有资料相容，说明规则尚未定清；若原文已有答案，直接补入理解。
4. 把澄清出的事实保存在正式规则/事件中；例子用于说明，不另建一套只存在于说明文字中的规则。

例如，假设需求说“仅恢复选中分组，其他分组保持当前编辑值”：选两个已修改分组，恢复其中一个，就能区分局部恢复与全部恢复。业务理解应保留目标范围和保持项；具体点击步骤、账户及执行数据交给用例阶段。

例子可使用小数值、具体状态或虚构对象以澄清语义；明确它是说明实例，不能把实例数值变成产品限值。简单、无歧义的规则不强迫制造正反例，也不在本阶段枚举全部执行组合。

## 5. 根据疑点选择分析方法

| 触发情形 | 分析方法 | 要弄清的业务问题 |
|---|---|---|
| 多条件共同决定结果 | 决策表 / 条件—结果表 | 哪些条件独立、互斥或有优先级；合法组合是否有唯一结果；冲突或空白在哪里 |
| 动作受对象状态限制 | 状态—动作表 / 状态图 | 哪些动作在什么状态下允许、禁止或未定；成功/失败后的状态和事实 |
| 内容、规模、格式改变行为 | 等价类和边界含义分析 | 哪些类别走不同规则；阈值端点、单位、计数口径和多个限制的关系 |
| 多角色或系统交接 | 任务流程 / 时序图 | 谁交什么给谁，何时责任转移，何时能继续，未收到或晚到的后果 |
| 多对象关联或历史版本 | 关系图 / 生命周期对照 | 身份、归属、维护方、变更传导、删除/失效及存量与历史差异 |
| 汇总、计算、筛选或排序 | 输入—计算—输出对照 | 单位、精度、空值、去重、顺序、舍入和结果适用范围 |

不穷举无意义的笛卡尔积：先按资料排除不可能组合，说明条件依赖，再检查可能改变结果的组合。合并行只有在相关结果和限制相同且有依据时成立。空白结果标未定，不用默认分支掩盖。

这些方法用于发现业务规则问题。测试覆盖强度、全量数据组合、测试路径选择和执行排期由下游负责；业务决定性条件本身在此阶段保留。

## 6. 检查需求本身是否足以验收

除“有没有抄漏”，还要检查：同一词是否有不同含义；条件是否矛盾；主流程能否达到目标；约束能否同时成立；承诺是否存在无法判断的形容词；失败后业务责任是否悬空。

用业务、使用、实现/运维等相关视角互相追问：谁认为完成，谁能继续使用，错误损失是什么，什么情况下规则会不适用。视角不等于强制组织会议；先查资料，有真正决策缺口再问有权裁定的人。

十三个既有机制维度不能穷尽质量要求。根据场景和来源检查有实际关联的内容：

- 性能/容量：什么操作、规模、负载、时间范围下达到什么目标；“响应快”尚不能直接验收。
- 可用性/易用性：目标用户怎样完成任务，状态、反馈、防误操作及无障碍等是否有明确承诺。
- 安全/隐私：角色和数据边界、敏感信息暴露、保留和清理要求；遵循有效规范，不自行给产品增设制度。
- 可靠性/恢复：中断损失、允许降级、恢复责任和业务可继续条件。
- 兼容/运行环境：已承诺的终端、版本、外部接口、地区/时间/语言、升级或迁移影响。
- AI/概率性输出：哪些结构和业务约束必须满足；哪些内容质量需要业务样本、评分标准或人工裁定；单次同输出/异输出不证明策略是否采用，也不能自行承诺绝对准确率。

已有承诺进入规则及相应机制。仅由经验提示的风险，先写为风险/查证问题；只有实际影响范围或验收且查证后仍未定的事项才阻断对应范围。不要把每个启发问题升级为产品需求或阻断项。

## 7. 风险、判断依据和停止分析

风险讲清“在什么情形下，什么可能出错，谁受到什么影响，以及为何值得关注”。结合历史证据、变更范围、使用频率和复杂度定性排序；无数据不编造概率、损失数值或精确评分。

对高风险结果深查依赖、条件组合、失败后果和证据区分力；对低风险明确规则简洁保留。风险与未决各有用途：已完全定义的规则仍可能高风险，未知也不一定阻断全部任务。

判断依据回答：正确行为由哪条有效规则决定；什么业务事实成立才说明满足；候选证据能证明哪些事实；一个表面成功但实际错误的行为能否逃过判断。

需要未来接口、日志或读回入口时登记观察需求，不编造物理路径。不要求所有业务都读数据库，也不把界面证据一概视为无效；证据是否够用取决于承诺本身。

当有效要求已承接、决定性差异已解释或登记未知、重要结果具备判断依据、继续追查不再改变当前判断时，可结束当前分析并交审查。新增证据改变事实，再局部展开。停止不等于声称已发现全部未知风险。

## 方法依据与取舍

以下是一手方法来源，不要求每次执行联网重读；本指南是面向本工作流的应用规则，不宣称认证或标准符合性。

- [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)，§1.4、§3、§4.2、§4.5、§5.2：测试依据分析、需求静态审查、条件/状态方法、验收标准和风险。此处用于澄清业务，正式测试点选择留在下一阶段。
- [Cucumber：Introducing Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/)：区分规则、例子与问题，以例子形成共同理解；不要求此阶段写 Gherkin 或强行每条规则配例子。
- [James Bach：Heuristic Test Strategy Model](https://www.satisfice.com/download/heuristic-test-strategy-model)：从项目、产品与质量等视角启发查证。按业务选视角，不把启发清单当作所有产品的强制规格。
