# 跨旧版机制继承与效果回归：适用于每次修改 Skill

## 一、版本差异审查必须覆盖的老能力

来源范围：10月9日打包的业务理解版本、10月20日工程化 V1.1、10月21日深入重构、10月22日简化发现版、3.1机制完整性版、3.2-alpha条件辨别版。详细矩阵由改造交付单独记录；没有取得过的版本要明确声明，不编造对比。

**不能退化的能力**：

1. 10/09：对象稳定身份、状态机入/出/非法动作、关系建立/失效/恢复/删除、事件失败终态、业务不变量、分支恢复、证据等级与未决问询。
2. 10/20：原型全入口/隐藏交互发现，未探索队列；用户任务 CAP 及结果；业务事件六问；输入载体与变化；后台完成和表面成功区分；配对证明；真正独立审查；澄清后同步。
3. 10/21：读懂原始资料与有效裁定的不同效力；历史上游依赖查证；用户视角、逐项结果差异；全文/表格/原型 UI 承接；完整且不冗余的中文图文；准确问询；修订后复核。
4. 10/22：用户任务和正反例优先于机械填模型；避免把测试点设计前置到业务理解；用最低必要模型表达事实；留真实证据限制。
5. 3.1：事件对状态/关系的有类型链接，允许真正只读/不涉及，不制造假迁移；并存事实显式承接；已有机制防退化；3.1 Contract 结构检查。
6. 3.2-alpha：决定性条件改变 → 不同业务结果 → 可区分假成功的证据；启发式审查不冒充语义事实；通用性优先。

**本次专修**：按子句隔离已取消/被替代要求，当前正确预期不能反向带入旧行为；长链路必须到达完整终态、并存事实真实推演；业务正反例要回查原始规则，不能靠常识定正确答案。

## 二、改造时要执行的比较顺序

1. 用与旧版逐项可追溯的能力矩阵，判断“保留/等价迁移/因有效规则取消而排除/待确认/退化”，不能只比 Skill 文件行数、业务事件条数。
2. 从原始需求和已确认裁定创建**冻结、隔离**的评估集，至少有 UI 基础操作、核心决策、范围变更、异步/重试、上游依赖和并行状态；已多次见过的危险源/AI工作台只能作为公开回归样本，不能冒充未见盲测。
3. 运行生成 Agent 时，固定输入/已确认裁定/可用工具、模型和时间预算。分别记录未读证据、正确/遗漏/错误/无依据新增及阻断问题；评审者应先读原件再读生成结果。
4. 当次没有独立隔离模型或真实新需求时，声明“方法/工具回归完成，但泛化效果未验证”，严禁宣布全面优于旧版。
5. 发现退化要复现 → 回溯丢失的分析活动 → 修订过程/代码 → 重跑对应负向与历史样本 → 记录误报及仍有局限。不是简单添加一句提醒。

## 三、放行判断

- **工具与结构层**：全量已有 Contract 测试 + 新辅助门禁正反样例通过；没有删掉历史能力或回退为只要求字面存在。
- **已知项目回归层**：旧范围复活、错误正反例、失败链路不闭合、跨版本并存和“表面成功”风险可以被流程主动识别或被证据门禁明确拦截；不要求 AI 自动知道未知产品选择。
- **未知项目泛化层**：由实际未见需求、隔离评估者完成新旧对照，记录高风险正确机制的召回、无依据推断和退化项。未执行时**不能签“效果已在陌生需求上验证”**。
