# 让人读懂的业务报告与待确认问题

本指南用于组织人工报告、绘图、HTML 和提问。内部模型继续保留完整规则与稳定引用；人工阅读以理解、判断和作出决定为目标。

## 1. 先回到原始资料，再决定怎么讲

先列当前任务可获得的需求原文、原型文件及交互、原始评审记录、有效人工回复。涉及现场问题时再查真实输入材料、原始反馈和操作过程；需要解释实现分歧时，在权限内读取请求响应、源码和下游产物。总结、旧报告和缺陷标题只作检索线索。资料缺失如实说明，不自行联系他人或操作真实系统。

原始需求说明承诺；原型说明交互设计或演示；代码和观察说明实现现状。发现分歧时保留各自内容与定位，不把当前实现自动当作正确行为。

工具按材料选择：全文检索定位规则，文档提取读取正文/表格，浏览器探索允许的原型，绘图工具表达关系，浏览器渲染检查 HTML。解析失败或只读到部分内容时记录范围，不声称已完整读取。

## 2. 先建立读者的业务图景

按以下思路组织，篇幅和分节随业务调整，不要求机械填满模板：

1. 谁在什么场景下，要解决什么问题；本轮理解覆盖哪里。
2. 一张可读的总览图，配文字串起从输入到最终结果的基础主链。
3. 沿用户任务解释关键步骤：为什么发生、什么条件改变路径、完成后能做什么、失败后留下什么。
4. 在出现歧义的地方解释概念与关系；例如任务与执行尝试、启用与就绪、当前配置与历史记录。
5. 针对实际难点补状态图、时序图、关系图或分支图，解释异步、配置、权限、失败和恢复。
6. 说明已知限制、交接重点及末尾需要人决定的问题。

正文每个重要任务都应能回答“做什么、为什么、怎样成立、怎样知道结果成立”。以具体场景解释抽象规则，示意场景明确标注，不能借场景补造产品承诺。简单动作可以一段讲清，不强迫画图。

业务背景中说明用户目标、结果使用者与系统责任边界；有实际依据的使用环境和质量要求随相关任务讲解。对容易混淆的规则可放紧凑的“例子—变化条件—结果解释”或决策表。风险讲清具体后果与依据，未知标清影响范围，不把分析问题全部抛给用户。完整条款承接记录留在审查摘要/附件，正文不承担台账展示职责。

基础功能盘点使用读者熟悉的业务名称，例如“上传资料后可用于问答”“修改后哪些任务采用新配置”。内部标识默认留在 JSON 或追踪附件；正文、图节点、目录和问题标题不显示能力/事件/来源编号。产品本身的名称及必要接口名可以保留，并在首次出现时解释。

沿任务讲解后，反查资料中的基础维护和查询活动是否有去向；复杂主链不能遮住编辑、启停、删除、筛选和历史等真实功能。它们可以归入任务，也可以单独简述，不要求都扩写成长旅程。不限定任务数量，不给独立功能强造上下游或提供引擎。

表格用于确有比较价值的短信息；连续过程、因果和背景使用图与段落。完整台账、字段映射、检查维度不要占据报告开头。保留分析深度，不用删掉异常或判断依据换取简短。

## 3. 图与讲解怎样配合

选择图形取决于需要解释的问题：

- 用户从哪里开始、最终得到什么：任务流程图。
- 前台、后台与外部服务先后做什么：时序图。
- 哪些状态允许操作、何时可继续：状态图。
- 哪些对象关联、由谁维护和失效：关系图。
- 用户在什么真实位置操作：有来源的标注截图；示意图不能冒充产品截图。

图题提出它要解释的业务问题。图前交代场景，图后解释关键转折、分支条件、结果和易误解处。节点用短中文业务名称；把长条件放到旁边讲解。大图分为总览与局部，避免把整份模型堆成不可读的网。

确定规则和未知部分在图中清楚区分。观察不到或尚未确认的链路标明限制；箭头不能暗示不存在的先后关系、同步完成或已验证事实。

图解多少取决于理解难点。复杂业务要覆盖基础主链和主要难点，不能只有一张装饰性总览图。颜色辅助区分，同时保留文字含义。Mermaid、SVG 等均可，不要求特定工具。

图放在解释相应内容的位置，不要求固定三张或全部前置。图中的业务承诺必须能回到资料；状态迁移、依赖或恢复路径未知时标为未定，不能为补齐图形自行添加。

## 4. 每个问题提供完整前因后果

写问题前先核查相关有效来源、依赖事实、已有回复与裁定，考虑别名、图表和版本。说明实际查证范围，不要求全项目关键词搜索后才能提问。访问不到、纯实现选择、待试验事项和产品未定义分别处理；真正影响业务后果的事项即使涉及技术概念也不能遗漏。

把问题当作给未参与分析的人阅读的短说明。每题围绕一个决定，按自然语言说明：

- **场景**：谁正在做什么，事情发展到哪一步；必要时配小图。
- **已知内容**：资料明确了什么。附相关短摘录或忠实摘要、文档名称、章节与可访问定位。冲突需展示双方。区分逐字摘录与自己的转述。
- **缺口**：现有资料为什么还不能决定当前行为；已自行查过哪些相关材料，核查范围有什么限制。
- **影响与决定**：不同答案如何影响用户、流程、结果或本轮范围；现在需要用户决定哪一件事。
- **选项与建议**：有已知可行选项时说明具体后果，允许补充答案；方案空间不明时开放询问。没有依据时说明暂不推荐，不用风险措辞强推某项。

这些信息不一定逐项打字段标签，但不能省掉解释。引用链接用于核查，问题主体应足以理解。阅读者无需先找另一个问题、来源索引或模型编号才知道在问什么。可独立回答的事项同轮集中，真正依赖前置决定的事项后置；背景相同的多个决定可以共享短场景，但仍能分别回答。

选择应来自已知方案空间，不将“保留草稿”直接等同于已具备断点续传等未确认能力；无法判断时开放询问。收到回复后，由业务事实变化决定是否修改正文、图和模型；来源效力、临时性质及受影响复核同步保留，不能只改文末答案。

### 表达示例：开关对下一条消息是否继续生效

以下仅演示写法，假设资料内容也仅用于示意，不能直接带入真实项目。

**场景**：用户打开“联网搜索”，发送第一条消息。回答结束后，他没有操作开关，又发送第二条消息。

**资料已经说明**：假设《工作台需求说明》的“输入区”章节写“本次请求使用用户选择的搜索设置”；假设原型发送第一条消息后，开关仍保持开启。正式报告需替换为实际查到的原文、文件链接和章节，不能照抄此假设。

**尚不清楚**：开关保持显示是否意味着用户已经允许第二条消息联网，还是仅表示上次选择。两种处理会影响连续提问的操作次数与授权提示。

**请决定**：开启搜索后，授权应持续到什么时候？

- 仅本条消息：下一条需要重新开启，用户每次明确选择。
- 当前会话内持续有效：后续消息继续允许搜索，界面持续显示开启状态，用户可随时关闭。
- 若这两种均不符合产品安排，请说明预期范围。

在没有明确授权依据时，说明暂不推荐，并保留待确认状态。不要因为原型开关未重置就替产品决定授权范围。

## 5. HTML 是图解阅读界面

用户要求 HTML 或图解阅读时，提供同版本 HTML，链接回正式报告和资料。默认界面按业务故事展开：简短导读、总览图、逐段任务讲解、关键局部图、限制与末尾问题。目录使用中文任务名称。

图在 HTML 中应实际可见。可直接内嵌 SVG，或使用可用的图形渲染器；只显示 Mermaid 源码不算图。离线交付优先自包含资源，不把核心阅读依赖在外部 CDN 上。

重要背景、未知和影响默认展开；内部映射与长证据台账用 `<details>` 等方式按需查看。来源入口展示资料名和章节；展开后能读相关摘录与位置。链接不可访问时给出可复制的完整文件路径并说明限制。

实际打开 HTML，检查图文字可读、长文本换行、窄屏布局、锚点和展开操作、打印效果以及无丢失的业务内容。工具可测溢出、缺图和断链，但不能据此声称人已读懂。未能渲染时明确记录未验证，不报告视觉验收通过。

## 6. 用什么判断交付有效

分别检查业务正确性和阅读效果：

- **业务正确性**：重要结论可回到有效来源；独立审查者先读原始资料再反查遗漏、臆造及矛盾；图与正文、问题、内部模型同版本一致。真实观察只能证明对应对象、版本和范围。
- **辨别力**：对关键机制提出可能的错误实现，检查当前判断依据能否识别；需要改造验收试验时，在隔离副本中植入遗漏或错误，记录实际发现、漏报和误报。已知答案练习不能冒充盲测。
- **阅读效果**：隐藏所有内部编号，只看默认正文、图和单个问题，能否说清主流程、关键区别、缺口及不同决定的后果。图缺少解释、关键背景只在折叠区、问题必须跳转才能读懂，都应修订。
- **第三方反馈**：有条件时请未参与生成的人试读，或由独立上下文审查阅读障碍。真实用户反馈与代理审查分开记录；未取得反馈就标未验证，不以自评好读替代。

修订前后用相同资料比较：是否减少无关跳转，是否更容易解释关键流程，是否能独立回答问题，是否丢失必要规则。单测、编号数量、表格数量、图数量和自审标记都不单独证明这些结果。


## 3.3 版本补充：效果与完整性优先

- 当任务复杂、跨角色或多模块时，主报告优先提供**文字解释 + 总业务流程图 + 关键链路图**，让用户理解实际入口、条件和结果；不能用一大堆 JSON ID、模型统计和自评结果代替。
- 正文只讲**本期有效业务**，原始但已取消的机制放在“范围变更/来源审查”栏明确注明不属于本期；不能一边说取消一边又把旧行为作为当前正确操作示例。
- 对重要长链及跨模块状态，主报告要能顺序读出：用户何时开始、运行中改变了什么、失败或停止如何结束、还有哪些旧事实不得影响新的请求。结论若未确定，写清条件和不同答案后果，不使用确定性词语。
- 每轮 Grilling 问题集中在文末，并按实际证据给出有依据的推荐或“不推荐”；交互讨论末尾说明本轮内容、阶段进度、当前环节和下一轮 Frontier。已正式确认的问题不得反复询问。
