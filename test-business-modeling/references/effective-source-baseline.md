# 有效业务事实基线：防漏读、防旧需求复活、防错误示例

> 先读原始资料、再判有效性、最后进行业务推演。本方法适用于新的未知项目，不以任何具体项目编码、文案或流程作通用假设。

## 一、输入必须从原件出发

1. 先登记本轮原始 PRD / 原型 / 评审后正式说明 / 权限与上游依赖 / 真实人工裁定。历史 AI 生成结果只能作为**最后的回归线索**，不能覆盖原件、不能当业务真值。
2. 每份资料列出文件/版本、可读部分、正文、表格、批注、隐藏页/可达路径、图/脚本和限制。对 HTML 原型建立**入口 → 控件/动作 → 前置显示条件 → 响应/跳转**索引；模态、抽屉、标签、空态/编辑态、上传入口、键盘操作均属于索引范围。运行原型前确认数据安全；不能动态操作就记录未探索路径。
3. 只要该模块属于本轮范围，全文、表格和实际交互必须被覆盖或标记受限。上游依赖按“当前业务规则是否会受它影响”有目的地追查，无需无限通读其他模块。
4. 需求原文编号不是最小单位：一句要求可能同时包含本期保留、已取消和未明确的子句。必须以**能独立满足或违反、导致不同业务结果的子承诺**拆开，保留原编号与子句定位。反之不能把同义句简单拆成重复事项。

## 1.1 原型与 PRD 的四向核对（不能跳过）

- `PRD → 原型`：每个承诺的输入、按钮、分支、状态反馈在原型何处可到达？无入口是否属于合法非 UI 服务能力？
- `原型 → PRD`：实际存在的上传、重置、可选角色/模式、键盘触发、弹窗内动作与条件显示是否有业务依据？
- `静态 → 动态`：源码/HTML 中发现的监听器、隐藏 tab/路由若允许实际操作，必须记录真实可达路径；仅源码存在不等于用户能操作。
- `动态 → 静态`：动态交互产生的新页面、状态、反馈、分支是否已补回页面状态索引？无安全可执行环境时把这两向标记“未实测”，不能假称完成。

每个入口和状态以 `用户角色 + 当前页面/对象状态 + 触发条件 + 操作 → 新页面/反馈/后续入口` 为最小记录。已知但未进入的抽屉、弹窗、编辑态、状态条件支线列入待探索队列；**高风险、核心任务的未探索分支阻断完整交付**。不为了凑覆盖在真实生产环境触发危险动作。

## 二、每条独立子句先确定效力

建议将已有来源追溯记录输出到 `evidence/effect-ledger.json`，与三份正式成果同一版本。`clauses` 每条至少：

- `id`：稳定唯一的子句编号；`source`/`source_location`：原件、章节/控件/表行或确认消息；`atomic_claim`：原始意图的精准摘要；
- `scope`：`active` 本期有效、`excluded` 本期排除、`superseded` 被较新有效决定替代、`unresolved` 当前未知、`dependency` 上层依赖；
- `authority`/`authority_location`：对排除、替代的有效裁定证据（不是仅引用生成者旧报告）；
- `current_expected`：**仅 active** 写本期行为结果，必须指向 `model_refs` 或明确的 `unknown_refs`；
- `unknown_refs`：无法裁定的具体问题，尤其要注明问题所限制的条件分支。

**混合子句**必须分开写两条或多条：保留部分属于 `active`，被取消部分属于 `excluded`，不能在同一“本期有效”行的 current_expected/当前行为中再次描述取消操作。原文历史描述应留在 `atomic_claim` 或历史章节；不得被用作当前可执行行为。

范围变更发生时，找出直接受影响的子句，再沿以下依赖层传播：用户活动 → 条件/输出 → 事件 → 状态/关系 → 跨模块流 → 图/正文 → 正反例 → 未决事项 → 下游交接。不允许仅在报告开头更新范围。

## 三、三类真值不可混淆

- **正式业务事实**：有适用证据与有效裁定；允许得到确定的当前结果。
- **业务分析假设**：能用于寻找漏洞、提出反例，但没有来源前不得用“正确结果”“必然”等词输出为测试基线。
- **待确认的分支**：问题要包含条件、分歧的不同后果、资料查证过程与受影响对象；不能同时以肯定句放进当前结果。

对正反业务示例先核原文，再定“确定/候选/未知”。例如把某种表达判为“形式合规”，要具体核对形式规则，不能因为它看起来是个常见业务名词，就替产品/法规得出结论。评估输出不使用错误例子作为评判基准。

## 四、遗漏诊断只查真实证据

按以下两个方向各检查一次：

1. **原件 → 业务模型**：每项本期有效子句都能定位到条件、结果/失败/保持、事件、规则、用户活动或具体问题；只挂 ID 或出现关键词不算承接。
2. **业务模型 → 原件**：每个“应当/不能/自动/仅”结论能定位原始证据、正式裁定，或清楚标明“推导假设/待确认”。核查结论是否误用其他版本、其他角色、其他时间窗口的规则。

边缘辅助项也要有去向，但不要求和高风险核心流程使用同样长度的证明。存在未读页面、无法渲染、扫描全文未核、未观察后端等限制时，如实记录范围，不把部分检查宣称为全部检查。

## 五、从当前范围反扫已排除行为

对于已正式取消的业务，记录可识别的旧操作或结果标记到 `retired_markers`；调用 `scripts/effect_audit.py` 在当前业务预期以及本期来源 CSV 中搜索。它只能输出**可疑候选**：否定句、引用历史说明也可能命中，必须由分析者逐项核实或给出有来源的解释，不得把机器提示直接改造成删除原始历史证据。对确实出现在当前正向行为的项目必须移出本期模型并检查所有下游承接。
