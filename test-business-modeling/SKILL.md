## 项目知识协作入口

处理具体项目工作前，读取 [项目知识读取与沉淀协议](../clarify-before-testing/references/project-knowledge-protocol.md)。该协议覆盖已有项目背景、非 Skill 材料接收、测试线选择和公共能力复用；本阶段职责仍由下文规定。


# 业务理解

把业务资料转化为下游可以据以判断对错的业务基线：**谁为什么需要它，在什么条件下应发生什么，哪些事实应保持，凭什么判断完成，哪里仍不知道。**

先理解和质疑业务，再组织模型。对象、事件、状态等是保存理解的工具，不是分析起点或完成证明。正常操作、交互限制和复杂后台机制具有同等的保留义务；分析深度按业务风险调整，不以记录数或问题数验收。

## 入口与阶段边界

1. 读取适用项目说明、当前 Run、范围、资料基线和已有人工裁定；沿用既有 Router，不创建第二套阶段确认状态。
2. 用户只讨论 Skill、方案或理论时，不启动正式 Run。已有明确答案直接继承；规则变更核对来源、范围、版本及被替代内容。
3. 本阶段允许用具体例子、反例、决策表和原型走查发现业务问题；它们用于澄清含义，不编排 TP/TC、执行步骤、测试数据集或产品自动化测试。不因“用例阶段才用数据”而禁止用例子思考。
4. 产品尚未开发、接口或存储方案未定，不妨碍理解已承诺的业务。说明未来需要观察的业务事实，将物理观察入口待落实与业务规则未定分别处理。

## 三份正式产物

```text
deliverables/01-business-understanding.md
deliverables/01-business-understanding-review.md
internal/business/business-model.json
```

主报告沿用户任务讲清背景、总览、关键规则、分支、结果、限制和文末问题；有多个主要链路时附总流程图和关键链路/交接流程图；审查摘要保存来源承接、实际审查及修订记录；JSON 保存稳定机制和追溯。三者同版本、同事实。已有工作记录可继续使用，不为新格式重做台账。

正文、图和问题使用中文业务名称，来源显示文档名、章节和定位；内部编号留在追踪层。组织报告前读 [人工呈现指南](references/human-readable-reporting.md)。HTML 仅按用户需要提供，生成后实际渲染检查。

## 机制完整性加固说明（3.1）

本版新增 [业务机制承接与防退化门禁](references/mechanism-integrity-gate.md)。它嵌入原有五环节：来源逐项核对、事件六问与生命周期的有类型连接、真实存在的并存事实、旧版有效机制回归及修订后独立复核。**必须在相关环节实际打开并执行，不得只读主 `SKILL.md` 就宣布完成。** 不新增工作流状态或替代人工确认。正式模型使用 `schema_version: "3.1"`；历史 3.0 只能检查，不能直接签新基线。

## 继承与效果改造（3.3，基于 10/09—3.2-alpha 全版本）

先读 [跨版本继承与回归](references/version-regression.md)。**旧版有效能力不可静默删除**：逐控件原型探索、来源发现与效力、用户任务/CAP、对象状态关系生命周期、事件六问、输入载体、证明边界、独立 Reviewer、澄清同步，均仍执行。继续使用 3.1 的模型合同，不以追加新字段取代既有机制。

新增两项必须在实际执行中完成的工作：

- [有效业务事实基线](references/effective-source-baseline.md)：原始条款要拆成能独立成立的有效子句，分别记录**本期有效/正式排除/替代/未决/上游依赖**。取消一项流程时，其正向效果不得留在另一条“本期有效”的分析里；历史原文可留作来源证据。
- [业务长链路与交叉变化推演](references/end-to-end-simulation.md)：从用户任务出发逐段推到成功、首次失败、最后允许一次失败、停止、重复、重新进入、旧新版本并存及下游消费的相关终态。按真实证据区分确定结果与待确认，不通过发明技术实现填空。

**不能拿熟悉的危险源或 AI 工作台故障做通用硬编码**。与 3.2-alpha 的正反条件辨别方法合用时，所有决定性“正确预期”先回原始规则核对；不确定的示例只能用于提问，不能作为事实或测试基线。

为减少又一次“主报告正确、细节把旧需求复活”的错误，正式候选除三份正式产物外，保留同版本来源/效果证据 `evidence/effect-ledger.json`；可复用已有来源跟踪并转换，**不得凭空补齐行数**。用 `scripts/effect_audit.py` 进行只读反查；脚本只能核实记录间显式矛盾和可疑标记，**不能证明语义完整，也不替代 Reviewer 和产品确认**。阅读参考文件是实际执行要求，不允许只改报告标题就宣称用过 3.3。

## 1. 确定业务目标与有效证据

开始分析前读 [业务发现与规则澄清](references/business-discovery.md) 第 1—3 节、[来源与效力](references/source-status.md)，并执行 [机制完整性门禁](references/mechanism-integrity-gate.md) A 节及 [有效业务事实基线](references/effective-source-baseline.md)。

- 查明谁使用、谁受结果影响、真实工作场景、本次变化及价值、系统与人工的责任边界。无法查明的背景如实留存，不编造业务目标或成功指标。
- 将范围分为直接交付、依赖查证和明确排除。本轮需求与交互完整读取；历史模块围绕“哪些事实会改变当前判断”定向查证。
- 从目录和现有总结定位原文；需求、原型、有效裁定、接口、历史用例及缺陷按各自证据性质使用。正文、表格、图和隐藏交互都可能携带规则。文件存在或提取成功不等于读完。
- 依赖查证保留提供方、维护方、使用条件、版本、变更影响和例外。新依赖继续追踪；更多细节不再改变当前判断时停止，或明确查不到的影响。既不通读整个项目，也不因缺少项目地图而假定无依赖。
- 新需求只替代其明确改变的规则。生效评审变更与人工裁定按实际效力处理；旧规则仍有效就继承。原型或当前实现不能自动覆盖正式承诺。
- 对范围内有效内容识别可分别成立或违反的业务要求，保留条件、例外、数量词、顺序、作用对象及结果。**同一原始条款含本期保留和正式取消时拆成独立子承诺，各自定效力**；不能在“本期有效”的行为预期内写回已取消的动作。早期可先记去向，交付前按来源条款→具体行为双向反查；不允许仅挂来源 ID 即视为覆盖，按 [门禁 A](references/mechanism-integrity-gate.md) 执行。

**完成条件**：业务目的与边界可解释；读取范围透明；重要依赖已查证或登记限制；有效要求没有因概括而消失。缺资料可以继续草稿分析，受影响部分保持未定。

## 2. 用任务、例子和反例澄清业务

读 [业务发现与规则澄清](references/business-discovery.md) 第 4—6 节，再按 [业务机制分析方法](references/business-modeling-method.md) 建立全景。

- 沿用户目标串起角色、输入、活动、决定性分流、最终结果和后续使用。反查真实存在的查询、编辑、重置、取消、预览等基础活动，不让主链遮住它们，也不凭常识新增功能。
- 解释易混概念、对象身份和归属；明确同名、同状态或同页面是否代表同一事实。区分用户动作、系统处理和外部协作。
- 对含歧义、多条件或高后果的规则，用具体业务例子及能区分不同理解的反例检验规则；简单清楚的规则不强制配例子。未知答案归入问题，例子不能替产品定规则。
- 多条件用条件—结果表，状态限制用状态—动作表，跨角色交接用流程/时序图，数量或内容差异用等价类和边界含义分析。按问题选工具，不为每个任务填全套模板。
- 从使用者、业务决策者、开发/运维等相关视角检查目的、约束和可判断性。模拟视角只能产生问题，不能冒充真实人员确认；需要人决定的事项集中澄清。

**完成条件**：基础活动有去向；重要概念含义一致；关键条件的不同取值或组合能解释结果差异，无法解释的已明确。交给建模的是经澄清的事实，不是功能标题。

## 3. 建模，并判断风险与验收依据

读 [业务机制分析方法](references/business-modeling-method.md)、[长链路及交叉变化推演](references/end-to-end-simulation.md)、[条件差异与可判别结果推演](references/outcome-discrimination.md)、[模型承载规范](references/business-model-schema.md) 和 [机制完整性门禁 B/C](references/mechanism-integrity-gate.md)；风险与质量分析按 [业务发现与规则澄清](references/business-discovery.md) 第 6—7 节。

- 对事件逐项核对：谁对什么做什么；允许与禁止条件；成功变化；应保持事实；失败最终事实；后续准入。**每个事件单独给出状态和关系的适用性判断 `mechanism_links`**：改变、只读/校验、明确不适用或待确认，变更/校验时连到具体 `SM/TR/REL` 及行为说明。不适用要给业务理由，不得全部留空；关联的迁移/关系无事件承接时按证据登记例外。
- **先澄清差异，再合并记录**。同一事件允许多个分支，但每个影响行为的条件要有对应结果、保持项或未知去向。只在名称、输入列表或来源引用中提到一个操作，不算解释了其行为。
- 共享规则可集中引用；合并后无法区分触发条件、结果或独立失败，就分别承载。不要把完整条件交给测试点或用例阶段重新推测。
- 按适用性查明输入形态和规模、配置生效、权限范围、异步完成、旧状态与并发、跨模块变更、存量及历史影响。**实际存在草稿/生效、旧/新请求、重试轮、授权变化等并存关系时单独推演**，说明每个事实的归属与版本隔离，不将多维并行事实误画成单一线性状态。查明业务允许的后果，不预设锁、队列、重试或全量回滚方案。
- 从业务损失、使用频率、变化范围、依赖复杂度和历史缺陷确定深入区域。有依据的性能、可用性、安全、兼容、数据保留等承诺同样进入模型；未量化且影响验收的才请求澄清。风险不能作为遗漏明确要求的理由。
- 对重要结果说明正确预期的来源、需要看到的事实、证据的证明范围及不足。跨位置比较对齐对象、任务、版本、范围和时间窗口；输出不稳定时区分必须满足的规则与需要样本评估的质量目标。
- **逐任务推演终态**：对关键业务链实际串起相邻事件和条件，明确正常完成、首次失败、最终失败、停止、重复、恢复及相关上游变化的去向。特别区分“同一请求的允许重试”和“用户发起的新请求”；只有确有依赖的时序变化才继续组合。
- **推演与已生效来源双向约束**：任何正反例声称某种输出合规或应失败，都需要在有效规则中找到足以区分它们的条件。原始来源无答案的例子改为待确认，而不是交给下游当标准答案。
- 用合理错误行为检查判断依据：若错误行为仍符合模型的成功条件，补查规则或补足事实；存在多种合理答案时保留问题。假设不冒充已发现缺陷。

**完成条件**：有效要求能定位到模型中的具体条件和行为，或有明确未决/排除依据；模型反向可追溯；重要结果可判断，不能判断的原因透明。业务差异已保留，不以模型数量和引用数量证明质量。

## 4. 独立审查与修订复核

审查者读 [完整性审查指南](references/requirements-completeness-review.md)，并执行 [机制完整性门禁 A—E](references/mechanism-integrity-gate.md)。若此次为版本优化，旧版有效机制须逐项登记“保留/等价改写/正式排除/待确认/缺失”，并依据当前范围判断，**不得按旧模型行数照搬或静默遗失**。按以下顺序实施。先用 [条件差异与可判别结果推演](references/outcome-discrimination.md) 检查关键并存事实与确定规则/未决问题是否矛盾，再从 [有效业务事实基线](references/effective-source-baseline.md) 反扫本期已排除子句是否出现在有效行为中：

1. 使用宿主支持的独立上下文。先提供有效原始来源、依赖依据、范围、版本、裁定和读取限制，让审查者留下自己的任务、规则及风险关注点；再提供候选报告和模型。候选文件即使可访问，也要求完成前一步后再读。
2. 从来源逐项检查业务要求是否仍在；从模型反查依据。十三个既有维度用于补查机制，不代替正常功能、交互与质量要求核对。
3. 对重点规则用例子重述“条件变了会怎样”；用可能的错误行为检查验收依据。引用、字数、字段非空及作者自评不能替代内容判断。
4. 记录来源、遗漏/错误位置、影响、处置依据和复核结果。核对有效子句的每一个“正确结果”是否真正符合原件；复合原始条款不能只凭一个引用整行放行。作者修订后，Reviewer 读取实际变化并复核受影响规则、图、问题及保持项。无发现如实说明检查范围，不编造发现。
5. 无独立上下文时继续自查、保存草稿并标明“独立审查未完成”；同一 Agent 换角色、脚本全绿或用户确认不能记作独立审查完成。

**完成条件**：已核对的来源范围和剩余限制可追溯；发现得到修订、有效保留或未决处置；修订有实际复核。基础全量核对与高风险深入检查分别说明，不把抽查结论扩展为全覆盖。

## 5. 澄清、同步与交接

- 能自行查明的先查。区分规则缺失、资料访问限制、实现选择、待试验事项及真正冲突；澄清可在分析过程中进行，不必等报告写完。
- **Grilling / Frontier 问询**：问题交代具体场景、已知规则与来源、缺口及不同决定的后果，并注明推荐口径是否有可靠依据。当前可回答事项集中；依赖前置答案的后置。编号 Q1/Q2… 便于确认，但不强制二选一，无依据时不推荐方案，不为了提问数量而提问。分轮沟通时末尾交代当前内容、进度、业务理解五环节位置与下一轮 Frontier；不重复已回答事项。
- 回复先区分正式裁定、纠错线索、获准临时口径、范围调整或阶段确认。按性质保留效力，**从变化决定逐项传播至有效子句及其权威依据、当前正确结果、规则、事件、状态、关系、流程、正文、图、正反例、问题与审查记录，并反查过期描述**；用户说“继续”不自动等于裁定业务规则。
- 交接重要规则分支、验收依据、风险和未决边界；完整追踪放审查附件/模型，主报告保留读懂业务所需内容。“后续建模具象化”不能作为已完成的终态。
- 正式交付前，阻断事项经查证、有效裁定、获准口径或明确范围调整处理；独立审查真实完成；三份产物一致。由既有 Router 取得并绑定人工确认后进入测试点设计。事实变化触发受影响复核及下游版本失效。

## 校验与完成判据

完整候选模型生成后运行；初始来源记录不要求提前通过终态合同：

```bash
python <skill_install_dir>/scripts/business_contract.py --input <run_dir>/internal/business/business-model.json --allow-waiting-confirmation
# 正式确认前再运行完整门禁
python <skill_install_dir>/scripts/business_contract.py --input <run_dir>/internal/business/business-model.json

# 同步核对来源效力/长链/结果：先候选后严格；脚本疑点需人工回原文裁定
python <skill_install_dir>/scripts/effect_audit.py --model <run_dir>/internal/business/business-model.json --ledger <run_dir>/evidence/effect-ledger.json
python <skill_install_dir>/scripts/effect_audit.py --model <run_dir>/internal/business/business-model.json --ledger <run_dir>/evidence/effect-ledger.json --strict
```

如已有当前有效范围追踪 CSV，第一次命令还须添加 `--active-csv <current_scope_csv>`；文件不存在时才省略，不要把路径占位符直接执行。正式交接须保证新脚本错误为零、所有风险标记经过来源查证与复核；不以工具清零替代语义审查。

分别报告结构校验结果、有效子句与业务结果的双向核对、重要业务链终态、来源读取限制、独立审查状态、人工确认状态。正式门禁必须使用 3.1 的 `mechanism_links`；3.0 仅允许 `--allow-legacy-schema` 进行旧数据检查且不可正式签核。脚本只检查其实现的结构、关联引用和局部一致性；**不会证明**规则完整、推导正确、来源表已实质审查或独立 Reviewer 真实发生。必须另附语义反查与审查记录。

业务理解达到交接条件，意味着：**另一位设计者能依据有效来源和模型解释每项范围内业务要求及其关键差异，知道怎样判断结果，且无需自行发明规则来填补交接缺口。**
