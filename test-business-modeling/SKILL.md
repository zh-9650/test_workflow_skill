# Test Business Modeling｜业务理解

## 1. 本阶段真正要完成什么

本阶段回答两个问题：

> **这个系统在当前测试范围内到底怎么运转？**

以及：

> **现有需求还缺哪些会改变业务结果、状态、关系、流程或范围的规则？**

所以业务理解不是“把 PRD 换一种说法”，而是：

```text
完整读取证据
→ 建立业务模型
→ 主动查漏补缺
→ 能查到的事实自己查
→ 真正需要人决定的问题集中整理
→ 用户批量回复
→ 更新正文、内部模型和审查摘要
→ 重新自审
→ 最终确认业务理解
```

本阶段不生成：
- 测试点；
- 测试用例；
- 具体边界值实例；
- 等价类代表值；
- 参数组合；
- 自动化执行步骤；
- 测试优先级。

---

## 2. 输入

优先读取当前任务真正相关的：

- PRD / 需求规格；
- 最新原型；
- 接口文档；
- 评审记录；
- 产品/业务补充说明；
- 必要技术方案；
- 必要源码；
- 当前系统页面/API；
- 用户本轮明确确认。

默认不继承其它项目或历史任务的规则。

如果同一结论存在冲突，先建立当前任务的证据优先级。常见顺序是：

```text
当前人工明确确认
> 当前正式需求基线
> 当前最新原型/评审结果
> 其它当前资料
> 历史资料
```

当前任务另有约定时，以当前约定为准。

---

## 3. 正式输出

必须同时产出：

```text
deliverables/01-business-understanding.md
deliverables/01-business-understanding-review.md
internal/business/business-model.json
```

其中：

- `01-business-understanding.md`：给测试人员阅读、讨论、确认的主文档；
- `01-business-understanding-review.md`：快速审查摘要；
- `business-model.json`：给后续测试点设计、结构校验和关联追踪使用，不要求用户阅读。

正式文档优先保证人能看懂。内部编号、枚举、机器字段不要直接倾倒到正文。

---

## 4. 先明确范围

记录：

```text
in_scope
dependency_scope
out_of_scope
```

- `in_scope`：本轮直接测试；
- `dependency_scope`：为了理解上下游需要读取，但不是本轮独立测试对象；
- `out_of_scope`：明确不测。

用户已经明确的范围不要重复询问。

---

## 5. 建立业务对象

识别真正承载业务事实的对象，不要把所有数据库表、Controller、Service 都当成业务对象。

每个核心对象至少理解：

- 它是做什么的；
- 稳定身份是什么；
- 改名后是否仍是同一对象；
- 关键字段和业务规则；
- 是否有状态；
- 与哪些对象存在业务关系；
- 删除后同名/同编号重建是否形成新实体。

---

## 6. 建立状态模型

业务存在状态时，不只列“有哪些状态”，还要说明：

- 从哪里进入这个状态；
- 可以执行什么动作；
- 合法迁移；
- 应阻断的迁移；
- 状态变化会影响哪些下游；
- 哪些关系保留、哪些只失效；
- 恢复后是否自动恢复原关系/能力。

多个独立状态维度不能混成一个状态字段。

每条重要状态迁移都要有来源状态和证据。

---

## 7. 建立关系生命周期

不能只写“对象 A 与对象 B 是 N:M”。

每种核心关系都要说明：

- 谁是事实来源；
- 从哪里建立；
- 从哪里修改；
- 谁只能查看不能维护；
- 上游改名后关系是否保持；
- 上游停用/异常时关系是删除、失效还是保留；
- 如何恢复；
- 从哪里解绑；
- 上游删除时是否阻断；
- 删除后旧关系是否可能复活。

每种关系都按：

```text
建立
修改
失效
恢复
解绑/删除
```

完整建模，并记录来源。

---

## 8. 建立核心业务事件

每个真正有业务意义的操作/事件至少说明：

- 从哪里触发；
- 谁执行；
- 前置条件；
- 输入；
- 成功后直接变化；
- 状态变化；
- 关系变化；
- 下游影响；
- 什么必须保持不变；
- 失败条件；
- 失败后最终应该留下什么业务事实。

尤其强制回答两件事：

```text
变了什么？
什么绝对不能被影响？
```

如果存在失败条件，却没有定义失败后的最终状态/数据/关系，不要自行补答案；先查证据，仍无法确定则形成待确认问题。

每个核心业务事件都要记录来源状态和证据。

---

## 9. 建立业务不变量

把跨多个操作都必须成立的长期规则单独记录，例如：

- 某种关系只能在唯一入口维护；
- 当前配置变化不得改写历史事实；
- 失效不等于删除关系；
- 跨作用域对象不能建立关系；
- 派生数据不能被下游直接维护。

不要把“看起来合理”的猜测写成不变量。

---

## 10. 建立主流程、分支和恢复链

按真实业务需要建模：

- 正常主流程；
- 多分支流程；
- 中断/取消；
- 回退/撤回；
- 重试；
- 异步失败；
- 修复后恢复；
- 跨模块数据流；
- 当前事实与历史事实分离；
- 上游中途修改对下游的影响。

不要为了“看起来复杂”制造系统不存在的流程。

每条核心流程也要保留来源。

---

## 11. 规则来源怎么标

重要业务规则和关键推导使用：

```text
CONFIRMED
DERIVED
TEST_BASELINE
IMPLEMENTATION_DETAIL
```

含义：

### CONFIRMED
正式需求、评审、当前原型或人工明确确认直接支持。

### DERIVED
不是原文直接写明，但可以由已确认事实稳定推导。
必须说明由什么推导而来。

### TEST_BASELINE
资料没有完全定义，但用户明确允许测试暂按某口径推进。
必须标明这是临时测试口径，不得伪装成正式产品规则。

### IMPLEMENTATION_DETAIL
不改变业务结果的技术细节，例如错误码、存储方式、日志落点等。
可以延后到执行设计或实现核对阶段。

真正未确定、且不同答案会改变业务结果的内容，不要先写成规则，放到“待确认问题与建议”。

---

## 12. 主动做需求完整性检查

完成第一轮业务理解后，必须再做一轮需求完整性检查。

不能因为“PRD 已经写了支持某动作”就默认相关行为都定义完整。

按适用性检查：

- 创建 / 编辑 / 删除；
- 状态迁移；
- 关系生命周期；
- 失败后数据一致性；
- 异常修复与恢复；
- 当前配置与历史事实；
- 权限/作用域；
- 异步、重试、重复请求；
- 长流程分支、中断、回退；
- 跨模块上下游影响；
- 并发和旧页面/旧状态提交；
- 唯一值与删除后复用；
- 主数据、关系、统计、索引等一致性。

这只是检查树，不是固定问题模板。当前业务不存在的机制标记“不适用”，并说明原因。

内部必须生成 `requirements_completeness_review`，每个维度只能是：

```text
已定义
已形成待确认问题
当前不适用
```

不能用空白或一句“已检查”代替。

详细规范：

```text
references/requirements-completeness-review.md
```

---

## 13. 先查事实，再提出问题

发现缺口时先判断：

### 可以查到的事实
从当前资料、接口、源码、页面或已有确认中继续查，不拿来问用户。

### 需要人决定的业务规则
不同答案会改变业务结果、状态、关系、流程、范围或后续测试预期，才进入待确认问题。

### 不改变业务结果的技术细节
保留在非阻塞问题中，不阻塞业务理解收口。

不要因为需求文件看起来正式，就默认它一定完整、一定没有矛盾。

---

## 14. 待确认问题如何写

所有当前已经能够讨论的问题**集中放在 `01-business-understanding.md` 末尾**，用户一次性批量回复。

每个业务问题至少写清：

- 编号；
- 问题；
- 为什么要确认；
- 已核对的证据；
- 可选处理方式；
- 每种方案的业务影响；
- 建议方案；
- 推荐原因；
- 会影响哪些状态、关系、流程或范围；
- 当前状态。

推荐只是建议，不会自动变成正式规则。

用户可以这样批量回复：

```text
Q-001：选 B
Q-002：按建议
Q-003：本期不做
Q-004：产品暂未确认，先保留
```

收到回复后必须：

```text
更新业务理解正文
→ 更新规则/状态/关系/事件/流程
→ 更新 business-model.json
→ 更新审查摘要
→ 重新做需求完整性检查
→ 重新自审
→ 刷新仍待确认问题
```

有依赖的问题可以标注依赖前置结论，等前置答案回来后再刷新，不要求用户一次把逻辑上还没成立的问题全部回答。

---

## 15. 给测试人员看的业务理解文档

`deliverables/01-business-understanding.md` 推荐结构：

```markdown
# 业务理解

## 1. 本轮范围
## 2. 整体业务怎么运转
## 3. 模块 / 业务对象 A
### 它是做什么的
### 关键字段与业务规则
### 状态及状态变化
### 与其它对象的关系
### 主要业务操作
### 失败时应留下什么事实
### 对下游的影响 / 什么不应变化

## 4. 模块 / 业务对象 B ...

## N. 主流程 / 分支 / 异常 / 恢复流程
## N+1. 关键业务不变量
## N+2. 已确认规则与来源说明
## N+3. 待确认问题与建议
## N+4. 非阻塞问题 / 实现问题
## N+5. 本轮确认结果
## N+6. 本轮总结
```

状态模型、关系生命周期、事件表内部可以很完整，但正式文档只展示人工判断真正需要的内容，不要把大量内部编号直接倒给用户。

---

## 16. 业务理解审查摘要

`deliverables/01-business-understanding-review.md` 至少说明：

- 当前范围是否完整；
- 核心业务对象；
- 关键状态；
- 关键关系及生命周期；
- 核心主流程 / 跨模块链；
- 需求完整性检查发现了什么；
- 当前会影响业务结果的待确认问题数量；
- 非阻塞业务 / 实现 / 界面 / 外部依赖问题数量；
- 本轮自审发现并修正了什么；
- 建议人工重点检查的业务问题；
- 当前是否建议进入测试点设计；如果还存在影响业务结果的问题，明确写“先完成问题确认”。

## 17. 内部结构化模型

生成：

```text
internal/business/business-model.json
```

详细结构见：

```text
references/business-model-schema.md
references/source-status.md
references/requirements-completeness-review.md
```

核心业务事实必须能追到证据或明确推导来源。

---

## 18. 强制自审

至少检查：

### 范围
- 是否漏模块；
- 是否错误纳入范围外内容；
- 当前资料是否登记完整。

### 业务对象
- 核心对象是否齐全；
- 是否把纯技术表误当业务对象；
- 稳定身份是否清楚。

### 状态
- 合法迁移是否清楚；
- 关键阻断/非法迁移是否清楚；
- 多状态维度是否混用。

### 关系
- 是否只写了 1:N/N:M 而没有生命周期；
- 建立/修改/失效/恢复/解绑/删除保护是否有定义；
- 关系事实来源是否明确。

### 业务事件
- 核心操作是否齐全；
- 直接变化是否明确；
- 下游影响是否追踪；
- “不应变化”是否明确；
- 有失败条件时是否定义失败后的最终事实。

### 业务不变量
- 长期规则是否单独建模；
- 是否把猜测伪装成正式规则。

### 流程
- 是否只有正常主线；
- 中断、重试、恢复、部分成功是否按适用性分析；
- 跨模块链是否完整。

### 需求完整性
- 所有通用检查维度是否有结果；
- 适用项是否指向证据/模型或待确认问题；
- 不适用项是否说明原因；
- 是否存在“没检查，所以默认没问题”的空白。

### 来源
- 关键状态迁移、关系、业务事件、流程、规则、不变量是否有来源；
- DERIVED 是否有推导来源；
- TEST_BASELINE 是否明确只是测试暂定口径。

### 待确认问题
- 能查的事实是否已经自己查过；
- 业务问题是否有证据、方案、影响和建议；
- 是否把未确认规则偷偷写进正文当成正式结论。

### 人工文档同步
- 主文档、审查摘要、内部模型是否在同一轮更新；
- 文档末尾的问题清单是否与内部模型一致。

---

## 19. 人工确认与进入下一阶段条件

业务理解要区分两个状态：

1. **内容已自审，等待问题回复**：模型和文档已经整理完整，但仍有会改变业务结果的待确认问题；此时不能进入测试点设计；
2. **问题已处理，等待最终确认**：影响业务结果的问题已经解决，正文、审查摘要和内部模型已同步更新并重新自审。

只有第二种状态下，用户最终确认当前业务理解后，才能进入测试点设计。

人工确认只由流程状态统一记录，不在 `business-model.json` 中再保存第二套确认布尔值。

非阻塞实现/UI/外部依赖问题可以保留，不要求为了进入下一阶段而全部消失。

---

## 20. 人工文档与内部数据同步

内部 JSON 使用 `presentation_sync` 记录：

- 主业务理解文档已更新；
- 审查摘要已更新；
- 待确认问题已同步；
- 正文与结构化模型一致性已检查。

最终确认时，流程同时绑定：

- `01-business-understanding.md`；
- `01-business-understanding-review.md`；
- `business-model.json`。

任一文件后续变化，都需要重新审查。

---

## 21. 结构校验

自审阶段可运行：

```bash
python test-business-modeling/scripts/business_contract.py \
  --input internal/business/business-model.json \
  --allow-waiting-confirmation
```

最终确认前运行：

```bash
python test-business-modeling/scripts/business_contract.py \
  --input internal/business/business-model.json
```

最终确认前必须保证：

- 业务模型结构完整；
- 需求完整性检查完成；
- 关键业务事实有来源；
- 会改变业务结果的待确认问题已经解决；
- 人工文档与内部模型同步检查通过。
