# 人工审查与集中确认规范

适用于业务理解、测试点、测试用例三个阶段。

## 1. 先查证，再提问

需求文档、原型、接口、源码、页面现状和评审记录都是证据，但“文档里写了”不等于“需求一定完整”。

提出问题前先判断：

- **可以查到的事实**：先从当前任务资料、接口、源码、页面或已有确认中查证，不拿来询问用户；
- **需要人决定的业务规则**：不同答案会改变业务结果、状态、关系、范围或后续测试预期，才进入待确认问题；
- **实现细节**：不改变业务结果的错误码、日志位置、底层存储等，保留但不阻塞业务理解；
- **上游缺口**：在测试点或测试用例阶段发现业务结果本身不明确，必须返回上游补充，不能在当前阶段自行决定。

## 2. 问题集中放在文档末尾

默认不采用“一次一个问题”的聊天方式。

每个阶段完成初稿和自审后，把当前已经能够讨论的问题一次性放到正式文档末尾。用户可以批量回复，例如：

```text
Q-001：选 B
Q-002：按建议方案
Q-003：本期不做
Q-004：产品暂未确认，先保留
```

收到回复后：

```text
更新正式文档
→ 更新结构化数据
→ 更新受影响的状态/关系/流程/测试点/用例
→ 更新审查摘要
→ 重新自审
→ 刷新仍未解决的问题
```

只有新问题确实依赖上一轮答案、当前无法合理讨论时，才在下一轮补充。

## 3. 每个待确认问题要让人能直接判断

至少说明：

- 编号；
- 问题；
- 为什么需要确认；
- 已经核对过哪些证据；
- 可选处理方式；
- 每种方式会产生什么业务/测试影响；
- 建议方案；
- 推荐原因；
- 影响范围；
- 当前状态。

建议只是建议，不能自动变成正式需求。

用户明确确认后才能记为已确认规则；如果用户只允许测试暂按某方案推进，应记录为“测试暂定口径”，不能伪装成产品正式规则。

## 4. 有依赖的问题怎么处理

- 当前已经能回答的问题正常列出；
- 真正依赖前置结论、当前无法成立的问题，标记“依赖 Q-xxx，前置问题确认后刷新”；
- 不要求用户一次回答逻辑上还没有成立的问题。

## 5. 三个阶段分别确认什么

### 业务理解

重点确认：
- 需求资料缺失的业务规则；
- 证据冲突；
- 状态、关系、删除、恢复、历史、并发、上下游联动等未定义行为；
- 范围和业务边界。

这是需求查漏补缺最重的一层。

### 测试点

重点确认：
- 覆盖范围；
- 风险优先级；
- 少量确有争议的测试点颗粒度；
- 是否需要额外完整流程覆盖。

发现业务结果不明确时，返回业务理解。

### 测试用例

重点确认：
- 用例展开是否合理；
- 参数化、组合和长流程是否过度或不足；
- 是否有当前无法构造的测试条件。

发现独立测试机制缺失时，返回测试点设计；发现业务结果不明确时，返回业务理解。

## 6. “自审完成”和“最终确认”不是一回事

每个阶段都可能存在：

```text
内容已自审，但仍有待确认问题
```

这种状态允许保存产物和问题清单，但不能进入下一阶段。

只有问题处理到满足进入下一阶段的条件，并且正文、审查摘要和内部结构化数据重新同步、自审后，才提交用户最终确认。

人工确认状态只由流程状态统一记录，不在业务模型、测试点 JSON、测试用例 JSON 里重复保存另一份确认布尔值。

## 7. 给用户看的文档只用正常测试语言

正式文档、审查摘要和聊天说明不输出内部调度或控制术语。

优先使用：

```text
当前阶段
待确认问题
已自审
等待问题回复
问题已处理，等待最终确认
已确认
需要重新确认
进入下一阶段条件
结构校验
恢复信息
```

内部代码可以保留技术字段，但不能把内部实现词直接倾倒进人工交付物。

## 8. 人工文档和内部数据必须同步

每个阶段最终确认时同时绑定：

- 主文档；
- 审查摘要；
- 内部结构化数据。

任何一个文件在确认后发生变化，都需要重新审查受影响内容。
