# 危险源填报质量智能体：测试点 1.1 → 用例 1.1 代表性示例

> **性质**：用于检验新方法能否写出有辨别力的数据、步骤、Oracle 的业务样例；**不是**拿到危险源新的 3.3 与 1.1 正式结果后生成的全量用例，也没有操作实际环境。来源为本次讨论已经确认的需求边界；未获得真实受控服务能力的地方明确列为执行依赖。

## 示例 A：技术协议失败与业务“无法判定”不允许混淆

**已知业务原则**：合法完整协议下 D1 无法判定是业务结果 U1；缺块/非法枚举/交叉矛盾等不完整或非法协议属技术失败，第一次失败可按现行规则有限自动重试一次，第二次失败不得形成业务 U1。

**测试目标**：`TP-示意-协议-有效性`；不同判定分支应由测试点 1.1 中的正式分支 ID 替代，以下仅展示两次独立实例的组织方式。

| 独立场景 | 决定性数据准备 | 业务步骤（含核对点） | 可判定预期与证据 | 状态 |
|---|---|---|---|---|
| TC-HAZ-ILL-01：合法 U1 | 一条经业务确认、上下文不足的危险源描述；同一次尝试生成**完整五块、有效枚举、合法交叉字段**且 D1=无法判定 | ① 数字员工中选择已授权能力并输入该描述；② 提交并记录请求身份；③ 检查输出协议/业务结果 | U1 必须来自完整合法协议，不能来自截断的 STEP1；需原始有效规则及解析结果证据；不要强制已经取消的人工复核面板出现 | 设计样例；U1 最终引导文案仍需上游确认 |
| TC-HAZ-ILL-02：非法协议两轮失败 | 同一合法输入；配置有证据的受控响应，第一次缺 STEP2、第二次仍缺 STEP2，其他信息不应拼接补全 | ① 提交并确认进入首轮；② 控制首轮返回缺块，检查没有有效结果；③ 观察仅发生约定次数重试；④ 第二次仍缺块，检查最终失败 | 最终为技术失败/incomplete（按正式口径 U2），不得从残存 STEP1 推出业务 U1，不得把两轮片段拼成五块；证据需轮次/完整解析/最终结果链 | `needs_environment_capability`：真实受控响应入口与可观察轮次能力尚未核实 |

**为什么要拆为两个独立执行场景**：两条行为的原因和预期结果不同。只有一条“查看无法判定文案”的测试不能区分正确 U1 与错当 U1 的技术失败。

**数据准备者还需要的具体说明**：如何稳定构造合法 U1 的真实上下文和合法五块协议；如何在测试环境可控地产生两轮完整/不完整响应；如何证明两次是同一业务请求的两次尝试；测试隔离避免污染其他运行。缺此能力不得标为“可自动执行”。

## 示例 B：提示词编辑期间的在途/新请求隔离

**已知业务原则**：编辑候选稿不立即生效；正式发布后对下一次新提问生效；已开始请求保持当时有效提示词快照。

| 步骤 | 必要操作与中间检查 | 业务断言 |
|---|---|---|
| S1 | 有权限的管理者将 V1 发布有效，保留 V1 可核验标识 | V1 为当前有效版本；草稿状态与正式有效状态不混淆 |
| S2 | 有权限的用户启动请求 A，并使 A 处于可控制的处理中间点 | A 的提示词快照/调用证据绑定 V1 |
| S3 | 管理者编辑 V2 候选，未发布；另一用户提交请求 B | B 仍消费当前已发布的 V1；若无法独立观测实际消费则标注依赖 |
| S4 | 按正式流程审批发布 V2，A 尚未结束；用户再提交 C | C 消费已发布 V2；A 不得中途被 V2 覆盖；同一版本号界面回显不能代替真实调用证据 |
| S5 | A/B/C 各自结束，查看结果归属 | 三个请求之间不互串；失败/停止路径需额外独立实例，不能用本正常链替代 |

**执行依赖**：能控制请求 A 处理中时点；能读取提示词实际调用版本证据；能安全创建 V1/V2 的候选与发布。本例为用例设计基准，不是已经有这些功能接口或具备测试钩子的证明。
