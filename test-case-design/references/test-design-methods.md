# 测试设计方法｜真正推导，不贴标签

## 1. 等价类

适用：

- 输入有有效/无效类别；
- 枚举；
- 类型；
- 格式；
- 数据范围可以分类。

先推导：

```text
有效类
无效类
每类为什么行为相同
代表值
```

不要先写 Case 再标 method=等价类。

## 2. 边界值

适用：

- 长度；
- 数量；
- 金额；
- 时间；
- 日期；
- 阈值；
- 分页；
- 容量。

至少：

```text
边界本身
边界内相邻值
边界外相邻值
```

边界必须来自业务规则，而不是随便选 0/1/999。

## 3. 判定表

多个条件共同决定动作/结果时使用。

先整理：

- 条件；
- 条件取值；
- 动作/结果；
- 有意义组合；
- 无效组合；
- 可合并组合。

再生成测试点。

## 4. 因果关系

适合：

- 条件依赖；
- 互斥；
- 与/或；
- 一个原因影响多个结果；
- 规则难以直接看成判定表。

不要求画图。

内部明确：

```text
Cause
Constraint
Effect
```

有价值时再转判定表。

## 5. 状态迁移

适合：

- 对象有明确状态；
- 不同状态允许操作不同；
- 操作改变后续行为。

至少分析：

- 合法迁移；
- 非法迁移；
- 重复操作；
- 关键路径；
- 失败状态；
- 恢复状态；
- 终止状态。

## 6. 场景法 / 业务流程法

适合：

- 多步骤；
- 多角色；
- 跨模块；
- 一个业务结果需要多次操作。

必须覆盖：

- 主成功流；
- 关键分支；
- 关键失败点；
- 中断后继续；
- 回退；
- 重试；
- 跨模块数据衔接；
- 长链路组合异常。

这是避免 CRUD 机械化最重要的方法之一。

## 7. 组合测试

适合参数多、全组合成本过高。

先识别：

- 参数；
- 参数值；
- 强交互组合；
- 业务必须覆盖组合。

Pairwise 不能替代明确高风险组合。

## 8. 错误推测

来源：

- 历史缺陷；
- 当前实现机制；
- 易错技术点；
- 测试经验；
- 当前系统曾出现的问题。

把具体 Bug 抽象成失败机制。

例如不要复制：

> “旧系统切换部门岗位没清空。”

而要抽象：

> “上游选择变化后，下游依赖项可能未重新计算/清空。”

## 9. 风险覆盖补充

完成主要方法推导后，再检查：

### 权限和数据范围
不同角色、组织、租户、所有者。

### 计算/统计
不能只拿 UI 和同一个聚合 API 互证；需要尽量独立的输入/计算依据。

### 数据一致性
详情、列表、统计、下游对象、历史。

### 上下游影响
修改、删除、停用、配置变化。

### 多入口
UI/API/导入/批量是否保持同一规则。

### 并发 / 幂等
重复操作、同时操作、重复请求。

### 恢复
失败、重试、重新进入。

### 异步
处理中、成功、失败、超时、最终一致性。

### 时间
边界时刻、周期、生效、到期。

### 外部依赖
外部异常是否破坏本地状态。

## 10. 三类典型业务

### 简单文本字段

```text
名称 1~50
```

等价类 + 边界值即可。

### 角色启停

状态迁移 + 判定表 + 场景法，再检查权限和下游影响。

### 跨模块生成流程

以场景法为主，再在各环节按需加入边界、状态、判定表、错误推测。

不要把整个链拆成互不相干的 CRUD。
