# 完整独立测试用例（1.2 强制交付）

## 一个用例就是一个业务场景，不再拼装

正式产物按 **独立验证场景** 展开，而不是“若干主项 + 若干执行实例”供人自行匹配。旧内部 `case_templates/execution_instances` 只为原 Contract 和模型复用存在，永远不是给测试人员的交接正本。最终一条用例至少包括：稳定编号、目标与上游分支、执行主体/权限、相关对象/归属/关联、初始状态、决定性数据取值、可证实的准备途径、准备完成核验、业务步骤、各关键步骤预期、最终业务判定依据、证据和隔离清理。

数据组若改变可独立记录的结果，**必须在 `full.md` 出现新的独立完整一行**，在 `case_cards.md` 出现新的完整卡片，在 `standalone-cases.json` 出现新的完整记录。冒烟里同样重复准备、步骤与预期。不允许写“参照 T-01 的步骤”“沿用上一条用例的数据”。

## 数据准备要求具体到什么程度

- **谁**：账号类型、角色/权限、租户作用域；禁止写“有效账号”。
- **对象和数据关系**：实体标识、主从归属、绑定与数据交互影响；多个对象需说清相同/不同 ID 和必要的相互状态。
- **初始事实**：哪个对象在哪个状态、哪个配置在生效、哪个请求在途；需要冲突则明确冲突双方。
- **决定性值**：边界值、协议块位置、异常种类、文件性质、模型响应类型或版本组合；使目标错误实现与正确实现能表现不同。未知真实值时写可供数据准备者挑选的约束，不臆造用户系统的 ID。
- **来源和建立方式**：仅记录已知可用的 UI/API/预置夹具/人工协调渠道及必要步骤；未知的受控故障注入/内部表结构需标 `needs_environment_capability`。
- **就绪核验**：用独立于“造数成功提示”的回读或真实状态证明数据满足条件。
- **隔离/恢复**：独立可复测，先执行失败不得影响其他用例；若确实为“故障修复后复测”，须在此条用例自己的数据准备中建立修复前/后可核验状态，不依赖先跑另一条用例 PASS。

本阶段**不执行造数，也不要求写实际造数脚本**。未知条件不能用空话补齐；该用例候选阻断，写明欠缺数据能力/Oracle。

## 步骤与预期怎么写

1. 步骤按业务动作和状态改变拆；每个可影响后续行为的重要动作应有中间断言。
2. 最终判定必须能区分目标错误实现和正确实现；Toast/HTTP200/模型自我说明不够时要独立回读/追踪真实来源。
3. 动作与预期同一行序关联；不能“操作一堆，最后统一检查正确”。
4. AI/RAG 的协议、权限、版本、工具调用/检索来源可以确定性断言；质量与效果需明确评测集、Rubric、统计样本和已批准的阈值；缺时只做候选。
5. 如前后两个业务结果互斥、失败发生位置不同、状态/角色不同或错误会互相遮蔽，拆成不同完整用例。

## 真正的签收标准

**任意抽取 1 条用例，不读别的用例、源模板或实例数组**，陌生数据准备者能独立说明要准备什么和如何核验，执行者能依次操作并知道每步检查什么，审查者能指出实际什么结果算 Fail，后续能独立清理及复测。若缺少一项，不称“可执行用例”。

## 一套事实、四个同步正本

内部 `test-cases.json` 仍兼容旧 Contract；从它使用 `standalone_cases.py` 生成：

- `deliverables/full.md`：每行 7 列，**完整**数据准备、步骤、预期、状态（入库可读版）。
- `deliverables/case_cards.md`：每条展开的完整卡片，便于审查。
- `deliverables/smoke.md`：已选冒烟同样完整，不能只引用 ID。
- `deliverables/standalone-cases.json`：供后续数据准备与执行的**单个案例一条完整机器正本**，不需拼主项和实例。

`run_checks.py` 正式模式必须验证四份正本与同一个源文件完全相同，否则拒绝交接；同样必须跑旧 Contract、TP 1.1 分支校验。脚本负责结构/同步，业务语义仍需独立源核对，真实可执行性以环境试跑为证据。
