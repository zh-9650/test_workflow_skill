# 用例生成的具体方法：场景、数据、操作、Oracle

## 1. 先做场景矩阵，再决定拆分/合并

每个候选场景记录 `TP-ID + 分支ID/变体 + 初始状态/主体 + 触发动作与关键顺序 + 变化与保持事实 + 目标错误 + 可观察 Oracle + 环境依赖`。

独立出例：业务预期不同；初始状态/故障注入点不同；互斥条件需要独立 Pass/Fail；前一故障会遮蔽后一行为；角色/租户/版本归属不同且可能独立错。允许参数化：执行骨架与核心断言同一机制且数据可独立执行、独立判定，每个数据组有自己的 `execution_instance_id`。综合链：多点连接产生不同于单点的错误（断裂、污染、迟到覆盖、假完成）；综合链不取代关键原子实例。

## 2. 设计方法要输出推导痕迹，不是标签

- 输入域：枚举有效/非法类、边界值及必要的归一化差异；必须能解释选了哪些代表值和未测范围。
- 多条件规则：判定表/因果关系；对独立变化造成不同结果的列分别承接；不能随意用 pairwise 代替互斥、约束或高风险三因素组合。
- 状态与关系：合法/非法转移、重复、失效与恢复；检查动作后未改变的事实与下游可用性。
- 长链：真实用户任务从入口开始，包含至少实际有价值的中间状态核对、成功/失败/停止/重试/再次提交终态以及配置/角色的时序交织（在来源有效时）。
- AI/RAG：确定性事实（可用来源、权限、检索范围、调用归属、工具成功、协议解析）与概率性质量（语义正确性、召回质量、忠实性）分开设计 Oracle。

## 3. 数据契约不是“准备合法数据”

每个执行实例至少说明：执行主体及授权、对象与真实业务标识之间的关系、初始状态/当前配置版本、**决定性取值/文件/依赖状态**、通过哪些合法入口建立或获取、准备成功的独立核查、隔离与恢复要求。如果环境目前不能造出故障/中间状态，写明缺哪种可控能力，不编造 SQL 表、Mock、CSS 选择器或后端接口。

例如危险源协议缺块：不只是“准备错误响应”，而应指定缺失哪个已确认的协议块、其他块完整且合法、首轮与重试轮怎样独立构造、用什么可控响应模拟或测试钩子保证达到该状态，如何检查最终只能技术失败，绝不误当业务 U1。若没有受控入口，状态为 `needs_environment_capability`，而不是完成可执行。

## 4. 步骤深度由业务动作和断言边界决定

每步写 `谁在什么状态 → 从什么证据已知的入口做什么 → 输入哪份可辨别数据 → 此步之后应观察到什么`。下列边界必须独立检查（适用时）：权限决策、关键数据写入、对象/版本绑定、异步开始/完成、跨模块交接、失败后保持、停止/恢复、最终有效结果。不是每点击一次都占一步；也不是所有用例定长 5 步。

旧 Contract 的 `assertions[].checkpoint` 只能为 `step|intermediate|final`，前两者需绑定真实步骤 `step_id`。`execution_instances[].expected_assertion_ids` 必须逐执行实例明确承接。中间断言失败会遮蔽后续断言时，增加独立原子场景以保证故障隔离。

## 5. Oracle（判定依据）从何而来

- `exact`：已确认的具体状态/数值/枚举/文案。
- `rule_or_invariant`：同租户作用域、请求版本快照、失败不修改对象等已确认规则。
- `reference`：可信参考实现、独立计算或固定基准。
- `metamorphic`：经业务确认的输入变形关系与输出性质。
- `statistical_or_rubric`：AI 非确定性质量应具有评测集/样本方式、明确可复核评分标准和批准的验收阈值；阈值未知不能冒充已确定。
- `pending_oracle`：尚缺可信判定标准；仅允许在候选文档保留，不允许称“设计已就绪”。

**假成功挑战**：`Toast 成功、HTTP 200、文档上传完成、前端可用、模型给绿色结论` 都可能不是实际业务成功。找能区分正确和错误实现的观察，例如独立读回、下游真实可调用、版本哈希/真正消费、跨请求结果归属或恢复后的对象关联。没有独立观察能力就标明依赖，不能写“查看日志即可”。

## 6. 可执行性纸面预演（不是执行通过）

让未参与设计的数据准备者/执行者只看 Case，尝试回答：准备哪几个对象、怎么保证状态满足、按什么顺序操作、在哪里采集证据、什么结果判 PASS/FAIL、失败后如何复测和清理。回答不出来则为设计缺口；环境没有入口则登记阻断，不捏造“已执行”。
