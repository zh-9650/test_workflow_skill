# Test Case Design｜测试用例设计（1.2 完整独立用例交付终版）

> **版本：2026-10-22 1.1；继承 2026-10-09 实际用例 Skill，不改变原始 Case Contract 2.0.0。** 必须先读 `references/handoff-business33-point11.md`、`references/scenario-data-oracle-steps.md`、`references/review-regression.md`。此 Skill 是唯一用例设计阶段，不新开子 Agent 和新 Skill。

## 1. 本阶段只解决什么

本阶段只回答：

> **用哪些具体执行场景，才能证明已确认的测试机制正确？**

输入：

```text
业务理解3.3（区分已确认/候选/未决）
+
测试点1.1（包含决定性分支/必须保留的变体）
+
同版本 business-model.json / test-points.json
+
3.3 effect-ledger.json（如实际存在）+ 生效裁定 + 原始证据（查实际入口、控制/观察能力，并可反查上游错误；不得自行更改正式业务预期）
```

输出：

```text
deliverables/full.md（**每行一条完整用例**，含完整数据准备与逐步预期的 7 列表格；兼容入库）
deliverables/case_cards.md（**逐条完整用例卡片**，阅读与审阅正本，与 full.md 同源自动生成）
deliverables/smoke.md（**每条仍自包含**，四列表格，不是只列编号）
deliverables/03-test-case-review.md（审查、未决与冒烟提取理由）
deliverables/standalone-cases.json（**交给数据准备/测试执行的唯一机器用例正本**，每个案例一条完整记录）
internal/design/test-cases.json（只用于沿用 10/09 Contract 的兼容建模，内部可复用模板，但**不是**测试人员/执行者需要手工拼接的交付产物）
```

测试人员主要阅读全量用例 `full.md`、冒烟用例 `smoke.md` 与审查摘要；JSON 用于结构校验、执行调度和关联追踪。`full.md`、`case_cards.md`、`smoke.md` 和 `standalone-cases.json` 必须由 `scripts/standalone_cases.py` 从同一内部数据**确定性生成并核对**，不存在四份各自手工维护的用例事实。最终入库前仍需按公司实际导入规则检查格式，不把“生成成功”误认为已经同步入库。

## 2. 不允许再做什么

测试用例阶段不能：

- 重新定义产品业务规则；
- 发现测试点缺失后偷偷把新机制塞进用例；
- 因为旧流程习惯机械执行“1 测试点 = 1 用例”；
- 用“结果正确、符合预期、按实际实现”等模糊预期；
- 为了数量把相同机制重复拆成大量用例。

如果发现：

- **业务结果不明确** → 返回业务理解；
- **缺了独立测试机制** → 返回测试点设计；
- **只是具体执行数据、边界、组合不足** → 在本阶段展开。

## 2.5 必须执行的九步方法（先推导，后填 Case 表）

**S0 输入与范围核对**：定位 3.3 有效事实与 1.1 分支的同一版本。区分 active、excluded、superseded、unresolved、dependency；未决规则不写死 Expected。缺变更传播或上游重要门禁尚未完成时，相关部分标候选，不得报“全量确认”。

**S1 场景双通道发现**：业务驱动（逐 TP、分支、原型操作、关键用户任务）+ 具体故障驱动（错作用域、半写入、错误版本、异步假完成、迟到结果污染、权限越权等）。故障只能是假设挑战，不能伪称线上 Bug。

**S2 选择与执行设计方法**：按条件类型实际推导等价类/边界、判定表、状态迁移、关系生命周期、连续流程、时序、约束组合、变形/属性；不得只是列方法名字。必要时先绘制一小张场景矩阵：`分支→决定条件→动作时序→正确结果/保持事实→错误实现→Oracle`。

**S3 颗粒度决策**：最终 `1 个独立业务场景 = 1 条完整用例`；一个 TP 可生成多条用例，一个用例也可在不遮蔽错误时有多个 TP 断言。**互斥结果、不同起始状态、不同失败注入点或独立判定分支**必须分别出例；同骨架参数化可以节约内部表达，但每一组都要展开成一条拥有完整数据、步骤和预期的正式用例。绝不交付“一个主项+若干执行实例”供用户自己组装。

**S4 数据契约**：写明执行主体及授权、对象及 ID/归属、初始状态、决定性输入/版本、准备途径、数据准备完成时的核查方法、隔离与清理；无实际接口/环境时只写真实可支持的候选入口和能力依赖，不编造 SQL、选择器、Mock。

**S5 操作与中间断言**：按有业务意义的操作和状态/关系/异步/交接边界拆步骤；不能只有“打开页面、操作、预期成功”。关键前置成功、失败保持、继续执行、旧/新请求隔离应写可以观察的检查点。断言绑定具体 `step_id` 或最终结果，必须能区分目标错误。

**S6 Oracle 选择与隔离**：区分 exact、rule_or_invariant、reference、metamorphic、statistical_or_rubric、pending_oracle。不得仅以 Toast、HTTP 200、模型自己说“通过”当 Oracle。AI/RAG 确定性协议/权限/来源事实与概率性答案质量分别设计；后者缺认可的评分标准/阈值时标 `needs_oracle`，不得正式放行。

**S7 完整用例展开 + 下游纸面预演**：先运行 `scripts/standalone_cases.py` 将每个独立场景展开为一个完整用例，生成 `full.md`、`case_cards.md`、`smoke.md`、`standalone-cases.json`；**只看这条用例**，数据准备者和执行者必须能知道需要哪种对象、从哪一个已经证实的入口准备、如何确定就绪、按哪个步骤执行、每一步看什么、怎么判定和恢复。前一条用例成功不是合法的本条前置；必须能在本条数据准备中独立建立前提。不满足则局部返工。

**S8 双向审查与 Grilling**：反查上游每个确定分支、必需变体、正反判别、长链终态/中断/交错是否有 `完整用例 → 断言 → Oracle`；抽查原始 PRD/原型。业务预期未知回 3.3，独立测试点缺失回 1.1。运行旧 Contract、分支门禁及**最终交付文件同源核验**，修改任意实例/条件后必须重生成所有正本。末尾集中列待确认与推荐。

**每轮固定在文末说明**：当前讨论内容、进度、测试流程阶段位置、下一轮 Frontier 问题。即使用户要求自动推进，也只在真正缺产品裁定时提问；不能以一句“已覆盖”跳过来源与分支反查。

**适配要求**：`case_quality_design` 的字段、完整例子与两道实际门禁见 `references/handoff-business33-point11.md`、`examples/sample-test-cases-11.json`、`scripts/branch_case_audit.py`。保留旧 `schema_version=2.0.0` 的主结构与证据策略。旧版测试点允许只读迁移检查，但不得假装它已满足 1.1 分支覆盖。**1.2 正式交付还必须验证每条独立用例的自包含数据/步骤/结果，以及文档和独立 JSON 与源模型逐字同源**。

## 3. 从测试点到执行场景

对每个测试点先判断需要哪种展开方式。

### 3.1 字段/输入规则

优先考虑：
- 等价类；
- 边界值；
- 必填/非法值；
- 同一规则下的关键代表数据。

不要把多个边界值再变成多个测试点；在内部可以参数化，但**最终每个独立数据场景均形成一条完整用例**并能分别记录结果。

### 3.2 多条件业务规则

使用判定表或等价的规则组合，覆盖真正会产生不同业务结果的条件组合。

不要暴力做完整笛卡尔积；根据风险选择必要组合。

### 3.3 状态迁移

覆盖：
- 合法迁移；
- 关键非法/应阻断迁移；
- 重复操作；
- 状态变化后的下游影响。

### 3.4 关系生命周期

根据业务理解覆盖：
- 建立；
- 修改；
- 失效；
- 恢复；
- 解绑；
- 删除保护。

### 3.5 失败后数据一致性

失败类用例不能只有“出现错误提示”。按适用性验证：
- 操作是否失败；
- 主对象是否保持正确状态；
- 数据是否部分写入；
- 关系是否出现半更新；
- 下游是否被错误影响。

### 3.6 恢复

恢复类用例至少体现：

```text
制造/进入异常
→ 修复
→ 重新进入或重试
→ 恢复验证
→ 标识/关系/历史连续性验证
```

### 3.7 并发和旧状态

必须明确：
- 参与者；
- 同步点；
- 提交顺序；
- 最终业务事实。

不能只写“两个用户同时操作”。

### 3.8 完整业务流程

完整流程用例不能只验证最后结果。至少设置两个中间检查点，验证关键状态、关系或下游事实。

## 4. 最终“用例就是用例”：唯一交付粒度

### 4.1 用例的定义

**用例是能独立准备、独立执行、独立检查、独立记结果和复测的一条完整业务场景。** 不是“主项”、不是“执行实例”、也不是要求人将两个文件合并的占位符。

每条必须自包含：
1. 用例 ID / 标题 / 目标 / P0–P2 优先级、对应 TP 和业务分支；
2. 执行主体（身份/角色/权限）、业务对象、数据归属和关联、必要的初始化状态；
3. **具体数据要求**（决定性特征、样例值/数据集、需要区别错误实现的构造），**准备途径**（已知可用的 UI/API/夹具等，未知的注明依赖）、**准备就绪核验**（从哪里独立回读什么事实）；
4. 有顺序的操作入口与步骤；每个关键状态/数据/关系变化处设置具体预期和证据，不只写“符合预期”；
5. 最终 Oracle（来自正式规则/不变量/参考基准/可信评分，标注不能判定的原因）及恢复、清理要求；
6. 不依赖上一条测试用例 PASS/准备成功；需要的前置数据在本条自己可重新建立。

### 4.2 只允许内部复用，不允许对外交付碎片

为兼容旧 `case_contract.py`，内部仍保留 `case_templates` 与 `execution_instances`，但它们只是**技术性中间表示**。**所有使用者只看 `full.md`、`case_cards.md`、`smoke.md` 或 `standalone-cases.json`；这些文件中每一条都必须完整展开**。

内部一个模板有三个不同数据组时，正式全量文档必须出现**三条各有独立编号、数据、步骤、预期和清理的用例**；不能通过“见主项 T-01”省略任何内容。`standalone-cases.json` 是后续数据准备/执行的机器交接正本，旧 `test-cases.json` 只用于兼容验证，不给下游作为“待拼装用例”。

若不同实例都需要调用同一个公共数据夹具，可复用**夹具实现**，但每条用例必须说明该夹具如何准备本条对象和如何独立核验；不能依赖其他用例先运行。

### 4.3 数据准备边界

**本阶段负责写清数据准备要求，不承诺数据已经创建。** 必须明确角色、对象 ID 关系、数据值/文件内容、初始状态、准备方式和就绪证据；若没有稳定制造异常的环境能力，将本条标为 `needs_environment_capability`，不能空写“准备一个异常数据”也不能猜测接口或 SQL。后续数据准备 Skill 再根据此独立用例实际创建并验证。

详细结构与负例见 `references/standalone-case-delivery.md`。

## 5. 多个测试点何时允许由同一条完整用例验证

内部复用操作骨架可以，但**只有同时满足以下条件，才允许同一条完整用例验证多个 TP**：

- 前置环境相同；
- 主操作骨架相同；
- 一次执行能自然观察所有预期；
- 每个测试点都有自己的断言；
- 前面某个断言失败，不会导致后面的机制无法继续观察。

以下类型默认不应随意合并：

- 失败后数据一致性；
- 恢复；
- 并发；
- 旧状态提交；
- 跨作用域/租户隔离；
- 复杂长流程。

如果确实合并，必须说明原因，并检查是否存在“前序失败导致后续检查无法执行”的问题。

---

## 6. 每个测试点必须有真实断言

一条**完整用例**声称关联多个测试点，不等于真的覆盖。

内部数据必须做到：

```text
断言 A → 测试点 1
断言 B → 测试点 2
断言 C → 测试点 3
```

每个测试点至少有：
- 一个明确可观察断言；
- 一条完整用例承接（参数化内部实例必须各自生成独立完整用例）。

---

## 7. 参数化 ≠ 合并交付用例

- 为减少作者重复劳动，可在内部复用一套相同动作骨架；
- **最终一组独立可判定的数据条件，就是一条完整用例**：用例编号、数据值、准备方法、步骤、各断言、清理都实际展开；
- 同一场景的没有独立验证意义的数据变化不要无端拆几十条；不同结果/独立失败风险必须单独出例；
- 同一个用例不能包含互斥数据却只给一个 Pass/Fail；不能通过引用另一个“主项”交付；
- 运行时每条用例独立记录结果，未运行时只能记录设计状态。

---

## 8. 本阶段发现新问题时怎么处理

测试用例阶段允许确认的问题主要是：

- 某类用例展开是否过多/不足；
- 多个测试点是否适合共用一个执行骨架；
- 某些测试条件当前是否可构造；
- 某些执行数据是否需要保留为单独场景。

如果问题会改变业务预期，返回业务理解。

如果发现缺了独立测试机制，返回测试点设计。

当前可一起确认的问题集中放到 `03-test-case-review.md` 末尾，每题至少说明：

- 问题；
- 为什么要确认；
- 已核对的业务理解、测试点或原始证据；
- 可选处理方式及每种方式的影响；
- 建议方案；
- 推荐原因；
- 影响范围；
- 当前状态。

用户可一次性批量回复。收到回复后更新正式用例、审查摘要和内部 JSON，再重新自审。

## 9. 给测试人员看与入库的正本用例（完整用例正本）

用例设计阶段同时输出两份原生符合公司规范的 Markdown 正本：

### 9.1 全量测试用例（`deliverables/full.md`）

采用标准 7 列，每**行即一条真正完整的用例**，不得把数据/步骤留在另一张主项或执行实例表：

```text
| 用例ID | 用例标题 | 前置条件 | 测试步骤 | 预期结果 | 优先级 | 疑问/备注 |
```

- 可另附公共环境说明/AI执行指南/经证实的异常造数方式，但这些**不得代替每条用例自己的完整数据准备**。本机生成脚本默认仅生成真实完整用例，不凭空补公共测试环境。
- 每行前置条件格内自包含全部数据准备、就绪核验、隔离要求；测试步骤格内自包含该用例的动作；预期格内按步骤给出真实可判定的业务事实与依据；不需要对照其他表拼装；
- 自动生成同源 `case_cards.md`（逐条完整卡片）和 `standalone-cases.json`（下游数据准备/执行的唯一机器交接正本）；
- 文档末尾固定增加 `待确认问题与建议`（没有问题时明确写“当前无需要人工确认的测试用例设计问题”）。
- `03-test-cases.md` 如需兼容，必须是由同一份完整用例正本复制/别名生成的内容，不得维护第二个版本。

### 9.2 提测准入门禁冒烟用例（`deliverables/smoke.md`）

**内置动态冒烟提取算法（依据 ISTQB 广度优先原则与公司《开发提测标准 V1.1》）**：

- **提取原则**：以提测准入的关键入口、主链、最危险的阻断与权限/归属来选冒烟；历史 10%～30% 只作为观察参考，不作为硬性通过条件。若项目没有某类业务（如删除/租户），不得为满足五类覆盖捏造功能。
- **绝不能只看 P0**：提测门禁不仅包含主干 Happy Path，还必须覆盖关键的强阻断与权限防护（即使在全量中定为 P1 也必须纳入）。
- **五大必选覆盖维度（Broad & Shallow）**：
  1. **界面与入口广度全覆盖**：每个功能菜单、子 Tab 页至少 1 条打开用例，保证无白屏、无 500、表格正常初始化；
  2. **核心业务对象生命周期闭环**：关键实体的创建落库、详情/编辑、状态流转（启用/停用）、删除二次确认；
  3. **关键业务强阻断校验**：核心必填项拦截、唯一性重名冲突拦截、前置依赖缺失时的强阻断提示（防止脏数据污染数据库）；
  4. **角色权限与租户隔离**：只读角色隐藏写操作、非管理员无越权菜单、多租户横向越权拦截；
  5. **端到端核心业务闭环**：贯穿上下游的 1~2 条最具业务价值的核心 Happy Path。
- **四大坚决排除雷区**：
  - ❌ 坚决不进 Mock 5xx / 超时 / 断网（属于健壮性专项，开发提测环境无法快速构造）；
  - ❌ 坚决不进手工修改数据库注入非法值的用例；
  - ❌ 坚决不进超长字符、emoji 截断、XSS/SQL 注入等极值边界用例；
  - ❌ 坚决不进高成本的并发竞态与大数据量性能测试。
- **表格与编制说明标准**：
  - 表头采用标准 4 列：`| 用例ID | 测试步骤 | 预期结果 | 提取来源 |`；
  - 顶部说明准入规则和提取依据；本表的每条冒烟用例必须把完整数据准备、步骤、预期重复展开，不能只列用例编号或让人跳转全量文档。

## 10. 测试用例审查摘要

`deliverables/03-test-case-review.md` 至少说明：

- **最终独立完整用例数**（正式交付 `full.md` 行数应与 `standalone-cases.json` 记录数一致）；内部模板数量仅是维护统计，不代表交付用例；
- P0/P1/P2 分布；
- 内部参数化复用的场景数，以及这些场景是否都已展开为独立完整用例；
- **冒烟用例提取分析**：冒烟总条数/场景数、占全量比例（只报告不硬判）、适用业务准入维度的覆盖矩阵与选择理由；
- 所有测试点是否都有实际执行场景和断言；
- 暂不能执行或仍待确认的项；
- 建议人工重点审查的典型用例。

## 11. 强制自审

至少检查：

- 所有确认测试点是否有实际执行场景；
- 每个测试点是否有独立断言；
- 边界/等价类/判定组合是否真的展开；
- 多测试点共用一个用例时是否互相遮蔽；
- 失败类是否检查失败后的最终事实；
- 恢复类是否检查修复后的连续性；
- 并发类是否有同步点、提交顺序和最终事实；
- 完整流程是否有中间检查点；
- 预期是否具体可观察；
- 是否偷偷新增没有测试点的业务机制；
- 是否存在重复用例或无意义拆分；
- 是否有未确认业务问题被伪装成正式预期。

## 12. 人工确认与进入下一阶段条件

自审与结构校验后分三种情况：

1. **发现业务预期不清**：返回业务理解；
2. **发现测试机制缺失**：返回测试点设计；
3. **只有用例层问题或无问题**：集中列出当前问题，用户批量回复后更新文档和内部数据，再重新自审。

只有不存在未处理的阻塞问题后，才提交用户最终确认。

人工确认状态只由流程状态统一记录，不在 `test-cases.json` 里再保存一份确认布尔值。

## 13. 人工文档与内部数据同步

`full.md`、`case_cards.md`、`smoke.md`、`standalone-cases.json` 必须由同一脚本在同一轮确定性生成并验证；`03-test-case-review.md` 须同步审查状态、未决问题与真实独立用例数。

旧内部 JSON 的 `presentation_sync` 不能替代真实文件核对。最终确认时，流程同时绑定：

- 正式独立完整用例文档、用例卡片、冒烟文档及完整用例 JSON；
- 用例审查摘要；
- 内部结构化数据。

其中任一文件后续变化，都需要重新审查。

## 13.5 原有分支门禁 + 完整用例交付第三道门禁

保留旧 `case_contract.py` 原样，**必须在其通过后**执行本期 `branch_case_audit.py` 或 `run_checks.py`。**同时必须跑完整用例展开与最终正本核验；只跑旧 Contract 和分支审查不等于可以交付。**对 1.1 每个已确定分支，记录 `branch_instances`（独立实例与断言）、`variation_reviews`（必需变体）、`discriminator_case_reviews`（正反两侧）、`path_case_reviews`（关键链）、`instance_readiness`（数据与 Oracle）；中间模型只放必要审计信息，不再复制完整业务事实。

正式交付示例：

```bash
python test-case-design/scripts/run_checks.py \
  --input internal/design/test-cases.json \

```

有明确未决问题时，加 `--candidate` 并**标注结果不可当正式签核**；旧版 1.0 测试点仅用 `--legacy-input` 排查兼容，输出也不得报符合 1.1 分支要求。两道检查只能找引用/遗漏/数据和 Oracle 说明的形式缺陷，真正语义仍必须回原始有效需求、独立审查与后期执行验证。

## 15. 终版生成与同步命令（必须执行）

在跑正式检查之前先从 `internal/design/test-cases.json` 展开：

```bash
python test-case-design/scripts/standalone_cases.py \
  --input internal/design/test-cases.json \
  --full deliverables/full.md \
  --cards deliverables/case_cards.md \
  --smoke deliverables/smoke.md \
  --smoke-ids evidence/smoke-case-ids.json \
  --standalone-json deliverables/standalone-cases.json
```

`smoke-case-ids.json` 仅存选中的**完整独立用例 ID**，不能用模板 ID 代替。所有生成用例的前置数据、步骤和预期已在自己的用例中展开。生成后用同样参数加 `--verify` 校验文件未被手工改出不一致内容，再运行第 13.5 节的正式门禁。若缺少真实造数手段/Oracle，相关用例保持候选，不能把缺口从最终文档中删掉以伪装 ready。

**最终成功标准**：测试者任意抽取一条完整用例，不读取任何其他用例，就知道准备什么、如何核验准备就绪、做什么、每一步怎么看、最终以什么为准及如何独立复测。
