# Test Case Design｜测试用例设计

## 1. 本阶段只解决什么

本阶段只回答：

> **用哪些具体执行场景，才能证明已确认的测试机制正确？**

输入：

```text
已人工确认的业务理解
+
已人工确认的测试点
+
同版本 business-model.json / test-points.json
+
当前范围原始证据（只用于补执行入口、字段名和交互细节，不重新解释业务预期）
```

输出：

```text
deliverables/03-test-cases.md
deliverables/03-test-case-review.md
internal/design/test-cases.json
```

测试人员主要阅读两个 Markdown；JSON 用于结构校验、执行调度和关联追踪。

---

## 2. 不允许再做什么

测试用例阶段不能：

- 重新定义产品业务规则；
- 发现测试点缺失后偷偷把新机制塞进用例；
- 因为旧流程习惯机械执行“1 测试点 = 1 用例”；
- 用“结果正确、符合预期、按实际实现”等模糊预期；
- 为了数量把相同机制重复拆成大量用例。

如果发现：

- **业务结果不明确** → 返回业务理解；
- **缺了独立测试机制** → 返回测试点设计；
- **只是具体执行数据、边界、组合不足** → 在本阶段展开。

---

## 3. 从测试点到执行场景

对每个测试点先判断需要哪种展开方式。

### 3.1 字段/输入规则

优先考虑：
- 等价类；
- 边界值；
- 必填/非法值；
- 同一规则下的关键代表数据。

不要把多个边界值再变成多个测试点；在用例里形成独立执行数据组，并能分别记录结果。

### 3.2 多条件业务规则

使用判定表或等价的规则组合，覆盖真正会产生不同业务结果的条件组合。

不要暴力做完整笛卡尔积；根据风险选择必要组合。

### 3.3 状态迁移

覆盖：
- 合法迁移；
- 关键非法/应阻断迁移；
- 重复操作；
- 状态变化后的下游影响。

### 3.4 关系生命周期

根据业务理解覆盖：
- 建立；
- 修改；
- 失效；
- 恢复；
- 解绑；
- 删除保护。

### 3.5 失败后数据一致性

失败类用例不能只有“出现错误提示”。按适用性验证：
- 操作是否失败；
- 主对象是否保持正确状态；
- 数据是否部分写入；
- 关系是否出现半更新；
- 下游是否被错误影响。

### 3.6 恢复

恢复类用例至少体现：

```text
制造/进入异常
→ 修复
→ 重新进入或重试
→ 恢复验证
→ 标识/关系/历史连续性验证
```

### 3.7 并发和旧状态

必须明确：
- 参与者；
- 同步点；
- 提交顺序；
- 最终业务事实。

不能只写“两个用户同时操作”。

### 3.8 完整业务流程

完整流程用例不能只验证最后结果。至少设置两个中间检查点，验证关键状态、关系或下游事实。

---

## 4. 用例主项与执行数据组

为了既保持可读性，又能独立记录结果，本阶段区分：

### 4.1 用例主项

描述可复用的执行骨架：
- 标题；
- 优先级；
- 前置条件；
- 主步骤；
- 断言；
- 关联测试点。

### 4.2 执行数据组

表示一次可以独立执行、独立记录 Pass/Fail 的具体场景：
- 数据变化；
- 参数组合；
- 边界值；
- 角色/对象实例；
- 本次实际要检查的断言。

例如一个长度规则可以是一个用例主项 + 多个执行数据组，而不是一个大用例里塞多个数据后只记录一个结果。

---

## 5. 多个测试点何时允许共用一个用例主项

只有同时满足以下条件才允许合并：

- 前置环境相同；
- 主操作骨架相同；
- 一次执行能自然观察所有预期；
- 每个测试点都有自己的断言；
- 前面某个断言失败，不会导致后面的机制无法继续观察。

以下类型默认不应随意合并：

- 失败后数据一致性；
- 恢复；
- 并发；
- 旧状态提交；
- 跨作用域/租户隔离；
- 复杂长流程。

如果确实合并，必须说明原因，并检查是否存在“前序失败导致后续检查无法执行”的问题。

---

## 6. 每个测试点必须有真实断言

一个用例声称关联多个测试点，不等于真的覆盖。

内部数据必须做到：

```text
断言 A → 测试点 1
断言 B → 测试点 2
断言 C → 测试点 3
```

每个测试点至少有：
- 一个明确可观察断言；
- 一个实际执行数据组承接。

---

## 7. 参数化用例

如果一个用例主项包含多组执行数据：

- 至少 2 组才算参数化；
- 每组数据有独立编号；
- 每组数据有独立预期；
- 每组数据有独立结果记录；
- 不允许把多个不同业务机制伪装成“参数化”。

---

## 8. 本阶段发现新问题时怎么处理

测试用例阶段允许确认的问题主要是：

- 某类用例展开是否过多/不足；
- 多个测试点是否适合共用一个执行骨架；
- 某些测试条件当前是否可构造；
- 某些执行数据是否需要保留为单独场景。

如果问题会改变业务预期，返回业务理解。

如果发现缺了独立测试机制，返回测试点设计。

当前可一起确认的问题集中放到 `03-test-cases.md` 末尾，每题至少说明：

- 问题；
- 为什么要确认；
- 已核对的业务理解、测试点或原始证据；
- 可选处理方式及每种方式的影响；
- 建议方案；
- 推荐原因；
- 影响范围；
- 当前状态。

用户可一次性批量回复。收到回复后更新正式用例、审查摘要和内部 JSON，再重新自审。

---

## 9. 给测试人员看的正式用例

`deliverables/03-test-cases.md` 以正常测试语言展示：

```text
用例编号
标题
优先级
关联测试点
前置条件
测试数据/执行数据组
步骤
逐步预期
```

不要把内部展开策略、映射编号、机器字段直接堆在正文里。

对参数化场景，用测试人员能直接执行的表格展示每个数据组及独立预期。

对长流程，用步骤和中间检查点明确展示，不要只写最终结果。

文档末尾固定增加：

```text
待确认问题与建议
```

没有问题也明确写“当前无需要人工确认的测试用例设计问题”。

---

## 10. 测试用例审查摘要

`deliverables/03-test-case-review.md` 至少说明：

- 用例主项数量；
- 实际执行场景/数据组数量；
- P0/P1/P2；
- 参数化用例数量；
- 多测试点共用执行骨架的数量；
- 失败后数据一致性、恢复、并发、旧状态、完整流程等专项数量；
- 所有测试点是否都有实际执行场景和断言；
- 哪些测试点被展开成多个执行场景，以及原因；
- 哪些测试点共用一个用例主项，以及为什么不会互相遮蔽；
- 暂不能执行或仍待确认的项；
- 需要返回测试点/业务理解补充的问题；
- 建议人工重点审查的典型用例。

---

## 11. 强制自审

至少检查：

- 所有确认测试点是否有实际执行场景；
- 每个测试点是否有独立断言；
- 边界/等价类/判定组合是否真的展开；
- 多测试点共用一个用例时是否互相遮蔽；
- 失败类是否检查失败后的最终事实；
- 恢复类是否检查修复后的连续性；
- 并发类是否有同步点、提交顺序和最终事实；
- 完整流程是否有中间检查点；
- 预期是否具体可观察；
- 是否偷偷新增没有测试点的业务机制；
- 是否存在重复用例或无意义拆分；
- 是否有未确认业务问题被伪装成正式预期。

---

## 12. 人工确认与进入下一阶段条件

自审与结构校验后分三种情况：

1. **发现业务预期不清**：返回业务理解；
2. **发现测试机制缺失**：返回测试点设计；
3. **只有用例层问题或无问题**：集中列出当前问题，用户批量回复后更新文档和内部数据，再重新自审。

只有不存在未处理的阻塞问题后，才提交用户最终确认。

人工确认状态只由流程状态统一记录，不在 `test-cases.json` 里再保存一份确认布尔值。

---

## 13. 人工文档与内部数据同步

`03-test-cases.md`、`03-test-case-review.md` 和 `test-cases.json` 必须在同一轮修改中同步更新。

内部 JSON 使用 `presentation_sync` 记录同步检查。最终确认时，流程同时绑定：

- 正式用例文档；
- 用例审查摘要；
- 内部结构化数据。

其中任一文件后续变化，都需要重新审查。

---

## 14. 结构校验

自审阶段可运行：

```bash
python test-case-design/scripts/case_contract.py \
  --input internal/design/test-cases.json \
  --points internal/design/test-points.json \
  --business internal/business/business-model.json \
  --allow-waiting-confirmation
```

最终确认前运行：

```bash
python test-case-design/scripts/case_contract.py \
  --input internal/design/test-cases.json \
  --points internal/design/test-points.json \
  --business internal/business/business-model.json
```

最终确认前必须保证：

- 业务理解、测试点和用例版本一致；
- 每个测试点都经过用例展开；
- 每个测试点都有实际执行场景；
- 每个测试点都有明确断言；
- 参数化用例有多个独立数据组；
- 多测试点共用用例时已检查互相遮蔽；
- 失败、恢复、并发、完整流程结构满足要求；
- 没有未处理的上游问题；
- 人工文档与内部数据同步检查通过。
