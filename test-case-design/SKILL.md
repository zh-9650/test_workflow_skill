# Test Case Design｜测试点与测试用例设计

本 Skill 包含两个明确子阶段：

```text
已确认业务理解
↓
测试点设计
↓
AI 自审
↓
人工确认测试点
↓
测试用例生成
↓
AI 自审
↓
人工确认测试用例
```

**测试点没有确认，不进入正式用例生成。**

---

# 1. 输入边界

必须读取：

- 已确认 `01-business-understanding.md`；
- 内部已确认业务模型/规则映射；
- 当前测试范围。

按需读取：

- PRD / 原型；
- 接口文档；
- 必要技术方案/源码；
- 历史缺陷，只作为错误推测来源。

如果发现业务理解里缺少一个会改变 Expected 的业务规则：

```text
返回 business-modeling
→ 补充
→ 自审
→ 确认受影响部分
```

禁止在测试点或用例里偷偷猜规则。

---

# 2. 测试设计技术与风险检查分开

核心测试设计技术：

1. 等价类；
2. 边界值；
3. 判定表；
4. 因果图；
5. 状态迁移；
6. 场景法 / 业务流程法；
7. 组合测试 / Pairwise；
8. 错误推测。

风险与覆盖检查视角：

- 权限和数据范围；
- 计算/统计；
- 数据一致性；
- 上下游影响；
- 多入口一致性；
- 并发；
- 重试；
- 幂等；
- 恢复；
- 异步任务；
- 时间；
- 外部依赖；
- 历史缺陷机制；
- UI/API 一致性（适用时）。

不要把这些风险视角伪装成“第九种测试方法”。

---

# 3. 测试点生成流程

```text
已确认业务理解
↓
按业务模块识别测试对象
↓
识别对象的业务特征
↓
选择真正适用的方法
↓
先做方法推导
↓
再形成测试点
↓
用风险覆盖视角补充
↓
检查状态、流程、联动、长链路异常
↓
去重和合并
↓
AI 自审
↓
人工确认
```

禁止：

```text
先写测试点
→ 再随便贴“边界值/判定表”标签
```

---

# 4. 八种方法怎么选

详细方法见：

`references/test-design-methods.md`

原则：

- 不是每个模块都用八种；
- 简单名称长度 1~50，等价类 + 边界值足够；
- 有状态才用状态迁移；
- 多条件共同决定结果才重点用判定表/因果关系；
- 多步骤、多角色、跨模块结果重点用场景法；
- 参数组合过大才考虑 Pairwise；
- 历史 Bug 要抽象失败机制，不照搬旧项目。

---

# 5. 测试点特别加强四类内容

## 5.1 状态变化

覆盖：

- 状态前；
- 操作中；
- 状态后；
- 非法状态操作；
- 重复操作；
- 失败状态；
- 恢复状态。

## 5.2 业务流程

检查：

- 前一步数据是否成为下一步前置；
- 中间一步失败；
- 跳过步骤；
- 重复步骤；
- 中途退出；
- 返回继续；
- 回退；
- 重试。

## 5.3 跨模块联动

每个高影响操作问：

> 这个变化会影响哪里？

尤其：

- 修改；
- 删除；
- 停用/启用；
- 迁移；
- 切换；
- 重新处理；
- 重新生成；
- 重新绑定；
- 修改配置。

## 5.4 长链路异常

不要只有：

```text
步骤1失败
步骤2失败
步骤3失败
```

还要考虑：

```text
前面成功
→ 中间选择分支A
→ 修改关键数据
→ 后面失败
→ 重新进入
→ 换分支B
→ 恢复/继续
```

---

# 6. 避免机械 CRUD

如果业务明显有规则、状态、流程、联动，而测试点只是：

```text
新增成功
编辑成功
删除成功
查询成功
新增失败
编辑失败
```

自审不通过。

测试点应体现：

- 为什么要测；
- 哪个规则/状态/流程/风险；
- 变化前后和上下游。

---

# 7. 正式测试点文档

```text
deliverables/02-test-points.md
```

按业务模块组织，不按测试方法组织整篇。

建议：

```markdown
# 测试点
## 1. 测试范围与设计说明
## 2. 项目管理
### 2.1 基础功能与业务规则
### 2.2 状态与流程
### 2.3 数据变化与联动
### 2.4 异常与特殊流程
## 3. 文档管理
...
## N. 跨模块业务流程
## N+1. 测试点统计与审查摘要
```

正式文档里“主要设计思路”只标记：

```text
等价类 / 边界值 / 判定表 / 状态迁移 / 场景法 ...
```

完整方法推导放：

```text
internal/design/test-design-analysis.md
```

# 8. 测试点生成后的强制自审

### 覆盖
- 每个业务模块是否有点；
- 关键规则是否覆盖；
- 状态是否覆盖；
- 核心业务流程是否覆盖；
- 跨模块联动是否覆盖；
- 关键数据变化是否覆盖；
- 长流程异常是否覆盖。

### 方法
- 是否根据业务特征选方法；
- 应该做边界分析的是否真的推导；
- 多条件是否做组合分析；
- 状态业务是否只做普通正反例；
- 长业务链是否用了场景法；
- 是否为了“八种方法”强行套方法。

### 质量
- 是否重复；
- 是否过度细碎；
- 是否一句话换对象复制；
- 是否没有验证价值；
- 是否把用例步骤拆成测试点。

### 风险
- 高影响操作是否充分；
- 删除/停用/迁移/切换/恢复；
- 历史易错机制；
- 跨模块链是否只有成功流。

发现问题先修，再审。

---

# 9. 测试点人工确认

不要把几百条测试点扔给用户一句“请确认”。

先给审查摘要：

- 总数量；
- 各模块数量；
- P0/P1/P2；
- 各方法使用情况；
- 跨模块流程数量；
- 长流程异常数量；
- 仍存在的不确定点。

建议用户重点审：

- P0；
- 跨模块主业务链；
- 状态转换；
- 复杂判定规则；
- 删除/迁移/停用/切换；
- 长流程异常；
- AI 自己不确定的点；
- 本次新增/修改需求。

普通 P1/P2 可按模块抽样。

用户抽样指出一类问题：

```text
扫描同模块/同类型
→ 批量修正
→ 重新自审
→ 再确认
```

---

# 10. 用例只能从已确认测试点生成

如果生成用例时发现：

- 新规则；
- 新场景；
- 新状态；
- 新联动；
- 原测试点遗漏；

不能悄悄加在 Case 里。

返回测试点层补充、审查、确认。

---

# 11. 正式用例：人看得懂，Agent 也能执行

机器字段放：

```text
internal/design/test-cases.json
```

正式：

```text
deliverables/03-test-cases.md
```

不要在正式用例里堆：

- source_ref；
- oracle_ref；
- digest；
- dependency_ref；
- internal coverage mapping。

---

# 12. 普通功能用例

结构至少包含：

- Case ID + 优先级 + 名称；
- 前置条件；
- 测试数据；
- 步骤；
- 每个关键步骤的可观察 Expected；
- 关联测试点。

避免：

- “进行相关操作”；
- “输入合法数据”；
- “结果正确”；
- “正常展示”；
- “符合规则”；
- “页面展示内容和状态都没有问题”等无具体可观测对象的泛义描述。

必须明确写出：
- 具体的断言目标对象（哪个输入框、按钮、表格列、提示条）；
- 确定的属性/状态（如：禁用、可见、高亮、状态变为‘已审核’）；
- 确切的数值、文案或返回码（如：提示‘保存成功’、列表显示 1 条数据、金额显示 100.00）。

---

# 13. 复杂业务链用例

多步骤、多角色、跨模块、多状态、长链路不要压成一行。

关键步骤都检查：

- 当前业务对象；
- 当前数据；
- 当前状态；
- 当前角色；
- 下游影响；
- 中间结果。

不要只在最后一步写一个“大而全”预期。

---

# 14. 用例生成后的强制自审

### 覆盖
- 所有已确认测试点是否有 Case；
- 是否错误合并导致验证目标丢失；
- 是否 Case 自己新增未经确认覆盖。

### 可执行性
- 前置是否足够；
- 测试数据是否明确；
- 每步是否包含可直接执行的具体动作；
- 是否存在 `{}`、`进行相关操作`、`输入合法数据` 这类不可执行占位；
- 是否缺关键导航。

### Expected
- 每个 Expected 是否有稳定 ID；
- 是否可观察（界面元素、接口响应、数据变动）；
- 是否可明确判断（有明确对象、确定属性、数值或文案）；
- 是否具体到业务结果；
- 是否存在 `页面正常展示`、`结果正确`、`符合规则`、`内容和状态都没有问题` 这类缺乏具体断言实体的模糊伪预期。

### 业务链
- 是否只有最终断言；
- 是否有中间关键状态；
- 跨模块数据是否验证；
- 中间失败是否有对应 Case；
- 恢复后状态是否验证。

### 重复
- 是否只换数据但目标一样；
- 是否应参数化/合并；
- 是否一条测试点生成过多低价值 Case。

### 可阅读性
- 测试人员第一次看能不能执行；
- 是否结构化到像 JSON；
- 是否一条过长却没有结构。

发现问题先改，再审。

---

# 15. 用例人工确认

自审通过后给摘要：

```text
总 Case
P0/P1/P2
普通功能 Case
业务链 Case
覆盖测试点 N/N
未覆盖
阻塞
```

存在未覆盖或阻塞必须主动说明。

用户确认后由 Router 绑定正式用例版本，才允许进入 `test-execution-planning`。
