# Test Case Design

## 1. 输入边界
只从已人工确认的业务理解生成测试点。若发现新规则/新场景/新状态/新联动，不在用例层偷偷补，返回上游补业务理解或测试点。

## 2. 选择并真正执行测试设计方法
按业务特征选择，不要求八种全用：
- 等价类：有效/无效类别、格式、枚举、类型。
- 边界值：长度、数量、时间、阈值等，至少边界、内邻、外邻。
- 判定表：多个条件共同决定结果。
- 因果图：复杂依赖、互斥、与/或，必要时内部转判定表。
- 状态迁移：合法/非法迁移、重复操作、失败/恢复/终止。
- 场景法/业务流程法：多步骤、多角色、跨模块、长链路；必须覆盖中断、回退、重试和组合异常。
- 组合测试：多参数高组合，保留明确高风险组合，不让 Pairwise 替代。
- 错误推测：历史缺陷和实现易错点需抽象成失败机制，不照搬旧项目 Bug。

## 3. 风险与覆盖检查视角
方法推导后再补：权限/数据范围、计算统计、数据一致性、上下游影响、多入口一致性、并发、重试、幂等、恢复、异步、时间、外部依赖、历史缺陷、UI/API 一致性。

## 4. 测试点
正式输出 `deliverables/02-test-points.md`，按业务模块组织而不是按方法组织。每点可写：ID、优先级、测试点、主要设计思路。
重点防止 CRUD 机械覆盖，必须检查状态、业务流程、跨模块联动和“多阶段+多分支”的长链路异常流。
完整方法推导放 `internal/design/test-design-analysis.md`。

测试点阶段单独使用 Contract 的 `mode=test-points`，此时只能要求业务理解已确认、测试点自审通过，不得要求测试用例已经存在。每个测试点必须有可读的 `test_point` 描述，不能只有 ID 和方法标签。

## 5. 测试点自审与确认
自审覆盖、方法适配、重复/碎片化、风险与联动。自审通过后给用户统计摘要，并建议重点审 P0、核心链路、状态转换、复杂规则、高影响操作、长流程异常和不确定点。用户指出一类问题时扫描同类问题并批量修正。
自审通过后先登记 `deliverables/02-test-points.md` 为 `test_points` Artifact，确认后再进入用例生成。

## 6. 测试用例
只有测试点确认后生成 `deliverables/03-test-cases.md`。
普通用例写：标题/P0-P2、前置条件、测试数据、步骤-操作-预期结果、关联测试点。复杂业务链用例用完整卡片，每个关键步骤检查当前数据、状态、下游影响和中间结果。
内部字段和追踪映射放 `internal/design/test-cases.json`。

用例阶段使用 `mode=test-cases` 或 `mode=full`，必须重新记录用例自审状态；发现新业务规则时返回上游，不得把它藏在用例里。

## 7. 用例自审
检查测试点 100% 承接、可执行性、测试数据明确、步骤不模糊、Expected 可观察、业务链中间断言、跨模块传递、异常恢复、重复和可阅读性。禁止“正常展示/结果正确/符合规则/按实际实现”类模糊 Expected。

## 8. 用例人工确认
自审通过后提供用例总数、P0/P1/P2、普通/业务链数量、测试点覆盖数、未覆盖/阻塞数，再请求确认。
确认前登记 `deliverables/03-test-cases.md` 为 `test_cases` Artifact；用户确认后才能进入 Execution Planning。

## 9. 方法参考
八类设计技术的真实推导结构与 Contract 要求见 `references/test-design-methods.md`；选择方法后必须生成对应内部推导，不允许仅写方法标签。
