# Coverage Types 机制覆盖分类规范

本规范定义测试点设计阶段使用的 18 类验证机制分类标签（Coverage Types）。

---

## 1. 定位纠偏：核对与打标工具，而非生成目录

> [!IMPORTANT]
> **核心原则**：
> 1. Coverage Types 是**事后核对、双向关联、缺口反查与统计分类**的维度体系，**绝不是批量自动生成测试点的枚举生成器**。
> 2. 严禁对着 18 个分类机械套用。必须从业务理解中的实际业务动作、规则与任务出发，推导出验证义务后，再按适用性打标。
> 3. 上游业务理解中的基础核心能力（CAP）用于全局索引与导航，进入本阶段后必须展开到实际业务事件、规则、状态机、实体关系与跨模块长流程，不能仅消费能力清单的标题。

---

## 2. 18 类法定覆盖机制清单

内部 `test-points.json` 中 `coverage_obligations[].type` 严格限制为以下 18 类枚举：

| Coverage Type | 机制含义 | 核心核对关注点 | 适用示例 |
|---|---|---|---|
| `event_behavior` | 业务事件的基本行为与准入 | 前置条件满足时的动作执行与直接业务产物 | 创建知识库事件被触发并生成新实例 |
| `field_rule` | 字段业务规则与属性约束 | 必填、唯一性、格式、长度、字符集、范围等限制 | 知识库名称在目标分组内的唯一性校验 |
| `state` | 特定状态下的行为约束 | 对象处于特定生命周期状态时的允许与禁止行为 | 文档处于 PARSING 状态时禁止触发检索 |
| `transition` | 状态机跃迁机制 | 合法跃迁触发条件，以及非法跃迁的明确阻断 | 任务从 QUEUED 跃迁至 PARSING，阻断直接跃迁 SUCCESS |
| `relation` | 实体关系建立与变更 | 实体间的从属、关联、挂载结果与有效性 | 知识库与分组建立归属关系 |
| `relation_lifecycle` | 关系全生命周期演进 | 关系的解绑、失效、恢复与级联删除保护 | 删除分组时对下属知识库的阻断或解绑策略 |
| `authorization` | 权限、角色与授权规则 | 角色访问控制、操作权限矩阵与数据权限越权拦截 | 普通用户禁止执行知识库物理删除操作 |
| `data_consistency` | 多实体与主从一致性 | 主记录、统计计数、关联明细、历史镜像间的一致状态 | 知识库文档计数与实际关联文档行数的一致性 |
| `downstream_effect` | 上游动作对下游的派生影响 | 上游对象变化后，下游候选、引用与依赖方的变更 | 分组重命名后，下游知识库面包屑导航的即时更新 |
| `invariant` | 业务不变量长期保全 | 系统在任何写操作或并发扰动下必须坚守的全局底线 | 系统中任一活跃知识库必须且仅能属于一个有效租户 |
| `negative_business_rule` | 明确禁止的反向业务规则 | 规范中显式规定的“不可/严禁/拒绝”业务限制 | 禁止对包含处理中任务的知识库执行归档 |
| `failure_atomicity` | 失败后的最终事实与一致性 | 按规则核对失败后应变化与应保持的内容，避免半写入或脏关系；不一律要求所有状态、历史和审计均不变 | 移动重名被拒后归属保持；若规则要求记录失败，则核对失败记录与其他事实一致 |
| `recovery` | 异常中断后的恢复与重试 | 核对实际定义的重试、重新进入及关系和历史连续性，不预设断点续传或继承进度 | 若规则允许重新处理，核对原标识、历史与新产物按规则衔接 |
| `concurrency` | 并发竞争与资源互斥 | 多请求并发、抢占资源、配额并发扣减时的互斥保护 | 两人同时创建同组同名知识库的并发冲突拦截 |
| `stale_state` | 旧页面与过期状态提交 | 根据有效规则处理过期状态、已变权限和旧配置，不指定版本锁等技术方案 | 若规则要求重新校验，旧页面提交时按当前权限和状态判断 |
| `scope_isolation` | 租户、组织与数据域隔离 | 数据与操作符合已确认的授权边界，不指定物理隔离等架构方案 | 未获授权的 A 租户用户不能查看或检索 B 租户的私有资源 |
| `long_flow` | 跨步骤长链业务连续性 | 多阶段异步演进、中间产物流转与端到端最终结果达成 | 文档上传 $\to$ 分块 $\to$ 索引 $\to$ 检索可用的长流程连续性 |
| `cross_module` | 跨系统/跨模块状态与事件传播 | 跨越微服务、独立子系统或跨边界事件消费的正确性 | 知识库元数据变更通知数字员工智能体更新挂载状态 |

---

## 3. 覆盖状态与去向闭环（不可无理由消失）

每一个从上游模型接收的重要业务事实（Event, Rule, Transition, Relation, Invariant, Flow），其对应的验证义务必须具备法定去向状态：

```text
coverage_obligations[].status:
  ├── covered               : 已由具体测试点（test_point_ids）承接
  ├── not_applicable        : 经过分析确认在本机制下不适用（必须提供 reason）
  ├── out_of_scope          : 明确属于本期排期范围外（必须提供 reason 与范围依据）
  └── pending_confirmation  : 业务规则尚不明晰，已关联设计问题等待确认（必须提供 question_id）
```

> [!CAUTION]
> **禁令**：
> 1. 上游已确认的事实严禁在测试点阶段“无理由蒸发”；
> 2. 不是所有系统都必须拥有全部 18 类机制，仅对当前业务范围实际存在的机制建立 Coverage；
> 3. 统计数字（如 100% covered）仅代表已发现义务有去向，不代表已穷尽真实业务的所有边缘风险。

示例仅说明分类含义，不替任何项目确定产品规则。环境暂不可测不等于业务不适用或范围外：本轮适用的机制仍由测试点承接，在审查摘要保留执行限制与后续交接。只有有效规则或获准范围调整才支持排除；`covered` 表示设计已承接，不表示产品执行通过。
