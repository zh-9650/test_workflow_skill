# Test Point Design Techniques 测试点设计与推导技术

本规范详述测试点设计中的节点分析、条件推导、基础功能反查、资料定向查证与设计技术按需应用规范。

---

## 1. 业务动作节点分析

对每个有独立业务意义的动作建立分析单元：

```text
source_context       : 动作从何处发起（页面入口、上游步骤、外部调用、系统定时）
actor                : 操作角色及当前具备的有效权限范围
preconditions        : 业务前置条件（主客体状态、已有关系、前置任务结果）
inputs               : 实际输入（表单/接口数据、环境配置、时间、上下文参数）
state_before         : 操作前主客体所在的生命周期状态
business_action      : 触发的具体业务事件或核心动作
outputs              : 动作直接业务产物（新实体、状态跃迁、回执、提示）
state_changes        : 哪些实体发生状态转移
data_changes         : 哪些物理字段/关联关系发生持久化更新
destinations         : 下一步业务流向或待办分发去向
downstream_impacts   : 对下游消费者、报表统计、缓存、索引的级联影响
invariants           : 必须保全的业务底线与不变量（哪些事实严禁改变）
```

## 2. 基础功能与常规操作反查清单（防长链遮蔽）

在长流程和复杂专项之外，必须反查需求和原型中实际存在的常规业务活动，防止它们被高级业务旅程吞掉：

| 基础操作类型 | 重点核对机制 | 常见遗漏陷阱 |
|---|---|---|
| **查询与筛选** | 单条件精确查询、组合筛选、模糊搜索、重置为默认条件 | 仅验证了有结果的情况，漏掉了“无匹配结果时的空状态与分页保持” |
| **分页与排序** | 核对已定义的默认页码、容量、翻页和排序规则 | 末页删除后如何定位、同值记录如何排序，先查有效规则，不自行规定自动回退或稳定排序 |
| **详情与回显** | 主从结构信息完整呈现、脱敏规则、富文本/特殊字符正常渲染 | 编辑页面打开时未完全回显已有复杂配置，导致再次保存被篡改 |
| **编辑与更新** | 核对更新范围、未改字段保留、无修改提交及并发冲突语义 | 只改一个字段却覆盖其他配置；冲突按有效规则处理，不指定乐观锁等实现 |
| **状态启停** | 核对有引用时能否启停、已有关系、新增使用和运行中任务的处理 | 有引用可能允许停用并保留关系，也可能按规则阻止；不能统一规定禁止停用或所有调用立即失效 |
| **删除与归档** | 核对删除或归档条件、关联对象处置、历史及名称占用规则 | 不预设物理删除、软删除、级联或名称释放；按已确认规则判断是否遗留错误关联或错误占用 |
| **批量操作** | 核对实际支持的选取范围、部分失败语义和结果反馈 | 不预设全批回滚或允许部分成功；根据规则判断是否静默遗漏、误处理或反馈不一致 |
| **操作历史** | 对已承诺的历史或审计信息，核对内容、主体、时间与保留规则 | 日志、版本或历史缺失需结合实际承诺判断，不自动要求每个写操作新增审计功能 |

清单用于提出查证问题，不是通用产品预期。功能存在不代表表中的所有细则都已确定；具体条件和结果必须回到有效来源，尚未明确的规则按缺口处理。

## 3. 动作与决定性条件推导范式

推导机制级测试点时，必须紧扣**决定性条件**与**成对证明边界**：

$$\langle \text{Actor, Context, Decisive Condition} \rangle \longrightarrow \langle \text{Substantive Oracle vs Superficial Trap, Invariants, Downstream} \rangle$$

1. **决定性条件 (Decisive Condition)**：
   - 必须精确指明是“哪一个关键变量处于什么状态”决定了走当前分支（例：`目标分组已存在同名活跃知识库`，而非宽泛的“前置准备好后”）。
2. **实质预期与表面假象**：
   - 实质预期说明业务承诺成立的结果，可以是读取内容、可用能力、状态或关系；不要求所有点发生物理写入；
   - 表面假象说明开发最容易犯的表面欺骗（只弹 Toast 但异步失败、接口 200 但内容为空）。
3. **保持项**：
   - 分别核对成功、失败与跨阶段过程中应保持的身份、关系、历史及其他事实。例如成功编辑基础信息不改变引用，成功回滚内容不删除历史；失败时仍可能按规则更新失败状态或追加审计记录，不能笼统断言所有字段和版本都不变。

## 4. 资料定向查证方法（定向补查）

当发现业务规则不完整或依赖机制存疑时，应按需开展定向补查，严禁全库无目标通读：

```mermaid
flowchart LR
    Q["1. 提出具体查证问题<br>(例: 停用资源是否允许被旧页面提交?)"] --> T["2. 选择目标材料与工具<br>(PRD / 依赖接口契约 / 历史缺陷)"]
    T --> S["3. 全文检索精准定位<br>(检索关键词获取对应段落/表格)"]
    S --> C["4. 读取上下文确认规则<br>(核对效力、版本与适用边界)"]
    C --> R["5. 带回适用条件与去向<br>(补充测试点或登记待确认问题)"]
```

- **查证原则**：
  - 先有问题，再查资料；定位后阅读完整上下文与图表，不断章取义；
  - 历史缺陷需阅读复现步骤与实际根因，不能只看标题；
  - 既有公共能力与老模块代码仅用于查清当前模块依赖的接口约定和风险，不把老系统的实现习惯盲目扩大为新需求。

## 5. 候选场景展开与缺口交接

### 5.1 候选场景展开维度
不是做无脑的笛卡尔积全排列，而是从可能改变业务结果的维度按需展开：
- `input_data`：输入特征与结构规则；
- `state`：对象生命周期前置状态；
- `actor_permission`：操作者角色与数据权限范围；
- `relation_dependency`：实体关联关系与引用状态；
- `config`：业务配置与策略开关；
- `time_history`：时钟有效期、时序窗口与历史记录；
- `execution_external`：异步队列状态与第三方依赖返回。

### 5.2 缺口分类与问题提出
> [!IMPORTANT]
> **纠偏**：设计问题绝不仅在“预期完全未知”时提出，而是涵盖以下 5 类正常业务确认：
> 1. `coverage_scope`：本轮测试覆盖的业务边界与排期取舍；
> 2. `risk_priority`：高风险机制的测试优先级评定；
> 3. `granularity`：争议业务机制的拆分或归并粒度；
> 4. `flow_coverage`：是否需要额外的跨模块连续性长流程覆盖；
> 5. `upstream_business_gap`：上游需求规则确实存在缺失或冲突（此类问题必须返回业务理解）。

## 6. 测试设计技术：按需作为推导工具

设计技术是推导机制的辅助手段，不是测试点的分类目录。声称使用某种技术，必须存在实际推导依据：

- **等价类划分**：用于输入类型、格式、枚举字典的有效与无效分类；
- **边界值分析**：用于数量、字符长度、时间范围、配额阈值的临界点识别；
- **判定表与因果图**：用于多条件相互制约、复杂准入互斥的规则规约；
- **状态迁移测试**：用于对象生命周期合法与非法跳跃路径的系统排查；
- **场景法**：用于长链路端到端用户旅程的骨架搭建；
- **错误推测**：结合历史缺陷记忆库，针对高风险实现盲区展开定向挑战。

## 7. 测试点与测试用例的分工交接

| 阶段 | 核心任务 | 不负责的事情 |
|---|---|---|
| **测试点设计 (Test Point)** | 明确**测什么业务机制**、触发的决定性条件、实质业务预期、防假象边界与保持项 | 不包含具体测试文件哈希、账号密码、边界数据样本（如 49/50/51）、具体点击步骤、定位器与脚本 |
| **测试用例设计 (Test Case)** | 将已确认的测试点展开为**具体环境下的可执行用例**、参数化数据组合、操作步骤与精确断言 | 不重新制定或脑补业务规则；若测试点含义模糊有权打回重修 |
