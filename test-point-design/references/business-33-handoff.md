# 业务理解 3.3 → 测试点 Skill：事实交接与纠错规则

## 0. 入参不以“旧模型字段够全”为准

首要输入：同版本、已确认的 `internal/business/business-model.json`、`deliverables/01-business-understanding.md`、`deliverables/01-business-understanding-review.md`，以及 3.3 的 `evidence/effect-ledger.json`（如实际交付）。再查原始 PRD、原型、评审和生效裁定。**上游缺少 effect-ledger 时不得自行补造“已核实”子句**；标记资料缺口，候选分析可继续，正式 3.3 交接前需取得真实的来源效力账本并复核。

模型版本和效力账本版本不一致、上游重要 Reviewer/业务人工确认尚未完成、存在改变预期的阻断问题时：只允许标注 `候选/受限` 的设计，不得标记可正式生成用例。源资料（含旧文档）的引用不等于当前有效事实。

## 1. 不重复上游建模，也不盲信上游

双通道，不颠倒：

- **继承通道**：逐条消费 `effect-ledger.clauses` 中 `active` 的独立子承诺；逐项考虑 `critical_paths` 的用户任务终态、失败/停止与时序交织；逐项继承 `discriminators` 中已证实的条件—结果差异。仍需对 `events/rules/transitions/relationships/invariants/cross_module_flows` 依原 Contract 双向建义务。
- **独立查漏通道**：原始 PRD/原型对照实际已存在的控件与操作（查询、重置、上传、键盘触发、关闭、编辑、批量及特定权限）、端到端用户任务、从状态/对象/权限/配置/时间改变反向推演、历史真实缺陷。仅生成**待核查线索**。存在未记录的业务规则时，查原件；仍无依据则回业务理解，不能由测试点 Skill 擅定正确预期。

覆盖义务必须对应可以违反的业务正确性：`在条件X发生动作Y → 应得到结果Z / 不得改变事实W`。一个上游事件往往需要多项不同义务；一项规则可能被多个事件消费。不得 1 事件=1 测试点、1规则=1测试点。

## 2. 来源效力与冲突处置

| 3.3 `scope` | 测试点阶段如何处理 |
|---|---|
| `active` | 逐条标记 `covered` 或关联真实待澄清问题；`covered` 必须关联具体分支，不能只挂来源 ID |
| `excluded` | 保留历史证据，不产生本期可执行正向预期；已取消功能若在有效测试点里出现，必须检查是否为否定约束/历史引文或真的复活 |
| `superseded` | 以明确的新生效子句为准；旧行为只作为变更/兼容风险线索，不能默默恢复 |
| `unresolved` | 保留可能的结果差异和上游问题，不写一个确定结论来“凑覆盖” |
| `dependency` | 确认作用边界（由谁控制、影响哪些在途与后续请求、可观察哪一事实）；不得把外部模块 CRUD 当本模块必做 |

相同结果若在 A 处“正式确定”，B 处又“待确认”，先核对作用对象、时机和版本，再去原始资料定位；查不到不能自圆其说。`--allow-waiting-confirmation` **不等于**正式允许错误期待交用例。

## 3. 应向下游交付什么

每个高价值验证分支给用例阶段一个简明可执行的设计包：

- `variation_axis`：决定分支的维度，例如操作时对象状态、配置有效版本、协议块位置、角色数据范围；
- `data_condition`：需准备哪类具备这些条件的实体/授权/文档，不必写具体账号或数据样本；
- `oracle`：看哪一个真正的业务事实来判断成功/失败，不能只看 Toast 或 HTTP 200；
- `required_variations`（来源明确存在不同位置/取值时）：列出不能被单个代表样本替代的变种，例如五个不同协议块缺失；这些仍可同属一个测试点。

关键流程另写任务起点、中间有效状态、可区分终态及被停止/重试/并发改变的事实。此阶段**不**编写详细执行步骤和数据值；不能靠“后续用例会补”掩盖尚未识别的业务分支。

## 4. 返回业务理解的明确边界

测试点发现上游未知行为时：登记 `场景/前提/两种可能预期/原始来源查证/影响的既有分支/责任人`，回到业务理解 3.3 更新有效子句及相应流程，标注版本失效。可以先完成其他已确认部分，但不能在没确认前任意挑一端作为 `CONFIRMED`。
