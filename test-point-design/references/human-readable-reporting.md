# Human-Readable Reporting 测试点报告与交付规范

本规范定义测试点阶段三份交付物的组织形式、人类阅读友好性要求、图文讲解规范及集中澄清机制。

---

## 1. 三份正式产物的清晰分工

测试点设计阶段输出三份标准产物，各司其职，严禁混杂：

```text
deliverables/02-test-points.md           👉 人工审查主报告（面向测试人员与业务专家，重在理解与决策）
deliverables/02-test-point-review.md     👉 审查摘要与审计底稿（面向质量负责人，重在发现、修正与限制说明）
internal/design/test-points.json        👉 内部结构化数据模型（面向机器与下游工具，重在追踪、引用与契约校验）
```

> [!CAUTION]
> **禁令**：
> 1. 主报告负责让人类高效理解与决断，内部 JSON 负责追溯与校验；
> 2. 严禁把 JSON 的机器字段（如 `primary_coverage_id`, `business_event_ids`）机械搬进主报告，生成难以阅读的八列超宽大表格；
> 3. 严禁让人为了看懂一条测试点而在多个文件之间频繁跳转。

---

## 2. 主报告 (`02-test-points.md`) 组织规范

### 2.1 人类阅读顺序架构
主报告应按照以下层次结构顺畅展开：
1. **本轮范围与版本基线**：说明当前测试的任务边界、排期版本与输入基线；
2. **基础功能验收导航**：为常规 CRUD、查询筛选、分页、详情等基础活动提供快速索引与定位锚点；
3. **业务路径图解与分流说明**：针对核心主流程提供直观的流程图，并紧邻附带自然文字解释；
4. **按业务任务/功能分组的测试点**：展示具体的机制级测试点；
5. **重点风险与剩余限制说明**：阐述当前环境或排期下的客观限制；
6. **文末集中待确认问题 (Grilling)**：集中向业务人员或架构师发起澄清。

### 2.2 测试点展现形式与排版
- **中文业务标题**：采用通顺、具体的业务短语（例：“跨分组移动时目标分组名称冲突拦截与状态保全”），禁止仅使用缩写代号；
- **排版形态灵活选用**：
  - 便于对比的一组测试点可使用小规模精简表格；
  - 复杂机制点优先采用**紧凑列表或结构化短段落**；
  - 目标、触发动作、决定条件与预期，以及适用的保持项和防假成功说明必须**默认可见**；普通点用短段落讲清，不强行填满同一组栏目；
- **业务优先级理由**：按业务任务/风险分组共享优先级理由，避免机械重复“P0/P1”。

## 3. 审查摘要 (`02-test-point-review.md`) 组织规范

审查摘要旨在向技术负责人汇报测试点设计的严密性与审查过程，重点内容前置：

1. **实际发现与修正记录（放首位）**：
   - 记录自查与独立复核中的来源、候选位置、发现、影响、处置依据及实际复核结果；复查直接和间接依赖，并核对原有正确事实未被误改。没有实际独立上下文时如实注明未完成，不能只填“独立通过”；
2. **重要排除与归并说明**：
   - 记录哪些场景被等价归并、哪些属于本期排除、哪些属于环境暂不可达；
3. **机制覆盖去向对账**：
   - 对 18 类 Coverage 的承接去向进行汇总统计与反查索引；
4. **严谨的语言定性**：
   - 必须严格区分：`已确认规则`、`合理推导`、`待澄清`、`观察手段待落实`、`设计推演`；
   - **绝对红线**：本阶段尚未进入真实执行，**严禁使用“PASS”、“已复现”、“已验证通过”等执行术语**。

机制总数和分组统计放次要位置。成功、失败及跨阶段中的变化和保持均按规则交代；当前环境无法验证时保留测试点、执行限制和交接，不混同业务排除。人工可直接定位需重点审查的条件、风险和争议，不能只得到覆盖率。

## 4. 待确认问题规范（文末集中澄清）

所有待确认事项统一在 `02-test-points.md` **文末集中呈现**：

### 4.1 提问标准
- **先查已有答案**：核对相关有效来源、依赖事实、上游裁定与已答问题，再提出确实缺失的决定；
- **自然讲清上下文**：用通俗语言交代场景、已知事实依据、尚缺决策点以及不同选择的下游影响；
- **引用自然来源**：指出相关 PRD 章节或原型图名，不单抛来源代号；
- **可回答的决定**：已知可行方案才给选项，客观说明影响；方案空间不明时开放询问，不强迫二选一；
- **支持不予推荐**：在缺乏充分业务依据时，显式标记 `recommendation_status: "not_recommended"` 并说明原因，严禁无依据强推；
- **业务缺口归位**：若问题涉及根本性业务规则或产品预期未定，必须标明 `return_to_business_understanding` 并退回上游。

没有待确认问题也明确说明，仍保留人工审查和正式确认。回复后按业务裁定、纠错、临时口径、范围调整或确认的实际性质，同步受影响正文、图、JSON 和审查摘要，复核共享规则与保持项；问题回复不是最终确认，人工确认也不代表产品执行通过。

## 5. 图解与 HTML 可视化阅读规范（按需提供）

当用户要求提供可视化图解或独立 HTML 界面时：
1. **同版本对应**：HTML 阅读界面必须严格同步同版本的测试点内容，并提供指向 Markdown 原文的链接；
2. **图文并茂**：流程图必须具备文字讲解，图中的连线、转折点与节点文字必须清晰易读；
3. **真实渲染检查**：确保 Mermaid 或 HTML 图表没有排版溢出、截断或窄屏错乱；若未经实际视觉核对，如实说明未验证项；
4. **产物地位**：HTML 仅作为人类阅读辅助界面，不替代三份正式产物的法定效力与版本确认规则。

## 业务理解3.3兼容和1.1新增的业务分支展示

- 主报告仍以**用户任务/基础功能/机制测试点**为阅读入口；不把内部 `branch_design` JSON 原样倾倒成几十页表格。
- 每一项高风险 TP 应直观展示：验证的业务机制、哪些关键条件使结果不同、分别应得什么结果、哪些事实须保持、怎样识别“显示成功但实质失败”；对能继续展开多种数据的同一机制，简明列出不得遗漏的变体，不强制每个变体单开 TP。
- 归并自多个义务的 TP 应在审查附件说明为何属于同一机制、所有源分支去向；另将长链起始条件、中间关键变化和成功/中止/失败终态分开说明。
- `02-test-point-review.md` 要说明本轮收到的业务理解3.3子承诺总量、当前有效/排除/待确定去向、关键链与正反题的实际承接、退化对照、用例可展开性抽查及无法核对的剩余证据；不得把 `branch_audit.py` 显示 ok 当成语义验收。
- 只有原件明确时才写固定业务结论。原型控件的存在与真实服务端生效分开描述，未真实操作的页面标记为静态依据。
